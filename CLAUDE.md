Reply provision therefore ENQUEUES a forking boot re-run, not just a promise resolution.
- **Attention:** per-opcode RETURN-to-scheduler from `JS_CallInternal` — NOT a JSPI suspend (JSPI saves the C stack while frames live on the heap arena → teardown desync/double-free). Universal, boot included. The yield CHECK is per-opcode; there are TWO orthogonal yield DECISIONS at that one check. (1) The VALUE yield — suspend the running flow the moment a parked flow outranks it (or on an emit/fork/suspension that changes ranks), NEVER after N opcodes (a per-N/opcode-budget counter is a step cap, banned); a flow that stays top-ranked runs on with ~zero switch cost; the WFQ, not a clock, decides WHICH flow runs. (2) The COOPERATIVE-QUANTUM yield — orthogonal and about THREAD-SHARING, not value: when the running flow has held the ONE worker thread for a bounded wall-clock slice, it suspends (same COW-snapshot suspend path as the value yield) and `scheduler_run` RETURNS to `qjs_step` so the host loop pumps messages / interleaves other engines / streams findings / snapshots, then re-enters and RESUMES THE SAME top flow on the byte-identical frontier. This is REQUIRED and universal (a lone engine has neither a competitor nor RAM pressure, so without it its one `qjs_step` never returns and the worker freezes, unobservable); it is a yield, NOT a cap (§NO BOUNDS) — it truncates nothing, drops/reorders no flow, and never decides what runs. The quantum is checked at BOTH the per-opcode hook (so a long single flow — e.g. trampolined recursion — yields mid-run) AND at `scheduler_run`'s loop head (so it returns to the host rather than re-dispatching the just-expired flow). Driving the call/object graph synchronously outside the scheduler (a boot epilogue) is the same sin as a bound — drive it per-orphan, yielding.
- **OOM:** snapshot/restore is ONE primitive (pause/resume, eviction, per-arm isolation). RAM = the hot working set; the cold/low-value tail moves to **IndexedDB** (not localStorage/`chrome.storage.local`). **Disk is the platform FLOOR — finite, real, NOT a bound to remove. IDB doesn't make OOM "impossible," it bounds RAM and moves the residue to a larger, slower floor. BFS is what makes that sound: it extracts the productive breadth before the floor is approached, so disk-pressure only ever touches the least-valuable starved tail, never lost productivity.**
- **PHYSICAL FLOORS CRASH LOUD; they are NOT masked.** Disk and RAM are the genuine physical limits of the unbounded BFS; the C stack is made a NON-limit BY CONSTRUCTION — trampoline every call, self-host every re-entrant. CALL-SITE-RESOLVED re-entrants (`.bind`/`.call`/`.apply`/`Reflect.apply`/the call-spread, and every CALL / READ / WRITE / MEMBERSHIP / DELETE THROUGH a Proxy) trampoline the ultimate target onto the heap frame stack AT THE OPERATOR SITE, because a proxy trap is a SINGLE handler dispatch with no C-stack continuation between invocations: `js_tramp_proxy_setup`/`_get_setup`/`_prop2_setup`/`_set_setup` re-dispatch the NORMAL handler — `apply(target,this,[args])` at `OP_call`, `get(target,key,receiver)` at `OP_get_array_el`/`OP_get_field`, `has(target,key)` at `OP_in`, `deleteProperty(target,key)` at `OP_delete`, `set(target,key,value,receiver)` at `OP_put_field`/`OP_put_array_el` — the OWNED handler method on `TrampFrame.owned_func` freed at every teardown, or forward to the target when the trap is absent. The handler's single result is carried by the `(call_first,call_argc)` stack-shape descriptor the `do_return` fixup reads: PUSH-1 for a value-producing trap (get/has/delete), PUSH-0 (`discard_result`) for `set` (an assignment leaves nothing on the stack — the compiler emits `OP_dup` before the put when the value is needed). The obscure `[[Get]]` frozen-property and `[[Set]]` strict-mode-throw invariants are documented DEVIATIONS: the trap's writes/fetches/taint all still happen, a proxy trap returning a spec-violating value is pathological, and any phantom past it is WFQ-starved (emits nothing productive), never a real endpoint. CONTINUATION-HOLDING re-entrants (array iteration forEach/map/reduce, String.replace, sort, JSON.stringify — sort+stringify short-circuiting an OPAQUE branch operand via the `__isOpaque` concretize, all compiled under `JS_SetBuiltinCompile`) hold loop/accumulator state on the C stack BETWEEN callback invocations, so they are self-hosted as bytecode (the loop becomes a heap bytecode frame; the callback dispatches via the already-trampolined `OP_call`). So overflow is IMPOSSIBLE by construction, never caught. The trampoline MUST restore the CALLER's closure `var_refs` on return (`caller_var_refs`) — else nested-closure non-tail recursion (a recursive tree-walk helper — ubiquitous) crashes. Hitting a genuine floor is a resource wall — IDB filling up crashes as OOM. UNTIL a re-entrant's self-hosting lands, its residual C-recursion overflow CRASHES the SAME way (offensive programming: LOUD, findings discarded, `_engineCrashOccurred`), NEVER caught-and-continued into a soft RangeError (masking a bound, building on an uncertain instance). The fix is ALWAYS to COMPLETE the primitive so overflow cannot happen, NEVER to catch the overflow or cap the depth to look "robust" — the exact soft-fail this project forbids. A crash on a not-yet-self-hosted path is a TODO surfaced loud, never a design.
- **Cross-session resume is REPLAY, not live-graph serialization.** A parked flow has TWO representations: HOT = the live heap frame in RAM (`JS_FlowResume` on the async heap-frame substrate — cheap suspend/resume for interleaving); COLD = a compact REPLAY RECIPE persisted to IDB = (bundle-ref/hash + the flow's DECISION VECTOR + accumulated value). It does NOT persist server data: rehydration re-derives example VALUES from CURRENT sources (fresh `fromReply`) so a resumed flow reflects the CURRENT API surface, never a stale snapshot — the whole point of the tool is the live surface, so byte-identical replay of last-session's data would be the WRONG goal. Eviction drops the live frame, keeps the recipe; rehydration RECONSTRUCTS the flow by re-running boot to the baseline then REPLAYING the decision vector — never by deserializing a live continuation + reachable object graph. **COW isolation is exactly what makes this sound: a flow's DECISION PATH is a deterministic function of (post-boot baseline, its OWN decision vector, its own execution) and NEVER of another flow's writes, so replaying its decisions over a re-run boot reconstructs the same PATH — shared state and interprocedural effects included, because re-running boot re-establishes ALL of them natively; only the concrete data values track the current server, which is desired.** Literal graph serialization is the WRONG primitive: it must rebuild object identity/aliasing across shared mutable state (the exact case that breaks it), and quickjs has no continuation serializer; replay sidesteps both. Replay cost is bounded by the eviction policy — only SHALLOW, low-value, few-decision flows are ever evicted (BFS keeps the deep productive ones hot), so a rehydrated flow is always cheap to replay. The decision vector IS the serialized continuation, compact and robust. **A recipe self-identifies by FUNCTION SOURCE (`JS_OrphanHash` = FNV-1a over the orphan's `b->source`), NOT by a positional collection index — collision-free + position-independent, so on resume it locates THE SAME FUNCTION by what it IS, in ANY context (present → drive with its decision vector; absent/different-source → skip; NEVER the wrong function). This is the ROOT that makes the frontier key just a RELEVANCE grouping (origin | bundle = external script srcs), not a soundness boundary: over-merging same-bundle-different-context documents is SAFE — each recipe finds its own function or skips — so NO per-context sub-keying is needed (only a fragile positional locator would require it; source-identity makes it unnecessary, and a coarse key gives better cross-visit resume). Shared state is re-established per document by re-running its OWN boot before replay; the same script in a different context is a different flow only because its baseline differs, and re-running that document's boot establishes exactly that. A positional index (or a filename+line+col hash) is the WRONG identity: script order / definition site shifts across contexts, silently pointing the recipe at a different function — the exact bug source-identity removes.**

But the app's OWN same-origin resources are TRUSTED ground truth to be LOADED, never left a shape: a fetch whose body is JAVASCRIPT is ALWAYS fetched + EXECUTED (a lazy chunk/module reveals real endpoints + branches + values — the headline moat surface); a CONFIG / same-origin DATA fetch is ALWAYS loaded so its fields become CONCRETE param examples, while its use in a BRANCH still FORKS / feasible-refines (loading kills the shape WITHOUT collapsing exploration — a loaded `features.admin:false` must NOT concretize the `if(features.admin)` gate, or the admin endpoint the moat wants is lost; config is opaque-for-control-flow yet carries its loaded value as the example, EXACTLY like `location.search`); a reply field flowing into a param drives the bounded `fromReply` GET. All via ONE bounded safe GET per resource, one-per-endpoint cached, origin-scoped creds under safeFetch's SOP/CORS; `location.origin`/`host`/`protocol` (the principal) is CONCRETE for URL building. A SHAPE for any APP-OWNED value is therefore a DRIVING FAILURE — the fix is to LOAD the resource or close the drive (real-instance drive, SSR seed, render-cycle), NEVER to accept `{shape}`; only genuinely-external attacker input legitimately lacks a real value.
- **Active discovery is REQUIRED** (lazy loaded scripts + discovery docs + Google API `req2proto` error-probes) — passive learning is too thin. Each active fetch is made FROM the document that learned the endpoint, CORS-bounded both ways to the page's own reachable surface, one-per-endpoint (no method is universally safe — GET can mutate via `/logout`, `/delete?id=`), never a blind sweep. Endpoints learned from runtime fetch/XHR hooks INSTEAD of QuickJS mean the core forced-exec is underperforming — fix the driving, don't lean on the hooks. **Static assets are NEVER endpoints** (magic-byte + content-type, not URL suffix) but still drive the code path. A STATE-MUTATING request (POST/PUT/DELETE, or a side-effecting GET like `/logout`, `/delete?id=`) is NEVER fired to learn — no `fromReply`, no probe, because the side effect is REAL — so its example values come ONLY from the local forced-exec path; that server-side-effect surface is the genuinely HARD frontier where forced execution must derive the request WITHOUT a real response, never by firing it.
- **Bind before build:** source a missing Web/spec capability host-runtime (JSPI) → engine intrinsic → existing Lexbor module → faithful spec port → hand-roll last (never crypto/parsers from scratch).
