**NO COUNTS, NO BOUNDS — the BREADTH-then-DEPTH WFQ scheduler allocates ATTENTION (which paused flow runs next); it does NOT terminate anything, and termination is not a thing it needs. A bound is NEVER better than the scheduler, only worse: it merely TRUNCATES distinct work the scheduler would otherwise reach productively.** Banned outright: depth/step/time/run/memory limit (INCLUDING a V8/native call-stack-depth limit — the engine NEVER throws a depth RangeError of its own; the call stack is REVIEWED REGARDLESS OF DEPTH), watchdog, idle/drain/no-progress count, pruning. A LOOP reuses one frame — never grows the stack — the PURE attention case (an infinite loop that might eventually emit is STARVED, resumable, never bounded). RECURSION grows the stack and is ALSO reviewed at EVERY level (the per-call yield hands the scheduler control); an unproductive deep recursion is STARVED (paused ~0 CPU) and its frame chain is SNAPSHOT + EVICTED to IDB so RAM stays bounded — **OOM is solved by EVICTING paused/starved deep state, NEVER by truncating depth.** Eviction = OS-swap for flow state: RAM holds only the HOT working set; when RAM crosses the limit the scheduler SNAPSHOTS the coldest/lowest-value flows (serialize the heap-stack frame chain + reachable object graph) to IndexedDB (NOT localStorage — too small + synchronous; NOT chrome.storage.local — banned) and FREES their RAM; resume RESTORES the buffer. So RAM is bounded by active concurrency, never by depth/flow-count. SNAPSHOT/RESTORE is ONE primitive serving everything: pause/resume (to RAM or disk), eviction (to disk + free), AND the shared-state fix (each flow/arm gets its OWN snapshot — an isolated clone per branch arm; resume restores ITS state, never another flow's mutation). The heap call stack is the prerequisite — a C-stack frame can't be serialized, a heap frame can. IndexedDB persistence is cross-session ⇒ a flow parked today resumes next session (continuous learning, never restarted). A stack overflow is IMPOSSIBLE by construction (segmented heap call-stack grows by segments); there is no depth at which work is declined. The model: run BREADTH first (BFS over forced schedules/frontiers = coverage) THEN DEPTH (the residue grind), every flow preemptible (JSPI stack-switch, no depth cap), cross-session-resumable, ordered by value-of-information — the ACTUAL output a flow emits (@H API endpoints AND @S XSS findings, weighted EQUALLY — never a static "reaches a network edge" guess; XSS reaches DOM/eval sinks, not the network) + a UCB-explore bonus for under-sampled flows + a fairness floor — so deep+wide RECURSION + INTERPROCEDURAL traversal is SPREAD over time, productive-first, never bounded. An unproductive flow is STARVED (~0 CPU, still resumable), never dropped; a YIELD only hands control back for the scheduler to pick the next flow; slow ⇒ fix the PRIORITISATION (resume-by-relevance), never the work. The synchronous-loop trap: anything that drives the call/object graph OUTSIDE the scheduler (a boot epilogue that walks it all in one blocking pass) is the same sin as a bound — it can't be preempted or starved, so it spins/stalls; drive it from the scheduler (per-orphan, yielding, captured-instance) instead.
