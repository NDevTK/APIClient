# Disposition
- **Best long-term design over everything** — over speed, safety, passing tests, and existing code. The design is never perfect; never stop improving it, never paper over a problem. One concrete landed diff per turn minimum. The stop-hook is a "go", not "did I do enough?". Context length is not a stop signal. Keep going — no drift toward closure, no quick-fix exits.
- **Biggest mechanism change comes FIRST.** Deferring progress to dodge risk is always wrong. A task's SIZE is never a licence to defer ("major undertaking", "own session", "fresh budget" are banned — there are no fresh sessions). The bigger the goal, the SMALLER the first concrete diff: decompose and land it THIS turn. A probe that localises the trap IS the diff; a verified narrowing IS the diff. A goal that stays a LABEL never progresses.
- **Regressions are encouraged**, never a reason to defer — regression risk COMPOUNDS every turn the wrong system stays load-bearing. Break first, then build the proper fix. Never revert a correct fix to dodge a regression. No bulk sweeps.
- **A superseded system is DELETED in the same diff, never kept as a fallback** (not behind an `if`, not a "safety net", not tried-then-overridden). A legacy fallback hides the new system's gaps and re-accretes dual-system rot; the new system must stand alone and CRASH where incomplete (the forcing function). "pre-existing" does not exempt code from removal.
- **Fix the ROOT; never mask it.** Make an impossible state impossible (complete the primitive), then delete the now-dead workaround. Fix limitations — never document a gap instead of fixing it, never a comment where a DCHECK belongs. Ask only to resolve genuine intent ambiguity, then follow up until resolved.
- **A `DFAIL` OUTLIVES THE ABSENCE IT DESCRIBES, AND THEN IT LIES.** The crash that names what to build is the right mechanism, and its failure mode is the mirror of a stale comment rather than the same one: the text stays accurate about the SPEC and goes wrong about THIS TREE, so it reads as authoritative while sending the next reader to build what is already there. Three in one session: `rendering.c` said report-an-exception "is a component this engine does not have" while `error_event.c`'s own comment recorded that this very DFAIL is why it was written; `shadow_root.c` said "this engine has exactly one registry" in three places after `CustomElementRegistry` became constructible; a DFAIL instructed the next person to build `tooLong`/`tooShort` from `minlength`/`maxlength`, which §4.10.19.3/.4 make unreachable without a user edit — the instruction was SPEC-WRONG and had been followed once. So a DFAIL naming another file is a claim about that file, and the claim is CHECKED before it is trusted and RE-CHECKED before it is repeated: grep the entry it names before writing the code it asks for, and when you build the thing, delete every site that named it — the one that crashes and the prose that agreed with it. A capability whose crash you cannot find is a capability you must assume exists.
- **THE INDEX IS SHARED, SO `git add` IS A PUBLICATION AND STAGING MUST BE ATOMIC WITH COMMITTING.** A shared checkout means `git commit` sweeps whatever is in the index, including another agent's `git add` that landed between your edit and your commit. `git add <explicit paths>` does not protect you. When a file holds your hunk AND someone else's work in progress, stage the hunk (`git diff -- <file>` → keep yours → `git apply --cached`), never the file. **`git commit --only -- <paths>` and `git commit -F - -- <paths>` are the same trap wearing a pathspec: they take WORKING-TREE content for those paths, not the index**, so a path you verified is not the content you commit. EIGHT sweeps happened in one session, and two of them defeat the older form of this rule, which said verifying `git diff --cached` immediately before committing was enough: (a) an agent DID verify immediately before, and the index still changed between that command and `git commit` — two commands are not atomic; (b) an agent staged its hunks and kept working while it waited on a build, and a different agent's commit published them under a message about something else entirely — the whole cold tier landed inside a commit titled for @S reproduction envelopes. So the rule is not "verify late", it is **stage and commit as ONE uninterrupted operation, or do not stage at all**: hold your work in the working tree, and when you are ready, `git apply --cached` your filtered hunks and `git commit` with nothing in between. A `git add` you leave sitting is not a private note, it is an offer. **Never rewrite pushed history to fix attribution** — an amend or a revert-and-recommit under other agents is strictly worse than a commit whose message under-describes it; state the mis-attribution in the report instead, and rely on the code carrying its own explanation at every site.
- **Do subproblems IN ORDER** — never jump to a problem before its subproblems. If a shortcut was taken, remove that code.
- **Aggressively delete non-perfect code, riskiest first** — that shows you care how the system works; dead-code removal takes no risk and shows nothing. Delete anything a browser engineer or solver engineer would not fully endorse.
- **A LEGACY FALLBACK IS A `DFAIL`, NOT A REPORT.** Logic not designed for suspend/resume that still runs is an unbuilt capability, and the file already has the mechanism for that: it CRASHES at the site, naming what to build. Do not invent a register, a hit counter, or a harness line that lets the suite stay green while a non-suspending path keeps running — that is choosing a green result over the forcing function, and it is the same risk-avoidance as keeping the legacy body. The conversion sequence ends in the DFAIL: widen the selector, build what the failures name, DELETE the body, and the C entry becomes `DFAIL("… reached its C entry with an ITERABLE source — route that call site")`. If several directories go red at once because the fallback is still reached, that is the correct state and the work queue, not a reason to build a softer mechanism. A site that is a genuinely DIFFERENT algorithm (Array.from over an array-like: length+indices, no @@iterator) is not a fallback at all and must not be tracked as debt — mislabelling it manufactures an obligation to delete something that should stay.
- **A REJECTED OR INTERRUPTED TOOL CALL MAY HAVE ALREADY RUN — verify the tree, never assume.** A compound command (`git checkout … && gcc … && …`) can execute its first stage before the rejection lands. Twice this has destroyed committed-quality work whose loss was then REPORTED AS "the revert didn't happen" — a false claim about the state of the repo, which is worse than the lost work. After any rejection, interruption, or surprising result: `git status` / `git diff` / `grep` for the symbol you believe you changed, and state what the tree ACTUALLY contains. The same rule covers every "same place / already fixed / not a regression" claim — CHECK THE DIFF, never a snapshot of the current file, which shows where a line IS and proves nothing about where it WAS.
- **PUSH BACK — sycophancy is a design failure, exactly like a defensive fallback.** Agreeing because something was asserted (by me, you, or the existing code) rather than because it is SPEC-TRUE is the same evil as swallowing a crash. When a claim conflicts with the spec (ECMAScript/WHATWG) or the real code, say so and prove it (`JSON.parse(location.hash)` throws `SyntaxError` in V8 — the honest answer, never a fabricated reason it doesn't). Deferring to authority over spec is a bug. Treat positive feedback as always-to-be-worked-on. Approximations are worthless. Avoid the word "genuinely" — it is a cop-out.
- **Own the push.** Commit + push VERIFIED work to `main` yourself. Engine = a clean quickjs-ng-delta fork (submodule `engine/qjs`, branch `apiclient-v2`, synced to upstream `quickjs-ng/quickjs`); the host/scheduler lives OUTSIDE the submodule (`engine/host/main.c`) to keep the fork a minimal delta. Build: `node engine/build.mjs`.

# Offensive programming — the mechanism is `engine/host/check.h` (mirrored on the JS side by `extension/check.js`)
Always safe to ship DCHECKS! If crashing thats a blocking issue to support properly. Pre-existing flaws must be fixed when order is right.
- **Every error/crash/abort in a DEV build is CORRECT, never softened.** It is exactly one of: (1) an UNEXPECTED STATE — an invariant the design must guarantee, eliminated at the ROOT so it cannot arise; or (2) a FEATURE THAT SHOULD EXIST but does not yet — BUILT at the root as a proper system. NEVER caught / swallowed / logged-and-continued / clamped / `?:`-past, never wrapped in try/catch for "browser-faithfulness". A crash is the system doing its job (forcing the root fix). A page's own uncaught throw aborting boot is INTENTIONAL — the engine has not yet faithfully implemented that capability; build it at the root. In release we cannot fix or add features, so the same error is ALSO correct (it fails because the capability isn't supportable outside dev); the release exemption never licenses a dev-mode fallback.
- **`DCHECK(cond,msg)` / `DFAIL(msg)`** = DEV-ONLY should-never-happen (design invariant, not-yet-built capability, COW-host gap). Aborts loud at the origin emitting `@WHY` with cond+file:line; compiled out in release (`-DAPICLIENT_DEV=0`) — condition MUST be side-effect-free, never recoverable control flow. Asserts "the engine's OWN logic is correct."
- **`CHECK(cond,msg)` / `CHECK_FAIL(msg)`** = ALWAYS fatal (dev AND release, emits `@E`) for a universal invariant that must hold in production: OOM/allocation (a dropped flow corrupts the frontier), a physical RAM/disk floor, a security/authorization boundary, data integrity. Asserts "we must not PROCEED even in production." When unsure, it is a DCHECK.
- **Assert EVERY invariant EAGERLY at its origin; too FEW asserts is the failure.** A bad state caught late is a bug you built on; caught where born it is a fix. Never a `?:`/`if(bad)return`/clamp/default past a broken invariant; never a try/catch that swallows one. Migrate every raw `abort()`/hand-rolled `@E`/`@WHY`/`assert` to the right macro. The goal is ZERO `@WHY`, reached by fixing the root — never by muting the check. DCHECKs are always safe to ship (no production effect). NOT a `@WHY` (do not assert these): a forced-exec flow THROWING on opaque/attacker input, and an unsolved `@S` sink (a parked search) — those are the exploration surface, not broken invariants. Learnings from a non-best design are worthless — known-incomplete logic is still a should-never-happen DCHECK.
- **Confident change = small components × two-sided asserts** — ONE system, not two. An isolation-testable component is a narrow interface you exercise with ONE fixture AND whose invariants crash loud when violated. Without the asserts it silently corrupts; without the boundary the asserts have no contract. Split every over-large file until each piece is one assertable contract; give each component its own DCHECKs. Metric: can you exercise this with one fixture AND does a violated assumption crash at its origin?
- **A FIELD A CONSUMER DEFAULTS IS A FIELD NOBODY WILL NOTICE IS NEVER WRITTEN, and the default is not the symptom — it is the concealment.** `x || 0`, `x || []`, `x || {}`, `x ?? d`, `x?.y`, a `catch {}` around a read, an `if (kind === N)` on a value the producer never returns: each turns "the producer does not produce this" into a plausible datum, and a plausible datum is indistinguishable from a measurement. SEVEN instances surfaced in ONE session, every one a live product defect and not one of them visible as a crash. `qjs_result` had NO CALLER and `result || {}` made that `{success:true}` with zero endpoints — a false clean bill from a run that learned nothing. `bridge.js` branched on `st === 1` for NEED_FETCH while `qjs_step` returns only DONE(0)/YIELD(2), so the whole `qjs_pending → safeFetch → qjs_provide` reply path was UNREACHABLE in the shipped extension and every flow a page's `fetch()` parked stayed parked forever — §Attacker-sources calls learning from replies "the POINT", and it had never once happened. The popup read `cspBlocked` where `solve.c` emits `cspBlocks`, so EVERY finding badged HIGH and a breakout real Chrome's CSP kills was reported as a clean XSS. `canVerify` required a `shape` field carrying a `{hash}` vocabulary the engine has never spoken, so live verify rendered for ZERO findings ever emitted. `resolverErrors || []` dropped every engine-recorded page error (`pageErrors`). `_orphans`/`_work`/`_parked || 0` were three names nothing emits, so the interleave diagnostic read zero forever. `@RESUMED` had a reader and no writer, so the number written to prove the cold tier read its residue back was `0` for every session there has ever been. **THE TELL IS GREPPABLE AND THE RULE IS MECHANICAL: a name that is READ somewhere and WRITTEN nowhere is a broken contract, and a default is what stops it being a crash.** So a consumer NEVER defaults a producer's field — it DCHECKs the field's presence and shape (`extension/check.js` mirrors `check.h` for the JS side), and a value the producer can legitimately omit is a POSITIVE statement the consumer reads as one (absence of `cspBlocks` IS `policy_allows` returning true), never a hole a `||` fills. When you add a reader, grep for its writer; when you rename a field, the old name must not survive on either side.

A JS orchestration layer is unwanted context-switching across the JS↔WASM boundary; DELETE it. The ONLY irreducible JS is a BRIDGE (never logic), dictated by SECURITY.md: the untrusted WASM bundle cannot fetch (all network via the trusted `safeFetch` chokepoint), cannot touch IndexedDB/`chrome.*`, cannot paint the popup. So JS is: relay safeFetch/IDB/chrome to host-edges, load the WASM, render the popup. WORKING JS IS NOT MOVED INTO C ON THIS RULE'S SAY-SO. Anything the trusted zone computes once, before or between flows, stays where the failure mode is a wrong answer rather than a corrupted heap. **AND THERE IS NO LIST OF WHICH-JS-IS-WHICH — `extension/jsaudit.mjs` IS DELETED.** It was a 510-line gate holding a row per file, a derived dependency order and a failing queue, and every one of those parts existed to answer "when does this file become C?" — a question this section no longer asks. Every retained bridge edge gets a DCHECK on the engine↔JS contract (a null/malformed engine result crashes in dev, never an `if(!x)return`).
- **Use browser / JS-engine developers' concepts and names — never coin a system when an established one exists.** `DCHECK`/`CHECK` are right because they ARE Chromium's `base/check.h`. Inspect values/heap/leaks with quickjs's existing dump infra (`JS_DumpValue`, `JS_DumpGCObject`, `JS_DUMP_*`, the `-d`/`ENABLE_DUMPS` path) and V8-style native-syntax debug intrinsics — never a bespoke page-global tool (fingerprintable, duplicative). **THE DCHECKs ARE THE GATE.** The engine asserts its own invariants at their origin and aborts loud where a capability is missing, so a change is verified by whether the asserts stay silent — not by a suite going green. `node engine/build.mjs cow` is too slow to run as a check; test262 under `FORK_PREEMPT=1` is how you EXERCISE code so the asserts get a chance to fire (and its `gc_obj_list` walk counts a leaked GC object as a failure), never the thing that certifies the change. An assert that fires names the exact unbuilt mechanism — that is the signal to build it, and a passing suite with a silent assert proves nothing it did not exercise. A memory bug (UAF/double-free/refcount/leak) is found by READING the ownership contract at the site that breaks it, then asserting it: a struct copied field-by-field must dup EVERY owned field, so adding a field creates an obligation at every clone/free/finish site — a DCHECK at the clone is what makes that impossible to miss, not a sanitizer run after the fact. Inspect with the existing dump infra (`JS_DumpValue`, `JS_DumpGCObject`, `JS_DUMP_*`) and gdb. A `printf`/marker probe is BANNED — it perturbs a timing-sensitive bug and reinvents existing infra. Use targeted Asan for memory crashes.
- **Don't code browser features in JavaScript.** Browser features are C engine components. (This is why continuation-holding builtins are HOOKED into the flow machinery, not re-hosted in JS — see §C-stack.)

# Browser half — a SOLVED problem: follow the spec, build like a browser
- **The project in one sentence: a browser with a BFS time-travel solver. Two halves, never blurred.** The browser half must look, behave, and be BUILT exactly like a browser — every semantic traces to a SPEC (WHATWG percent-encode sets, HTML5 tree-construction insertion modes, ECMAScript, CSP, Trusted Types, mXSS re-serialization), implemented as a COMPONENT (`location.c`, `domparser.c`, `dom_element.c`, Lexbor parse, quickjs exec) with a DCHECK asserting the spec invariant. **THE SECTION NUMBER IS PART OF THE CITATION — "per HTML" is not a citation, `HTML §13.2.5.43` is.** A named spec with no number cannot be looked up, so it cannot be checked, so it is indistinguishable from a recollection; the number is what makes the claim falsifiable by the next reader, which is the whole value of tracing to a spec at all. **AND A CITED NUMBER CARRIES AN OBLIGATION TO BE RIGHT — a wrong one is WORSE than none**, because it reads as authoritative and sends the reader to a section that does not say what the code claims. That is the stale-`DFAIL` failure mode with a spec behind it: true-sounding, unverified, and load-bearing. Numbers RENUMBER, so a citation names the section's TITLE beside its number (`HTML §13.2.5.43 comment start state`) — the title survives an edition the number does not, and a mismatch between the two is then visible instead of silent. VERIFY the number against the spec text before writing it, never from memory: `§13.2.5.41` was written here for "comment start state" minutes after this rule was set, and §13.2.5.41 is the BOGUS comment state. Real Chrome is CONFIRMATION, never the source of truth — the spec is. A browser-fidelity gap is always "implement the spec at the root," a bounded known-answer task. The browser half should be BORING and spec-locked; a surprise there is a fidelity bug.
- **ORDER and NARROW behavior ARE the spec, not details to approximate** — event-loop task/microtask ordering (Promise/`await` resumption), insertion-mode order, parse-then-execute script order, DOMContentLoaded-then-load; the per-component percent-encode SET, `<template>`/RCDATA/foreign-content parsing, `[[Get]]` frozen-property, `slice(1)` on the source's real leading char. The solver runs ON TOP of these, so a wrong order or fudged edge silently corrupts what it solves. Most "solver gaps" are really the browser behaving slightly wrong.
- **A PER-REALM FACT IS ANSWERED PER REALM, AND A MODULE-STATIC PROTOTYPE IS A WRONG ANSWER — not a wrong identity.** `js_call_c_function` does `ctx = p->u.cfunc.realm` (and `js_callee_realm` does it for every step machine), so a member installed ONCE answers every document's question with the DEFINING realm's `ctx` forever. That is not the pedantic half of §3.7 — it is how `window.locationbar.visible` reported every popup a tab (the root navigable is not a popup and the root is whose ctx arrived, and the 51 subtests split exactly along that line), and how a shared `EventTarget.prototype` registered every iframe's unqualified `addEventListener('load', f)` on the ROOT window. The MECHANISM is quickjs's own per-context class-proto slot (`JS_SetClassProto`/`JS_GetClassProto`), built EAGERLY at the realm's creation beside `JS_AddIntrinsicDOMException` — never lazily on first read, which creates a baseline object inside whichever flow happened to touch it first. A runtime-lifetime FUNCTION OBJECT carries a realm the same way: mint it in the realm that uses it (per fire, per call) rather than holding one in a static. The defect class is ONE fact answered from ONE place for MANY agents — a module static, a hardcoded string, a remembered global — and the fix is always to ask the realm, never to set the static from more places. **The list of per-realm intrinsics must live in ONE place that EVERY realm goes through, including the agent's first one** — a `_install` line hand-copied into each host's child-realm builder is the hand-picked list `build.mjs` warns about, and a component missing from one copy silently shares another realm's prototype with nothing to say so.
- **NO STUBS.** A shape-only object with noop methods, or a getter returning bare opaque WHERE THE SPEC COMPUTES A REAL VALUE (a `getComputedStyle` that returns opaque, an IndexedDB `put` that drops its value), is a fidelity gap marking where the real impl belongs — fill it in its real-browser-named component (`intersection_observer.c`, CSSOM, `indexeddb.c`), never a generic bag file. A web API not yet built is honestly ABSENT (the page's own throw on a missing global is the forcing function).

Every member is real C (a computed value; the concolic value only where the value is unknown, e.g. `AbortSignal.aborted`; a dedicated documented no-effect ONLY where the spec defines no scriptable headless result, e.g. `element.click()`). `js_noop` as an interface member is BANNED — it is the lazy stub the audit exists to expose. Use the IDL's TYPES (coercions, nullability, `[Reflect]`, `[CEReactions]`) as the spec of behavior to implement, never as codegen that fabricates it.
- **Headless is not valueless — MODEL the state with mock-backed IO, don't shrug to opaque.** The only missing piece is a physical IO device; the spec still defines behavior without one. File System Access presents a MOCK filesystem that ROUND-TRIPS — `file_system.c` is the FS Standard's own model (file/directory entries, binary data, the lock and its shared count), reached through `storage_manager.c`'s bucket root and `file_system_handle.c`, and a byte written through a `FileSystemWritableFileStream` is a byte a later `getFile().text()` reads back. This line used to point at a `storage.c` that has never existed in this tree, which is why the file it named must be one you can open; `HTMLMediaElement` is a real state machine that plays with no device; `matchMedia` resolves a default viewport for its `.matches` example yet stays CONCOLIC (a branch still forks the alternate-viewport world); `getComputedStyle` layers UA-default + inline; `AbortSignal` is the real aborted-state machine; a `[CEReactions]` op RUNS custom-element reactions. Opaque is reserved for the UNKNOWABLE (attacker input, server-injected absent state), never for "there is no device." Never collapse a modelable value to bare-concrete either — that deletes the fork and its coverage; the concolic value is opaque-for-control-flow yet carries the concrete example. Err toward MORE exploration (the WFQ starves the unproductive arm).

# Solver half — the NOVEL contribution: forced multi-path concolic execution on time-travel primitives
- **Every value is CONCOLIC — a triple of (source-identity provenance, a constraint-DOMAIN of what it can be, a concrete EXAMPLE when the code pins/computes/learns one). There is no binary "opaque" sentinel** — that oversimplification is deleted. "Unknown external input" is the MOST GENERAL concolic value: unconstrained domain, no example yet, tagged by source. The solver's whole job is to NARROW the domain and FILL the example. Every predicate narrows (`x=='p'`, `startsWith('http')`, `<3`); every op propagates the example (`"/api/"+cfg.region ⇒ /api/us-east-1`, never `/api/{region}`). The example propagates because the engine RUNS THE REAL OP on the concrete (the `+` actually concatenates) — NOT because a carried label/note is derived by a propagation hook. The triple RIDES the value the interpreter already computes; it is not a second value-class shadowing it. A separate tagged-value class whose result-note a `Combine`-style hook derives at each op IS the recorded transform-expression §Re-execution forbids (it cannot see interprocedural/shared-mutable state), a redundant WORSE taint tracker beside the sound re-execution search — building one is the cardinal misread of this line, not an implementation of it. `JS_IsConcolic` (domain-carrying) is the only predicate; a re-introduced know-nothing branch is a regression.
- **Forced multi-path (J-Force lineage) FUSED with a per-flow path constraint (DART/SAGE/Kudzu lineage).** Concrete execution is the GROUND TRUTH that grounds all shared/interprocedural state, so the constraint is only ever over INPUT variables — which is why "a solver can't model shared state" is a category error (the solver never sees state). Control flow is FEASIBLE-REFINED by the domain, not blind fork-both: where the domain permits both outcomes BOTH arms run (reaching gated/admin code); a contradicted branch is pruned (sound-only — uncertainty keeps the arm). **CONCRETIZE-ON-PIN**: once `x==='admin'` pins the value, a later branch on it is decided by RUNNING the real predicate on that value (`cons_eval_pinned`, no fork); symbolic contradiction detection is only the unpinned residue (an open interval like `x>5 then x<3`). The scheduler asks the substrate ONE feasibility seam and holds zero constraint logic.
- **`@H` and `@S` share the explorer + constraint but DIVERGE at emission — conflating them is a dumbing-down.** `@H` must NEVER INVENT: a param pinned by `x==='v'` concretizes to `v` (the code determined it); a param gated only by range/prefix/regex stays a DOMAIN-ANNOTATED SHAPE (`{int>5}`, `{startsWith:/api}`) — inventing `6` for `x>5` fabricates an observed key. `@S` SOLVES/SEARCHES freely for a firing input (equality tokens, in-range values, negative/blocklist constraints, gate-guided breakout) because emission is WORKING-POC-ONLY and fire-verified — a wrong solve simply never fires and is discarded, so completeness beats purity.
- **Re-execution discharges the constraints — NO external Z3, NO taint tracker, NO recorded transform-expression, NO chain-inversion** (a transform-expression cannot model interprocedural + shared-mutable-state code; running the real code subsumes it). Not because running code is stronger at algebra (it is not), but because @H never solves (algebra's use is gone) and the @S constraint is "breaks out at the REAL sink after the REAL transforms," which only re-execution decides soundly and re-running the candidate makes safe. NO state-merging (veritesting) and NO function summaries (unsound under shared mutable state) — path explosion is handled by WFQ starvation + re-execution. Opacity SURVIVES numeric coercion (`+x`/`Number`/`parseInt`), so control flow keeps forking rather than collapsing to NaN.
- **A JS-engine encoding builtin is modeled FAITHFULLY, never re-implemented or enumerated by the solver.** `JSON.parse`/`stringify`, `encode/decodeURIComponent`, `escape`/`unescape`, `btoa`/`atob` are spec builtins like `+`: the engine runs the REAL codec (concrete truly encoded; concolic flows through shape-preserving). The solver must not hand-roll base64/percent/JSON nor emit encoder-inverted candidate variants (wrong layer, redundant). A builtin that can THROW runs and throws faithfully like V8 — `JSON.parse(x)` on opaque input FORKS a feasible success arm AND a throw arm (the real `SyntaxError` propagating to a `catch`→sink, or aborting visibly when uncaught); the leading `#` makes `JSON.parse(location.hash)`'s success arm infeasible so it throws exactly as V8 does. Special-casing a builtin's result to bare opaque is a double fidelity bug.
- **Learning from replies is the POINT, never suppressed.** The JS/JSON a server returns is the richest source of real example values; a consumed reply is ALWAYS fetched to fill examples (JS bodies additionally EXECUTED for their endpoints). ONE concolic value carries both the forking symbol AND the concrete example — never split into separate passes (a gated endpoint would then lack the gate-independent values the other pass knew). At a branch the example marks the real arm PRIMARY; the forced sibling drops the contradicted example, so only gate-DEPENDENT values degrade to a shape while gate-independent values stay concrete. Safety is NOT the sandbox's job: the untrusted WASM holds no network/security policy and learns freely; `safeFetch` alone enforces SOP/CORS/method/credentials. A safety `if` inside the engine is a layering violation.

# The scheduler — BFS + time-travel, each code flow run fairly
All code flows types such as long-running loops at ANY time and depth must be suspend/resume never drive-to-completion!
- **A "code flow" is a path through the program, isolated by its per-flow COW delta and captured as a SNAPSHOT.** BFS runs flows by value-of-information, FAIRLY — no flow monopolises; a deep loop suspends and yields so siblings run, then resumes. Time-travel: a COW snapshot holds any flow's state; suspend parks it, resume continues it from the exact point — hot in RAM or cold on disk, identically. A large loop is just fair BFS work, always suspend/resumable.
- **NO BOUNDS, ever.** Never a depth/step/time/run/memory/recursion cap, watchdog, idle/drain/no-progress/recycle count, seen-set, or same-args/same-state fixpoint. A bound truncates distinct work. Only EMITTED OUTPUT — never identity — proves a flow is done: shared state means byte-identical args can still PROGRESS, so a "re-computes nothing" proof is a cap in disguise. The engine never throws its own depth `RangeError`; recursion is reviewed at every depth.
- **ONE WFQ policy at both levels** — an anytime-bandit priority: accumulated emitted VALUE (new @H+@S) + a UCB optimism bonus ∝ 1/(visits+1) so a never-run flow is never starved − CPU-AGING so a monopolizer that burns CPU without emitting sinks below productive+unrun flows. Additive (not a literal value/cpu ratio, which degenerates 0/0 on unrun flows), ORDER-only, never drops a work item. **Level-2 (within a document):** the engine orders its flows (boot fork, branch-arm, orphan-invoke, loop/recursion arm), each a COW snapshot on the heap call-stack, preemptible per-opcode, suspend/resumable across sessions; the running flow yields the instant a parked flow outranks it. **Level-1 (across documents):** one WASM instance per page, so the host orders live per-page engines by best-flow weight, runs the top until its best flow no longer outranks the runner-up, then re-ranks. Engine creation is admission-gated to the RAM working-set floor; a fetching engine is skipped so one doc's wait never stalls another; an engine self-parks its residue to the IDB cold tier under pressure. Cold-tail resume is the SAME admission step (not a separate loop), ranked by a `frontierWeight` estimator (emit-per-visit, since a parked flow has no live CPU to age by).
- **ONE global, continuous, cross-session frontier** — one attention process for the whole extension; the frontier is the UNION of every flow from every origin ever visited, persisted in IndexedDB, never reset. A new page APPENDS its flows (boot fork + orphans); it does not start a new scheduler/run/attention. A browser restart resumes the same frontier by global value-order. Any per-page/per-session/per-tab scheduler, registry, run-counter, or reset is the cardinal violation.
- **THERE IS NO GRIND — BFS is the one system.** Orphan-driving (force-invoking a never-called function to surface its unused endpoint) is just another BFS flow. "Breadth first THEN depth" is ONE continuous BFS whose ONE WFQ merely orders higher-value-of-information flows ahead of lower — one queue, one registry, one loop. A second scheduler beside it (engine-side silent-counts/fixpoints/deep-step driver, or host-side deep-grind loop / no-progress recycle / per-culprit abandon) is the cardinal violation. **The @S candidate re-fire is a FLOW in this ONE BFS, never a separate executor.** A standalone verify driver (a `flow_exec_once`-style `while(JS_FlowResume){}` that runs one candidate start-to-finish with preemption OFF) is the same cardinal violation twice over: a SECOND scheduler beside the BFS, AND a drive-to-completion (an unbounded candidate loop hangs, non-parkable — violating §scheduler's suspend/resume-at-ANY-depth). A candidate re-fire is seeded as a candidate-session flow on the ONE frontier, preemptible and parkable like every other flow; the sink firing is observed by the same detectors during its scheduled run. No verify subsystem, no carve-out — the same ONE loop verifies as explores.
- **AN OPERATION THAT BECOMES A WORK ITEM TAKES ITS INPUTS WITH IT — anything it reads back off the object it acts on is read at the wrong TIME.** This is the defect that arrives with every conversion from a call to a job, and it arrives silently because the wrong value is a REAL value belonging to that object. §7.4 step 14's load is the worked example. As a call it fetched the address it was given; as a job it read the address off the navigable, which is right for the create that named the navigable after its destination and WRONG for `open("post-to-top.html","iExist")` — a navigation whose target is a srcless frame whose own address is `about:blank`. The destination was discarded, the frame materialized empty, and the only symptom was a test waiting for a message. The same sentence covers §7.2.6's inherited policy (whose clone it is depends on the OPERATION — the creator's for a create, the initiator's for a navigation — never on the state of the thing being loaded) and §4.4's base URL (resolved by the INITIATING document, which by the time the job runs is the document being replaced). What the target's state may still decide is what is genuinely a fact about the target and not about the operation — here, the document's IDENTITY. **AND THE OBJECT'S OWN STATE MUST BE THE PRE-OPERATION STATE, which the spec already says.** §7.4 creates a navigable holding the initial `about:blank` and navigates it afterwards; storing the destination there instead was harmless while the load was synchronous and became a DOUBLE LOAD the moment it was not — a read reaching through before the job ran built the destination early, the job then found a materialized navigable and loaded the address again into a second document. Two fetches, two realms, one navigable, nothing to say so. When you make something asynchronous, re-derive every field from the spec's ORDER, never from what the synchronous version happened to leave lying around.
- **A CAPABILITY MATERIALIZED PER FLOW AND NEVER RECLAIMED IS A CEILING, and the probe that cannot afford it is the measurement, not the problem.** A child realm is built once per flow that creates a navigable with an address (its scripts are an observable), recorded, and released only with the agent — so a fixture statement creating one src'd iframe asks for one realm per flow and the heap ends at 4022. The response is NEVER to soften the probe, and never to defer the materialization that made it honest: it is to NAME the ceiling in the assert that fires (the reader of a `@WHY` is standing at the allocation, and "OOM" alone tells them nothing about realms) and to build the reclamation. A "destroy" that only sets a `closed` flag while the document, its Window and its realm stay allocated is a STUB in §NO STUBS' sense — §7.4's destroy-a-navigable destroys the active document, and a flow parked inside it is the reason that is a mechanism rather than a `free`.
- **Attention: per-opcode RETURN-to-scheduler from `JS_CallInternal`** (not a JSPI suspend — JSPI saves the C stack while frames live on the heap arena → teardown desync). Universal, boot included. TWO orthogonal decisions at the one per-opcode check: (1) the **VALUE yield** — suspend the moment a parked flow outranks (or on an emit/fork/suspension that changes ranks), never after N opcodes (an opcode-budget counter is a step cap, banned); a top-ranked flow runs on at ~zero switch cost. (2) the **COOPERATIVE-QUANTUM yield** — about THREAD-SHARING not value: after a bounded slice of CPU ACTUALLY CONSUMED the flow suspends (same COW-snapshot path) and `scheduler_run` RETURNS to `qjs_step` so the host pumps messages / interleaves engines / streams findings / snapshots, then resumes the SAME top flow on the byte-identical frontier. Required and universal (a lone engine otherwise freezes in a non-returning `qjs_step`). **THE BUDGET NEEDS AN ASYNCHRONOUS SOURCE, AND THIS LINE SAID "WALL-CLOCK SLICE" WHILE IT HAD NONE.** A yield-request bit polled at every opcode makes the suspend point universal; it does NOT make the budget expire, because the hook that reads the clock runs only where something RAISED a request, and everything that raised one was a shape of the PAGE'S OWN BYTECODE (back-edge, call, fork). Straight-line call-free code therefore did not merely mis-measure the slice, it never EVALUATED it — a budget noticed only when the debtor volunteers. So the quantum is a COMPONENT (`solver/quantum.h`), it raises the request from OUTSIDE the flow's instruction stream (natively `timer_create(CLOCK_THREAD_CPUTIME_ID, SIGEV_THREAD_ID)`; the handler raises the bit and decides NOTHING), and it is measured in CPU because §Testing says so and because a DESCHEDULED thread denies nobody the thread — the host that would use it is that same thread. **WHAT EACH HOST CAN MEASURE IS ASKED, NEVER ASSUMED** (`quantum_measure`/`_is_cpu`), because the two hosts differ and a file that compiles for both may not claim one's property for the other. A single-threaded wasm instance has NO CPU clock (emscripten answers every WASI clock from `emscripten_get_now()`, checked at the first slice so the day it stops being true the assert says so) and NO way to be interrupted mid-call: JS is run-to-completion, so a periodic export between steps is not mid-call, and the only agent that could raise the bit is a second thread in SHARED linear memory (`-pthread`, cross-origin isolation, plus the address of the main thread's own thread-local request byte). That is the transport requirement, named — until it is provisioned the extension's raise sources are the interpreter's own, so the back-edge and call raises are the WASM HOST'S ONLY EDGE and not transition scaffolding. **AND IT IS COSTED, NOT MERELY NAMED, BECAUSE MOST OF IT IS ALREADY SHIPPED:** `manifest.json` carries `cross_origin_embedder_policy: require-corp` today, so what stands between this host and a SharedArrayBuffer is `cross_origin_opener_policy: same-origin` — the manifest ships `same-origin-allow-popups`, which does NOT make an extension page `crossOriginIsolated` — plus `-pthread` on the wasm link and an exported address of the main thread's own request byte. The flip is not free and the cost is in the OTHER half of this project: §LIVE-VERIFY opens the attacker popup from an extension page, and `same-origin` severs an opener across origins. Whether that delivery survives it is a question to ANSWER on the real harness before the flip, never to assume in either direction — and the COOP value is one setting for every extension page, so there is no per-page way to have both. THE RAZOR: if a resume is not byte-identical — drops, starves, skips, reorders, or forgets ANY flow — it is a CAP, banned; a yield you cannot prove is lossless is a cap.
- **Every runtime job is a scheduler flow — no job-queue drain.** Every enqueued job (async resume, `.then`/`.catch`/`.finally` reaction, `queueMicrotask`, `setTimeout`/rAF) is a first-class flow in the one WFQ (COW-snapshot, preemptible, park-as-snapshot-able). There is NO `while(JS_ExecutePendingJob)` loop — the scheduler IS the job pump. An await's result is DELIVERED (consumed): the continuation resumes WITH the settled value, or RE-THROWS a rejection into it so `try/catch`/`.catch` runs, then continues the same flow — never dropped. Code-loading async ALWAYS executes (`await import(x)`, a chunk `fetch().then(eval)`, a `document.write`'d `<script>`). A flow's OWN await chain resumes strictly in program order; only WHICH flow runs next is value-reranked. An async recursion is a TREE of parkable flows, explored, never terminated or judged "redundant" (redundancy is undecidable). Two mechanisms keep it unbounded-until-disk with no bound: the WFQ orders by actual emitted output (a so-far-unproductive level is momentarily outranked, rises the instant it emits), and RAM pressure suspends the lowest-value tail to the IDB cold tier as a snapshot. STARVE means deprioritize-and-page (resumable, cross-session), NEVER terminate. An async OOM is never a missing bound — it is a non-parkable structure; making every continuation a first-class flow makes that OOM impossible by construction.

# State isolation — per-flow heap+DOM COW delta
- **Shared state = per-flow heap+DOM COW delta.** Each flow owns the heap slots and DOM nodes IT wrote, layered over the shared baseline. Context-switch SWAPS deltas (unapply outgoing, apply incoming), not a serial revert — so every flow is preemptible mid-write (no writer runs to completion) and any number interleave. The delta captures MUTATIONS (restore old value on unapply) and CREATIONS (delete added slot/node on unapply) across the JS heap AND the Lexbor DOM — ONE uniform primitive for isolation, snapshot, eviction, per-arm exploration, cross-session resume. A serial undo-log or host-side save/restore bracket is the wrong design (forces run-to-completion, cannot interleave).
- **The document is a time-travel entity, not a static DOM** — its tree/attributes/inserted nodes are PER-FLOW; `querySelector` in flow A and B can see different documents; rewinding restores the exact document a flow saw. The BROWSER owns the DOM API (reads AND write operations, `browser/document.c`, `browser/dom_element.c`, Lexbor tree); the SOLVER owns the time-travel STATE (`solver/dom_cow.c`: capture each write into the running flow's delta, swap on switch). A DOM write is the coupling point (the mutating edges `appendChild`/`setAttribute`/`innerHTML` are solver-coupled; a pure read like `querySelector` needs no capture).
- **A COMPONENT'S OWN C RECORD TIME-TRAVELS, and the capture belongs in its ACCESSOR.** A browser component keeping state behind a class opaque writes where no property hook and no engine hook can see, so `cow_capture_host_record(obj, rec, &LAYOUT)` runs where the flow REACHES the record: a record a flow has reached is one it may write, the delta dedups to one entry, and there is then NO write site left to miss — which is the only way this goes wrong. The layout names the record's owned JSValues and is the SAME list its finalizer frees, so a field added to one and not the other is caught by reading them together. Finalizers and gc_marks go through `JS_GetOpaque` instead, deliberately: a capture during collection would dup values on an object being torn down. The raw byte capture (`cow_capture_host_state`) is for a POD LATCH ONLY — a memcpy of a JSValue makes a reference it does not count, so the next restore frees a value the blob still names.
- **PLATFORM DATA A FLOW QUEUES IS A JS VALUE, never malloc'd C.** A port's message queue, a broadcast, a pending task's payload: each must PARK to the IDB cold tier and RESUME, and each must fork per-flow. A JS Array does both for free — its mutations are property writes the delta already captures, and the snapshot machinery already carries it. A malloc'd list captured as head/tail POINTERS reverts the POINTERS on a context switch and leaves the NODES reachable from nothing: a leak the runtime's own GC walk cannot see, so no gate reports it.
- **The delta captures ONLY shared baseline state — flow-private state is never captured** (the load-bearing invariant keeping a delta O(shared-state-touched) with no bound). An object CREATED by the running flow (`flow_local`) can never be observed by another flow, so `cow_capture`/`_prop`/`_create` SKIP it. The delta holds only genuine cross-flow state, never a loop body's per-iteration transients. This holds only if EVERY flow runs at flow-private mark, so an iteration over opaque input MUST fork each iteration as its own parkable flow (then each iteration's transients are flow_local). Boot is the one flow whose creations are legitimately BASELINE, so an opaque loop in boot forks per-iteration boot-flow siblings too.
- **A genuinely large delta (a loop mutating real SHARED state each iteration — common, never assume rare) is O(N) shared writes, handled by the ONE resume mechanism, NEVER by serializing delta bytes.** There is no delta-byte paging / buffer-pool spill (that is the live-graph serialization Cross-session forbids — a delta names its target by a live heap pointer with no cross-tier identity). The RAM bound comes from making each iteration its own parkable flow (a loop is a CHAIN of per-iteration flows, each O(1) incremental). Same-session paging and cross-session resume are the SAME operation: a hot flow resumes cheaply; an evicted one serializes its snapshot to disk and resumes it later. One honest exception: a uniformly-productive unbounded shared-accumulation loop (every iteration BOTH emits new AND mutates shared state) hits the physical RAM→DISK floor — the real limit, never a cap and never dedup'd. Diagnose a large delta by WHAT fills it: flow-private bloat (fix by running each iteration at flow_local mark) or genuine shared state (per-iteration flow chain, snapshot-parked, resumed).
- **Async/promise state is per-flow state that time-travels.** A pending promise, its resolve/reject capability, a suspended async frame, a queued `.then`/microtask continuation belong to the FLOW and ride its COW delta — flow A's promise settles with X while flow B's settles with Y. Modeling async as global (a shared job queue, a `JS_ExecutePendingJob` drain, a resolve fn held across a fetch OUTSIDE the delta) is a bug class: one flow's async effect leaks into another's timeline. The correct primitive is ONE — the per-flow COW delta extended over the promise/await/continuation graph.

# The C stack is a NON-limit — trampolining + hooking, overflow impossible by construction
- **All calls trampoline onto the HEAP stack** (`TrampFrame`/`do_tramp_call`/`do_return` + exception unwind): every `OP_call`/`OP_call_method`/tail-call pushes a heap frame and `goto restart`s instead of recursing into `JS_CallInternal`, so the C stack stays flat and direct/method/tail recursion is unbounded — the substrate for snapshot/preempt/evict/resume at depth. The trampoline restores the caller's closure `var_refs` on return (else nested-closure non-tail recursion crashes). `JS_ThrowStackOverflow` becomes impossible on the path; overflow on a not-yet-hooked path CRASHES LOUD (never caught into a soft `RangeError` that masks a bound). Hitting a genuine floor (IDB full) crashes as OOM.
- **C-function re-entry (a C builtin calling `JS_Call`→`JS_CallInternal`) reaches no-C-recursion by TWO mechanisms, split by whether the builtin holds a C continuation:**
  - **Call-site-resolved** (`.bind`/`.call`/`.apply`/`Reflect.apply`, the `f(...args)` spread, the builtins' internal `js_call_function`, and every CALL/READ/WRITE/MEMBERSHIP/DELETE through a Proxy) hold NO surviving continuation — the interpreter RESOLVES them at the operator site and trampolines the ultimate target directly, no C round-trip (`do_forward_call`/`do_forward_callfn` reshape the operands to the method-call shape and share one `do_forward_dispatch`; `js_tramp_proxy_*` re-dispatches the trap's normal handler and places its one result via the stack-shape descriptor `do_return` reads). Recursion is unbounded through a bound/`.call`/spread/proxy reference. **A trap's post-check IS why the continuation exists** — the target's invariants ([[Get]] frozen-property SameValue, [[Set]]/[[Delete]]/[[Has]] non-configurable rejection, [[Construct]] must-return-object) run on the trap's RESULT, so they ride the continuation and execute at `do_return` before the result is placed, sharing ONE implementation with the C path. Routing a trap without its invariant is not a partial implementation, it is a WRONG one — `new Proxy(frozen,{get(){return 999}}).f` must throw.
  - **Continuation-holding** (array iteration `forEach`/`map`/`reduce`/`sort`-comparator, `String.replace`/`JSON.stringify` callbacks, and getters / Promise reactions) keep loop/accumulator state between callback invocations, so they cannot be call-site-unwrapped. **They gain suspend/resume by HOOKING the callback drive into the flow machinery — NOT by re-hosting the builtin in JS (that would violate "don't code browser features in JavaScript").** The builtin STAYS a C engine feature; its callback dispatch routes through the trampolined `OP_call` and the `async_func_resume_run` seam (the single point that self-resumes a body through forced back-edge preempts — see the driver rule below), so the callback's body — sync loop, `await`, generator — suspends/resumes at any point exactly like a directly-called function, and the builtin's own iteration is preemptible at each callback boundary. Where the builtin ITSELF branches on a value (sort's `cf(...)<=0`, stringify's `typeof`/`Array.isArray`), an OPAQUE operand must NOT fork that branch — short-circuit via the `__isOpaque` leaf: sort's element order is meaningless → collapse to 0; stringify's opaque field VALUE is tainted external input → yield the OPAQUE itself (taint preserved, never a de-tainting placeholder). Either way the callback still runs (its emits/side-effects happen); only the meaningless fork is removed.
    **A continuation-holding builtin IS its step machine — the JS_Call-loop version must NOT survive alongside it, and THE CALL PATH ASKS NOTHING AT ALL.** The builtin DECLARES itself a step machine at its definition (`JS_CFUNC_STEP_DEF`), and it is driven from the ONE point every call shape already converges on: the C-function invocation itself (the `JS_CLASS_C_FUNCTION` branch / `js_call_c_function`'s `cproto` switch). **What is banned is a predicate that selects a FALLBACK, not dispatch as such.** The defect is a subsystem deciding, from a pattern, whether to run logic that was never designed to suspend — because that logic then survives, and every narrowing condition in the predicate is a case silently handed to it. Once the legacy body is DELETED there is nothing to fall back to, and the surviving question ("is this callee the Promise constructor / a step machine?") is ROUTING: it picks which one implementation runs, and a shape it fails to answer for CRASHES rather than quietly degrading. Judge a predicate by that test, not by its existence: if deleting the thing it selects against would leave it still needed, it is routing; if deleting that thing makes it meaningless, it was a fallback and should have gone with it. **A dispatch predicate at a CALL SITE is still BANNED — including a single uniform one —** `if (tramp_step_def_of(callee)) goto do_step_tramp;` repeated at `OP_call` / `OP_call_method` / `do_forward_dispatch` is the recognizer allowlist in its final costume: it is still per-spelling plumbing, it must be added once per call opcode, and every omission is a silent gap that only surfaces when some test happens to use that spelling. Renaming the predicate from "recognizer" to "capability check" changes nothing — the test is not what it ASKS, it is WHERE it is asked. One convergence point, no per-site `if`. A `tramp_can_call_<builtin>` recognizer — a list of pointer comparisons deciding which builtins get the suspending path — is BANNED, and so is the same list re-spelled as a magic-indexed table of "who is special". A recognizer can only exist because a legacy implementation still exists for it to choose against, so **the recognizer is a symptom: delete the legacy body and the choice disappears.** **THE GOAL IS TO REPLACE THE FEATURE, NOT TO BUILD A MECHANISM THAT SELECTS BETWEEN TWO OF THEM.** A capability declaration is not a licence for the old logic to keep living behind it — every selection mechanism (recognizer, cproto check, step table, gate predicate) is TRANSITION SCAFFOLDING whose only correct trajectory is to zero, and while it stands it is where the bugs come from. The bug list is not theoretical: a double-free (state freed by `fini` and again by the shared unwind), a stale `tramp_first` handing a builtin `this=undefined`, a `JSStepHdr` overwriting the first fields of a state that had not adopted it, an init-failure leak of ~20 objects per throwing test — NONE of these are bugs in the old walk or the new one. They are all bugs in the seam between them, and they cannot exist once one implementation is gone. So a conversion is not "add the machine, then choose it"; it is REPLACE the feature, in one diff, and the seam never exists to be got wrong. **EXPAND THE NEW LOGIC'S SCOPE UNTIL THE FALLBACK IS REDUNDANT — never un-expand.** A selector that narrows to the cases the new machine already handles (generator-backed sources, bytecode callbacks, string operands) exists because the machine is missing a capability, not because the other cases are unsupportable. Widen it and the failures NAME the missing capability: `iterator-closed-for-*` named IfAbruptCloseIterator; a drive-to-completion DFAIL named plain-iterator `.next` on the tramp. BUILD the named thing, widen again, and when nothing is left to select the legacy body deletes. Reverting the widening because it went red is STOPPING HALFWAY: it hands control back to the fallback and destroys the signal that told you what to build. Widen ONE consumer at a time — widening several at once produces a failure count with no name in it, which is how a previous attempt regressed 12 tests and got reverted with "the C path owns semantics this machinery does not reproduce" and never said which. If a named capability genuinely cannot be built now, record it BY NAME so the next attempt starts from building it, never as a silent narrowing. **DO IT IN THAT ORDER — legacy body FIRST, detector second.** Deleting the detector while its twin still lives breaks every path the detector was routing, and the reflex is then to re-add the detector under a new name (recognizer → "capability check" → a magic-indexed table → a `||` in a gate). Each conversion is three ordered steps: (1) DECLARE the capability at the builtin's definition (`JS_CFUNC_STEP_DEF` for continuation-holding; call-site-resolved for `.apply`/`.call`/spread); (2) DELETE the legacy `JS_Call`-loop body in the SAME diff; (3) the detector now has nothing to choose — remove it. A detector that survives step 3 means step 2 was not finished. The same applies one level up: a gate asking what the TARGET is (`tramp_can_call(t) || tramp_step_def_of(t)`) exists only because the reshape path cannot handle every target kind — fix that path, and the question disappears. The tell that you are building the banned shape: every narrowing condition in the recognizer (a C/bound callback, a non-primitive receiver, a patched `exec`, a subclass) is a SILENT FALLBACK to the old code, and each new call spelling (`.call`, `.apply`, spread, `super[x](...)`, `Reflect.apply`, the direct `@@replace`) becomes its own bug — one builtin answering differently depending on how the call was written. **An unconverted call path is a `@WHY`, never a tolerated slow path.** An earlier version of this rule claimed the opposite — that with the legacy body gone a stray call site would be "merely NOT-PREEMPTIBLE" because a generic driver in `js_call_c_function` still returned the right answer. That was FALSE and is deleted: the preempt hook fires unconditionally, so a callback holding a loop aborts from inside that driver anyway; it never degraded gracefully, it only moved where the crash surfaced. A second, non-suspending driver for the one step machine IS the dual system — it is deleted, and `js_call_c_function` DFAILs on a `JS_CFUNC_step` callee as a BACKSTOP. The enforcement is structural, not that backstop: every call shape whose callee has no bytecode body converges on ONE point (`do_generic_callee`), which is where the step question is asked, so a new call opcode cannot forget to route — there is no route to remember. Each opcode declares only its OPERAND SHAPE (`tramp_first`: `-1` plain `[f,args]`, `-2` method `[this,f,args]`), from which the cleanup follows; that is why those blocks were duplicates and why they collapsed. Every call shape (`.call`, `.apply`, `Reflect.apply`, spread, `super[x](...)`, tail position, and the PLAIN `f()`) must reach the step driver; "it still works, just without suspension" is not an allowed state, because correctness that survives a missing route is exactly what lets routes go missing. **A directory that ABORTS is not better than one reporting errors — it is the same failures with the count hidden.** Routing a previously-unrouted shape turns an abort into a real number, and that number going from "no result" to "67/190" is the FIRST HONEST MEASUREMENT, never a regression to revert. Reaching for the revert there is the same reflex as keeping a legacy fallback: making the report look better instead of making the system right.
    **A step state must be COMPLETE before the first operation that can throw, and a callback frame OWNS its arguments.** Two ownership invariants, each of which produced real bugs (a segfault and two leaks) that all looked different and were the same mistake. (1) `init` must place EVERY owned field on the state — and `string_buffer_init` the accumulator — before anything that can fail, because the failure path tears the state down through `fini`/`_end`, which frees exactly what the state holds and nothing else: a field handed over LATE leaks (the whole collected match array), and a buffer initialised late is freed with a NULL ctx (a segfault). A user `toString`/`valueOf` inside `init` is one of those throwing operations. (2) `narg_alloc == 0` means BORROW the argument slots in place, which is sound ONLY when they are the caller's OPERAND STACK, which the caller frees; a C-builtin callback borrows from the step state's own `cb_args` buffer instead, so a callee with a REST parameter built its rest array out of slots nobody owned and leaked the entire runtime graph on every continuation-holding builtin. A callback frame therefore allocates and owns its arguments. Fixture rule that follows: a step builtin's callback must be exercised with a REST PARAMETER — every other arg shape (`(v)`, `(a,b,c)`, `.call`, `.apply`, bound, thisArg) takes the identical borrowed path and cannot find it.
    **A data pointer must never be stored in `JSCFunctionType`.** That union holds FUNCTION pointers; putting a step-def pointer in it is a strict-aliasing violation that passes at `-O0` and under gdb and segfaults a whole directory at `-O1` with no single file reproducing. Reach the def through a named `STEPDEF_*` id instead. When a crash appears only under optimisation, `-fno-strict-aliasing` is the one-command discriminator — use it before theorising.
- **The generator/async DRIVER rule (the suspend/resume seam).** A forced preempt at a loop back-edge returns `FUNC_RET_PREEMPT` to whichever driver resumed the body; `async_func_resume_run` self-resumes through it (park+rebuild the frame, continue) so a preempt is never mistaken for an ECMAScript yield, and clears `throw_flag` before each re-resume (a preempt-resume is a continuation, never a re-throw). `flow_preempt_routable` fires the preempt only where a driver adopts this seam (the flow base; every generator/async body via `js_generator_next` / `js_call_generator_function` / `js_async_function_resume` / `js_async_generator_resume`). A C-reentry callback with no driver is routed by the hooking rule above. Overflow/recursion is reviewed at every depth, never a `RangeError`.
- **Boot IS the forking first flow — ONE boot system, never two.** The COW baseline is PRE-boot (post-env setup, before any page script); boot runs as the first flow with its heap+DOM creations+mutations in `g_boot_delta`. Boot's own `if(__FLAGS.admin)` FORKS a true-arm sibling boot flow in the same run (the primary keeps the canonical logged-out delta). `g_bundle_id` is computed synchronously by a pure Lexbor `<script>` scan, independent of boot execution, so the host reads the frontier key before init returns. A separate non-forking boot pass, or a gate-exploration driver separate from the one boot flow, is a regression. A guarded init (`if(!window.d){window.d=src}`) re-fires because the global is absent at the baseline — no special-casing. A boot-time `.then`/`await` continuation is a first-class async flow with an intact suspended snapshot. For a reply-GATED branch to fork WITH its example, the fetch-initiating scope RE-RUNS as a forking starter when the reply is provided — reply provision enqueues a forking boot re-run, not just a promise resolution.

# Time-travel resume — suspend and resume a snapshot
- **A parked flow is SUSPENDED as a snapshot and RESUMED from it — the same execution continued, byte-identical, at any loop depth or `await`.** The snapshot is the flow's per-flow COW delta (its heap + DOM writes) plus its suspended heap-frame chain (`JS_FlowResume`). The snapshot IS the continuation: restore it and continue from the exact suspension point. Suspend holds the flow at ~zero CPU; resume picks it up unchanged.
- **The frontier persists as suspended snapshots across sessions.** Hot snapshots live in RAM; under RAM pressure the cold low-value tail serializes to IDB and resumes on demand. A browser restart resumes every parked flow from its snapshot by global value-order — a high-value flow suspended last week resumes ahead of a low-value fresh one today.
- **A resumed flow re-derives example VALUES from CURRENT sources** (fresh `fromReply`), so it reflects the live API surface — the point of the tool. The snapshot carries the flow's own path and state; the concrete data values track today's server.
- **OOM / paging:** snapshot/restore is ONE primitive — suspend/resume, eviction, per-arm isolation. RAM holds the hot working set; the cold low-value tail serializes to IDB as suspended snapshots and resumes on demand. Disk is the platform FLOOR. BFS extracts the productive breadth first, so disk-pressure touches only the least-valuable suspended tail.

# @S — the PoC is CONSTRUCTED from the running code and PROVEN by firing
- **The breakout is DERIVED from the parsed sink context for EVERY sink class — no fixed payload table.** HTML breakout from the real Lexbor parse context (`construct_ctx_breakout`); JS breakout from a real lexical-context detector (`solve_js.c` → `construct_js_breakout`: the hole's string/template/comment state decides the minimal escape). The old fixed lists are DELETED. The only residual fixed vectors are single-context sinks (a URL sink IS `javascript:`, a `<script src>` IS an attacker host).
- **Three runtime observations construct it, solved JOINTLY** (path ∧ context-breakout ∧ filter-survival ∧ FIRING): (1) the SINK PARSE-CONTEXT grammar — parse the sink output with the real parser for the exact context the tainted byte lands in, honoring the parser's own decoding (entity/URL/JS-unescape) and mXSS mutation; (2) per-flow CHARACTER/SEGMENT PROVENANCE through the real filter — which bytes survive to which positions and in what form (dropped/escaped/case-folded/re-encoded/moved/split), observed per re-execution (never a static transform-expression, which cannot see a config-loaded allowlist), so breakout bytes are placed where they survive in the surviving form; (3) the path VALUE-DOMAIN so the same input passes every gate en route.
- **ONLY FIRING proves it** — require X9 to actually CALL, not merely appear: `onerror` on an empty `src` never errors, `innerHTML` does not execute `<script>` yet DOES fire `onerror`/`onload`, a `javascript:` URL needs navigation, `setTimeout(str)` evals. The firing vector is chosen per sink from its real semantics, auto-firing (parse-time) preferred over interaction-required, and stated honestly. Absence of a PoC is NEVER a "safe"/"verified:false" verdict (a custom input may still break a gated sink) — only search-not-yet-solved, a PARKED @S flow (never a terminal `@WHY`). Constrained sinks are solved by forced-exec search GUIDED BY THE GATE (`JS_SetGateHook` reports the concrete strings the code tests tainted input against; those tokens are prefixed/suffixed onto candidates). The search is DISTANCE-DIRECTED (a fitness of {filter-survived, sink-reached, context-escaped, handler-fires} the WFQ reads; a near-miss is mutated toward the gap using byte-provenance; a dead candidate starves).
- **Cross-flow shared state is solved by re-running the state-producer under the candidate before the sink:** boot re-run (source stored at boot, sunk in a handler), closure re-resolution (drive by source identity, not the stale captured closure), and an attacker-SESSION flow (source stored by handler A, sunk by handler B — one flow fires all handlers in seed order over one accumulating COW delta, then a candidate-session re-fires). A source stashed in a DOM attribute keeps taint via an `(element,name)→opaque` shadow map (Lexbor would ToString it away).
- **A firing breakout in the model is NOT yet a working exploit.** (a) EXECUTION ENVIRONMENT: the PoC must run under the page's ACTUAL policy — CSP (an inline `onerror` is dead under `script-src 'self'`: pick a policy-permitted vector or record "sink REAL, CSP blocks: needs X", never a bare XSS), Trusted Types (an `innerHTML` sink throws unless a policy stringifies), SRI/nonce/hash — read from fetched headers + `<meta>`, confirmed by the sink actually throwing/executing on real Chrome. (b) STORED/second-order is a TWO-STAGE PoC (the plant + the victim load that fires, with ordering and both deliveries), carried by the parked-flow machinery. (c) The attacker value GENERALISES beyond a string — DOM-CLOBBERING (`<form id=cfg>` flips a later `fetch(cfg.url)`) and PROTOTYPE-POLLUTION (a downstream gadget reads `__proto__[x]` into a sink), which the engine solves because it RUNS the gadget a template/SMT never sees. (d) Emit the STRONGEST working input per sink, each carrying its reproduction envelope (browser, needs-a-click, is-stored, required CSP/TT state). (f) A shared sanitizer is characterized once and reused, ALWAYS re-verified by re-execution (never trust-without-running).
- **LIVE VERIFY = ENGINE AGREEMENT:** the engine's exact PoC (its X9 fire-marker → `apiclientsink`) is delivered to the real page in a sandboxed attacker popup via the same URL/postMessage delivery the engine models. A hit = ground-truth real exploit; no hit = an engine-fidelity divergence to fix. Never a re-derived PoC.

# Attacker sources, values, and discovery
- **Each attacker source is defined with its intrinsic BROWSER constraints** (the engine is a real browser except forced-execution). `message.origin` is a valid origin the attacker controls by registering a domain, so a forgeable check (`endsWith`/`includes`/`startsWith`) is SOLVED (surface the required origin) while an unforgeable one (`===` exact) is unsatisfiable cross-origin and SUPPRESSES the finding — never a false PoC, never a dropped real one. `location.search` and `location.hash` are percent-encoded by the browser per the WHATWG per-component sets (verified on Chrome: both encode `< > " space`; the FRAGMENT additionally encodes backtick and NOT `'`, the special-QUERY encodes `'` and NOT backtick) — so a raw-hash HTML breakout is a FALSE PoC unless the app decodes it, but a JS-context breakout (`';X9();//`) is a REAL raw-hash XSS with a source-specific char-set. Deliver each candidate through the source's real browser transform (encode the search candidate, prefix the hash, structure the pm object) so re-execution decides breakout faithfully. Completing this per source (cookies, referrer, `name`, IndexedDB, form values) is the frontier — a source without its constraints yields PoCs that don't reproduce.
- **RUN, DON'T MATCH. COMPUTE OR SHAPE, NEVER INVENT.** Values are what QuickJS computes — no regex/name/identifier matching, scoring, heuristics, or bundler recognition (code is minified; names are meaningless). A value known only to satisfy a range/prefix/regex gate is INVENTED, not computed ⇒ a domain-annotated shape (`{int>5}`), never a concrete pick; only an equality-pinned or run-computed value is concrete. A missing value = a missing host-edge stub or opaque-infectious `OP_*` transfer, never a parallel resolver or re-implemented language feature. Forms/custom-elements are learned by EXECUTION (`.submit()`, `connectedCallback`), never by reading a DOM attribute.
- **The symbolic/trust boundary decides WHICH values carry a learnable example; a SHAPE for an APP-OWNED value is a DRIVING FAILURE.** Genuinely external / attacker input AND server-injected absent state (`window.__USER`/`__FLAGS`/`__NEXT_DATA__` — absent app-state is unknown injected input, so the read is SYMBOLIC and the auth gate FORKS to the logged-in arm, never a concrete `undefined` that buries the admin code) stay symbolic (domain-carrying, example-free), must never force a branch, and legitimately lack an @H example. But the app's OWN same-origin resources are TRUSTED ground truth to LOAD, never a shape: a fetch whose body is JAVASCRIPT is ALWAYS fetched + EXECUTED (a lazy chunk reveals real endpoints — the headline moat surface); a config/data fetch is ALWAYS loaded so its fields become concrete examples, while its use in a BRANCH still forks (a loaded `features.admin:false` must NOT concretize the gate, or the admin endpoint is lost — config is opaque-for-control-flow yet carries its loaded value as the example). `location.origin`/`host`/`protocol` (the principal) is concrete for URL building. A fully-opaque app-owned URL is a FATAL `@WHY` to fix, never a placeholder. Iterating an opaque collection FORKS unbounded (each iteration a parkable flow) — never "driven once" (a banned seen-set), yet it behaves like once because the identical-input tail emits nothing new and is outranked+paged.
- **Active discovery is REQUIRED** (lazy scripts + discovery docs + Google API `req2proto` error-probes) — passive learning is too thin. Each active fetch is made FROM the document that learned the endpoint, CORS-bounded both ways, one-per-endpoint (no method is universally safe — GET can mutate via `/logout`, `/delete?id=`), never a blind sweep. Endpoints learned from runtime fetch/XHR hooks instead of QuickJS mean the core forced-exec is underperforming — fix the driving. Static assets are NEVER endpoints (magic-byte + content-type, not URL suffix) but still drive the code path. A state-mutating request (POST/PUT/DELETE, or a side-effecting GET) is NEVER fired to learn — its example values come only from the local forced-exec path (that server-side-effect surface is the frontier where forced execution derives the request WITHOUT firing).
- **Bind before build:** source a missing Web/spec capability host-runtime (JSPI) → engine intrinsic → existing Lexbor module → faithful spec port → hand-roll last (never crypto/parsers from scratch). APIs must follow their IDLs; nothing may be opaque. APIs work regardless of multiple tabs/windows (cross-WASM chains), a real permission system, plugged-in speakers, or a real filesystem via virtualization. Treat the browser as REAL — permission-gated APIs, URL params, FSA, popups, iframes — or the project can't be made; virtual systems (their own component) let forced execution reach more code (an FSA file containing XSS).

# Security → SECURITY.md
Authorization keys on `sender.tab.url` (never `sender.id`/`msg.*`); credentialed-read PRINCIPAL = `MessageSender.origin`, never URL-derived; content script + website + QuickJS/WASM bundle are UNTRUSTED, the offscreen is the only trusted zone; one WASM instance per DOCUMENT (not tab); ALL network via `safe-fetch.js` or `pageContextFetch`; state in the offscreen + IndexedDB (`chrome.storage.local` banned). Tabs may hold cross-origin documents.
- **AN INSTANCE IS AN ORIGIN-KEYED AGENT CLUSTER — `(browsing-context group, origin)` — because that IS the spec's heap boundary, and ACROSS one THE COW DELTA SYNCHRONISES.** Two same-origin documents in one browsing-context group are ONE similar-origin window agent: HTML puts them in a single heap and then RELIES on it. `iframe.contentDocument.body.appendChild(subframe)` inserts a node THIS document created (§4.5 adopt, then the insertion steps), so `subframe.parentNode` is afterwards a node belonging to the OTHER document while the wrapper stays the same object; `frame.contentWindow.onunload = fn` hands the other document this agent's live closure to CALL, with a live Event going back. Those are not property reads that could suspend — they are one object graph — and passing them by NAME is an unbounded bidirectional export table with cross-boundary GC that answers `===` wrong. Splitting a same-origin pair is therefore not the stricter choice, it is the WRONG one, and refusing to costs nothing: the security invariant is ORIGIN, not document, so SECURITY.md's one-principal-per-instance still holds EXACTLY, and an origin-keyed cluster is also what makes `document.domain` a no-op — spec behavior, not a hedge. What crosses an instance boundary is then a CLOSED set — WindowProxy, Location, serialized messages — which is the whole reason the boundary is tractable and is what a real engine ships (Blink's `RemoteDOMWindow`/`RemoteFrame`). A DIFFERENT-ORIGIN document, or the same origin in another browsing-context group, IS a separate instance and may be remote; a flow touching both still has ONE world spanning them, and the delta that world is made of must apply, unapply and park across all of them — a per-instance delta that only agrees locally is two timelines wearing one name, the identical bug class as modelling async state globally. Cross-WASM COW sync is a REQUIRED mechanism, and no design may be chosen because it avoids building it.
- **A HOST THAT CANNOT PROVISION A SECOND INSTANCE HAS NOT TESTED THE TRANSPORT, AND EVERY CROSS-INSTANCE MECHANISM ABOVE IS THEN A DESIGN THAT HAS NEVER RUN.** The peer to provision is a CROSS-ORIGIN document — provisioning one for a same-origin child tests a transport that must never carry it. The world registry, the nearest-first ancestry and the lazy segment materialization can all be written, reviewed and self-tested with no peer in existence — and they were, for long enough that grep answered "a self-test" when asked who calls them. That is the shape a cross-instance design fails in: not a wrong answer, an unexecuted one. So a host is not finished when it can ANSWER a cross-document read; it is finished when it PROVISIONS the peer that answers. In a process that means a child PROCESS (the same binary, re-executed with the child's name, address, origin and policy, over a pipe); in the extension it means a second WASM instance the offscreen routes to. What crosses is TEXT and it carries its TYPE, because a live JSValue crosses neither a process, nor an instance, nor a session, nor a park — and because `otherW.length === 0` distinguishes a number from the string "0". A member whose value is an OBJECT does not cross at all until the remote-object handle exists: answering one by serializing it is how a cross-document read starts returning something that is not the thing, so the encoder CRASHES there instead.
- **A PEER ANSWERS BY RUNNING A PROGRAM, never by reading a property from C.** The read it is asked for is an IDL getter, and a C activation has no flow base under it — the same rule that makes every other read a flow makes this one one, and it is also what lets an answer that has to suspend exist at all.
- **A SYNCHRONOUS CROSS-INSTANCE READ IS A SUSPEND POINT — that is what the primitive is for.** The cross-origin allowlist is not all navigable-own state: `otherW.length` is the child-navigable count of the ACTIVE DOCUMENT and `otherW.closed` tracks the peer, so a cross-origin read must answer on the line that made it while the answer lives in another instance. (Same-origin, `iframe.contentWindow.document.body` is answered in-heap in that same turn, because the two documents are one agent — a suspend there would be OBSERVABLE and therefore a fidelity bug, not extra rigor.) At the real boundary the flow SUSPENDS exactly as it suspends at an `await` or a loop back-edge, the peer instance resolves the read in its own scheduled turn under the requesting flow's world, and the flow RESUMES with the value — byte-identical, at any depth. Sibling flows run meanwhile, which is the point. A same-origin `about:blank` child (`window.open()` with no argument, an `<iframe>` with no `src`) is created synchronously by the spec, and its CSP is not a special case: every Document has a §7.2.6 POLICY CONTAINER, and §7.4 CLONES the creator's when there is one — clone it ACROSS the boundary like any other cross-instance state.
- **§7.2.5.1's SAME-ORIGIN CHECK IS DECLARED BESIDE THE MEMBERS, never asked at the read.** A WindowProxy exposes a FIXED cross-origin list (window, self, location, close, closed, focus, blur, frames, length, top, opener, parent, postMessage) and everything else is same-origin only; a read outside it is a SecurityError, thrown at the read, because a page distinguishes that from `undefined`. The failure mode of checking per-read is SILENCE: this surface had no check at all and was safe only by the accident that the members built so far were nearly the whole list — the first one added without one would have leaked a cross-origin document with nothing to say so. An OPAQUE origin is same-origin with NOTHING, not even another opaque one, which is the same rule SECURITY.md states for the credentialed-read principal because it is the same concept. Both halves are the assertion: a filter that threw for everything passes a test that only checks the throw.
- **A cross-document message is an EMISSION, never shared mutation** — immutable once posted, so nothing has to un-send it when the sending flow parks or is outranked, and it needs no COW capture. It carries three things and each is load-bearing: the SERIALIZED bytes (never a live value — a live value crosses neither an instance, nor a session, nor a park); the SENDER'S ORIGIN stamped by the TRUSTED ZONE, never by the untrusted engine (the same rule as keying authorization on `sender.tab.url` — a forgeable `event.origin` defeats every origin check in every bundle, and would make the solver report exploits that are not real and miss ones that are); and the SENDING FLOW'S WORLD, its decision vector. Delivery SEEDS a flow in the receiver whose world is receiver-baseline ∧ that vector: two arms of a fork post two messages belonging to two contradictory worlds, and merging them fabricates a timeline neither sender was in. The offscreen ROUTES, because it is the only zone that knows which instance holds which document. No second scheduler — a delivery is a work item on the ONE frontier.

# Testing — FEATURE test262 (`node engine/test262.mjs [subdir]`) + the solver differential (`node engine/solvergate.mjs [doc]`)

So a gate runs from a FROZEN SNAPSHOT — `git worktree add --detach <dir> HEAD` plus a worktree of the submodule at `HEAD:engine/qjs` — and the commit it measured is REPORTED WITH THE RESULT. A result quoted without the revision it came from is not a measurement, and "I rebuilt and it went away" is the tell that the first build measured the edit rather than the tree. The corollary is the reason this is not a burden: an agent that cannot build is not being denied a gate, it is being kept out of the shared tree's way, and the one process that DOES build owes every agent the revision its number belongs to.
