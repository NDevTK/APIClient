## What this extension does (in service of the goal)

A Chrome Extension (MV3) that learns the *real* API surface of complex production web apps by running their unmodified JavaScript bundle on a forked QuickJS engine under forced multi-path execution. The deliverable for each visited page is per-endpoint records:

- `{method, path}` — recovered from real forced execution reaching the host-edge call, or from `__feDriveStatic` invoking an unreached function for real, or from a `<form action>`/`[*-url|-href|-src]` attribute in the parsed Lexbor doc
- `params` — query + body field names and locations; per-field provenance (`literal` value vs `opaque` attacker-input)
- `examples` — real values observed during forced execution OR captured network traffic. Never synthesized; never extracted from bytecode literal pattern matching
- `requiredHeaders` — fetch `init.headers` + XHR `setRequestHeader` captured per-endpoint as transport metadata, not body params. The header SET is whatever the bundle actually attached, with per-header literal/opaque provenance — NOT a hardcoded "Github needs X" list
- `provenance` — JS source spans (file:line:col) for every recovered fact, click-through to the bundle in `globalStore.scriptCache`

Security findings (XSS / open-redirect / code-exec) are a beneficial byproduct of the same forced execution + Z3 path-satisfiability filter — same instrumented run produces both API records and tainted-sink verdicts. The engine is one execution, two views.

## How the analyzer learns an endpoint (the seven sources, in order of preference)

A learned endpoint record is built up by combining whatever of these the analyzer can ground at analysis time. There is **no scoring** — every source either grounds a fact concretely (through real execution on the engine, real HTTP traffic, the real Lexbor DOM, or the real server's own response) or does not contribute to it. Bytecode literal-pattern extraction is explicitly NOT a source — it bypasses the engine and would lie about what the page actually does.

1. **Real forced execution reaches the host-edge call.** `@H` records emitted by `engine/qjs/hostedge.js` carry `{api, args, at}` — the URL, method, body shape, headers, and stack chain. This is the preferred source: it's the same code the real browser runs. Value resolution is automatic because patched QuickJS runs the bundle for real (closures, prototypes, framework state machines all evaluate with exact ECMA semantics). Per-field body/header provenance distinguishes `literal` (concrete value the bundle pushed) from `opaque` (attacker-controlled input flowing in).
2. **`__feDriveStatic` invokes unreached bytecode functions** — for every JS_CLASS_BYTECODE/GENERATOR/ASYNC/ASYNC_GENERATOR function whose body contains a host-edge get_var/get_field (the `@T` set), `js_fe_drive_static` calls it with as many SYNTH-opaque args as its declared `arg_count`, AND an opaque `this` (most real host-edge sites are class methods reading `this.fooUrl`/`this.src`; with `this=undefined` the first `this.X` throws and the method aborts before its fetch). **NO `__feMute`.** Muting frontier emission inside driven functions is a perf shortcut that BREAKS the goal: a feature's fetch is usually behind a branch (`if(cond) fetch(...)`), and muted the BFS never explores the other arm, so the branch-conditional endpoint + its body-field example values are silently dropped — the exact unused-feature surface code analysis exists to recover (audited on github: 92 fetch `@T` collapse to ~9 `@H` under mute). Learning a feature whose interaction has NOT happened is the whole point of forced execution, so the driven functions' branches MUST be explored. Termination is structural (distinct schedule prefixes + X-Force §3.2 fitness gating + SMT F-frontier pruning), never a mute/cap; a slow BFS is a fitness/pruning bug to fix, not a reason to stop exploring. The fetch/XHR/WebSocket inside the driven function fires and emits a real `@H` with whatever ECMA computed (literal/this-derived URL, body field names, computed values). This is the proper `@T → @H` promotion path — it RUNS the bundle's own code, never pattern-matches bytecode literals.
3. **Captured live-traffic from the active tab** — the user (or harness-driven popup) interacts with the page, the SW captures request/response, the analyzer threads them through the same learning pipeline as `@H` records. Real captured values beat any inference.
4. **HTML attribute extraction from the Lexbor-parsed document** — `__feHtmlEndpoints` walks `document.querySelectorAll` for `[action]`, `[formaction]`, and convention `[*-url|-href|-src]` patterns (multi-token only — excludes bare `<a href>` navigation). Real Lexbor spec DOM, no bytecode pattern matching. Bare HTML resource attributes (`<img src>`, `<link href>`, `<a href>`) are excluded because they're rendering, not API.
5. **Discovery-document probing** (`extension/lib/discovery.js` `buildDiscoveryUrls` + `convertOpenApiToDiscovery`) — sends real HTTP fetches to standard discovery paths (`/openapi.json`, `/.well-known/openapi.json`, `/swagger.json`, `/$discovery/rest`, `/swagger/v1/swagger.json`, version variants, `?labels=PANTHEON` for Google's visibility expansion, `X-Goog-Api-Key` / `X-Http-Method-Override: GET` for endpoints that reject plain GET). Any one that returns JSON gets parsed via the OpenAPI/Swagger 3.x/2.0 → Discovery converter and merged. Discovery URLs are PROBE strategies (try the spec/convention paths), not hardcoded "vendor X needs Y" recognition. The schema is whatever the real server returned.
6. **Error-message probing** (`extension/lib/req2proto.js` `probeApiEndpoint` + `sendProbe`) — sends a deliberate type-mismatched payload to the real endpoint, parses the server's error response (`Missing required field X at 'path'`, `Cannot bind query parameter`, `Invalid value for enum`), and rebuilds the schema from the server's own diagnostics. Recursive: nested message-type fields probed with indexed payloads (Go BatchExecute convention); repeated fields re-probed with index 1 appended; enums detected via "is not a valid enum value" responses. Pure server-grounded learning — the schema comes from the server's own validator, not from any external spec.
7. **Authenticated replay loop (`schema.verify`)** — for each learned endpoint with at least one example per required field, re-issue the request credentialed through the active tab, diff the response against the learned response shape, refine. A learned method is "real" only after at least one such replay confirms shape.

When a fact (URL, method, header value, body field value) can't be grounded by any of the seven sources for a given parameter, the record carries `valueSource:"opaque"` with NO synthesized value — the structural-learning discipline. A fully-opaque URL/method is a `resolverError`, never a fabricated endpoint.

**What is explicitly NOT a source** (and why):
- **Bytecode literal extraction** (static walk of `OP_push_atom_value`/`OP_push_const` between get_var and call to grab a URL prefix) — bypasses the engine. The literal might be in a never-taken branch, an init-object field value, a method string, a content-type. Static pattern matching at this layer fabricates facts. The proper path is `__feDriveStatic` (source 2): invoke the function for real; if it has a literal URL, real execution emits it.
- **String-concat fragment extraction** (capturing the leading literal of a template-literal URL like `` `${host}/api/${id}` `` as `urlPrefix`) — same reason. The literal IS in the bundle, but treating it as a URL prefix without proving it reaches the URL slot is a hack. Real execution under opaque args yields the resolved or opaque URL; static fragment grabbing presents partial-as-meaningful.
- **Identifier name matching, regex on code, scoring, depth caps, magic numbers** — the foundational rules. Code is minified; names are meaningless.

## The engine that makes this possible (foundation)

The analyzer's core is **forced multi-path execution on a forked QuickJS engine compiled to WebAssembly**, not a hand-coded interpreter. Re-implementing ECMA semantics on Babel (`extension/lib/ast.js`, now **deleted**) was a runtime-on-Babel dead end — an unbounded transfer-rule treadmill that could never match a real engine, which is why minified jQuery's `$.ajax`→transport never resolved. (V8 was evaluated and dropped: no first-class wasm target, and `jitless` negates its JIT edge, so a real engine with a tiny, portable patch surface — QuickJS-ng — was the correct choice.) The unmodified bundle is *executed for real* by patched QuickJS inside the extension's offscreen Web Worker; only the **host/environment boundary** is modelled, never the language. The boundary is two layers: `engine/qjs/qjs_dom.c` binds **Lexbor** (spec HTML5 parser + DOM + CSS selectors + WHATWG `URL`, compiled into the same wasm) so `document`/elements/`customElements`/`new URL()` are a real spec DOM, not stubs; `engine/qjs/hostedge.js` is the record-only Web-boundary shim (`XMLHttpRequest`/`fetch`/`eval`/`location`/storage/`MessageChannel`/…). API learning and XSS taint tracing share that one execution — no duplicate traversals, no parallel resolvers. `extension/lib/sourcemap.js` (sourcemap + TS-type extraction) is the only remaining genuinely-static helper. No shape matching on identifier names, no heuristic name lists; legacy code is deleted, not wrapped.

## Forced-execution engine — the deliverables (the record; no separate ledger)

All under `engine/qjs/` (a forked QuickJS-ng tree) + `engine/build.mjs`:
- `quickjs.c` — patched interpreter: the opaque sentinel + `__opaque`/`__isOpaque` globals; selective forcing in the 4 `OP_if_*`; opaque propagation in `OP_CMP`, `OP_get_field/2`, `OP_get_array_el/2`, `OP_call(_method)`, `js_json_parse`; SMT-directed BFS pruning helper `qjs_z3_check_flip_sat` (kills X-Force false-paths before drive.mjs enqueues them); `js_fe_static_sites` (location-only @T emission for unreached host-edge call sites); `js_fe_drive_static` (invokes each @T function with opaque args matching its declared `arg_count` so its host-edge call fires for real). Patch sites are surgical and source-grounded (read the real handler, single-exit guard mirroring existing idiom).
- `quickjs-forced.h` — the controller: `qjs_forced_decide_k` (schedule in, `B`/`F` trace out; takes the TAINT predicate term for SMT pre-check), `qjs_forced_config` (argv config — env is unreliable in modular wasm).
- `qjsmain.c` — host: install the Lexbor DOM binding, expose `__hostMicrotaskDrain` (drains Promise queue via `JS_ExecutePendingJob` so `fetch().then` callbacks fire inside the driver loop), eval each file as a global script; parses `--fe-exec/--fe-sched=/--fe-trace=/--fe-html=`; surfaces an uncaught bundle throw as a structured stdout `@E {file,message,stack}` (flushed immediately) — a host-model gap, never swallowed.
- `qjs_dom.c` — the QuickJS↔Lexbor binding (the spec DOM/CSS/URL layer): node wrappers with stable identity, `el_of()` node-type guards, real constructors for the full WHATWG HTML element-interface set so `class X extends HTMLElement` works, a `customElements` registry with **live-element upgrade on `createElement`** (a defined element is a real Lexbor node whose ctor ran), `<template>.content` as a live `DocumentFragment`, and WHATWG `URL`/`searchParams` bound to Lexbor's `url` module. No leaked process-lifetime `JSValue` (a never-freed proto dup triggered the `JS_FreeRuntime` GC assert — at emcc `-O1` `assert()` is live so it aborted the worker too).
- `hostedge.js` (single source of truth, drive.mjs tests it) + `driver.js` (event-loop epilogue with microtask `pump()` inside the fixpoint) — the record-only Web-boundary shim: fetch/XHR/`location`/storage/`MessageChannel`+`MessagePort` (wired into the pump), `bodyShape()` per-field provenance walker, structured @H records carrying `[url, method, bodyStr, bodyShape]`, interim JS base64 + UTF-8 `TextEncoder`/`TextDecoder` (pending the bind-before-build moves).
- `drive.mjs` — the X-Force schedule driver: BFS over `F` frontiers; **Linear+Quadratic+bootstrap-Exponential** fitness composition (X-Force §3.2 algorithm 1) with `coveredEdges`/`sinkSeen` gating; Quadratic-boost fires on any NEW @S sink OR NEW @H call site; `ep()` with `walkShape` for structured per-field body provenance; emits `runs / host_calls / endpoints` + per-endpoint `{name, in, valueSource, examples}` params + `structural` (`@T`) summary split into network vs sink candidates.
- `engine/build.mjs` — builds native `qjs.exe` (Node-iterate, via a gcc `@response-file` since ~150 Lexbor TUs blow past the Windows cmd length limit) + three wasm targets (`cli` NODERAWFS, `mod` ES6, `worker` SINGLE_FILE classic-factory) from the SAME patched source, and `stage` copies `qjs_worker.js` + generates `hostedge.gen.js` into `extension/lib/qjs/`. SINGLE_FILE embeds the wasm so the MV3 CSP (`default-src 'none'`) can't block a fetch; `wasm-unsafe-eval` is the only CSP addition. Max wasm memory is the wasm32 ceiling (4 GiB), not emscripten's 2 GB default.
- `extension/ast-thread.js` — the classic Web Worker (run from the offscreen doc `ast-worker.html` per the separate-worker performance architecture): enumerates schedules, one fresh `createQJS()` per schedule, adapts `@H`/`@S`/`@T` records → `{fetchCallSites, securitySinks, dangerousPatterns, resolverErrors, focusedView, structuralCandidates, protoEnums:[], protoFieldMaps:[], domEndpoints:[], sourceUrl, sourceMapUrl}` — the exact shape `background.js` already consumes. An `@E` becomes a `resolverError` carrying the **offending `/b.js` source snippet** (sliced from the in-hand combined code at throw time) so a host-model gap is self-diagnosing, not a bare `line:col`. `focusedView` (endpoint/sink spans at real bundle source positions, gate-evidence = example-value spread) is the execution-grounded replacement for the retired Babel viewer index.

## Authoritative rules (NEVER overridden, including by the goal at the top)

These exist because they describe what makes the analyzer's output *trustworthy*. The goal at the top of this file is to *learn the API surface*; the goal is destroyed if the learned records contain invented or wrong values, so:

### Assume vs. solve — the dividing line (authoritative)

*API learning assumes; security solves.* Every URL/method/header/body part is what real forced execution computed, or — when opaque on every path, *including code no forced path reaches* (unrequired modules; the JAW `@T` static half) — a structural **shape**. It is never solved (Z3 is not used to invent API values) and never invented: we want the *hidden/unreachable* API surface, not only the reachable one, so an SMT solve over API values would be exactly wrong. **Z3 is invoked for two things only: (1) deciding whether a tainted `@S` source→sink path is satisfiable with an exploit-shaped value, and (2) BFS pruning — deciding whether a flipped-schedule frontier is feasible under current Φ; UNSAT ⇒ suppress F-emission.** Neither solves for API values.

A value opaque on every forced path is a param **shape** (name + location + `valueSource:"opaque"`), never invented. A fully-opaque URL/method is a `resolverError`. Adding *value* capability = a missing host-edge stub or a missing opaque-infectious transfer (an `OP_*` the unknown should flow through) — never a parallel resolver, never a solver, never re-implementing a language feature.

**The five learning sources above** all produce real grounded facts — by running the bundle on the real engine, by invoking unreached functions on the real engine, by capturing live traffic, by walking the real Lexbor DOM, or by replaying a learned method credentialed. These are concrete grounding through the engine, never bytecode pattern matching or external-schema pulls.

### Structural learning vs. value placeholders

`fetch("/api/check?nwo=" + encodeURIComponent(repo))` where `repo` is true attacker/opaque input → emit `GET /api/check` with param `{name:"nwo", location:"query", valueSource:"opaque"}` and NO synthesized value. Structure (path, param names, locations, methods, body field names) is fair game whenever the engine reaches the host call; values come only from what the real execution computed (or one of the eight sources above).

### Computed values are resolved by RUNNING the code on the real engine

Every URL part, header, body field, and call-site argument is whatever patched QuickJS computes when the unmodified bundle executes under forced multi-path exploration. Closures, prototype chains, `Function.prototype.call/apply/bind`, `for..in`, `Object.assign`/spread, getters, framework state machines (jQuery `$.extend`/`ajaxTransport`/Deferred) all evaluate with exact ECMA semantics for free, because it is a real engine, not a model. WHATWG `URL` is *not* ECMA — it is bound to Lexbor's spec `url` module in `qjs_dom.c` (parse/relative-resolution/components/`searchParams`/setters/`canParse`), so it is spec-exact without a hand-rolled parser. If a value doesn't resolve, the bug is in the forced-execution driver (a branch not explored, a host stub returning the wrong shape, an opaque value not made infectious) — fix the controller/host-edge, never fall back to placeholders, never call a value "dynamic" as if that excuses a gap.

### Always read real website JavaScript — never guess

Before claiming a fix or a finding is correct, open the actual minified bundle in `globalStore.scriptCache` (or via `finding.view` / `finding.func` / `finding.callers` / `ast.probe.finding`) and confirm the AST decision against the real source. No assumed shapes, no "probably the framework does X", no test-only validation. If a real-site bundle is needed and not yet captured, capture it via the harness; don't reason without evidence. Production code if traced following ECMA will contain everything it has to otherwise the page would not function.

### Framework code is just JavaScript — RUN it, don't model it

jQuery `.fail(cb)`, axios interceptors, react-query, redux thunks, Catalyst controllers, Turbo Streams all bottom out at `fetch`/`XMLHttpRequest`/`WebSocket`/`postMessage`/`eval`/`innerHTML`. QuickJS executes the framework's own bundled implementation exactly; the host hook observes the native call it reaches. No framework recognition, no inter-procedural modelling to get wrong — the engine already did it. Real minified jQuery 3.7.1 (`testing/harness-dumps/jquery-3.7.1.min.js`) is the standing regression gate: jQuery-only (with `driver.js`) must analyse without spurious forks.

The green polarity gate set (re-verify native ≡ wasm before any claim):
- `_xss` — 4 `@S`, all REAL_EXPLOIT with Z3 witnesses (`<svg…>`, `alert(...)`, `javascript:…`, `<svg`)
- `_xss_neg` — TAINT_REACH / INFEASIBLE / REAL_EXPLOIT distinguished; SMT-directed BFS pruning verified live (with `--fe-sched=111` against the `r === "admin" ∧ r === "guest"` infeasible gate, the F-emission for the inner branch is suppressed — the driver never sees an X-Force false-path frontier)
- `_xss_redir` — open-redirect vs `javascript:`-scheme distinguished
- `_apidepth` — computed example values (real btoa of forced JSON, map+join, reduce, closure)
- `_url` — WHATWG URL parsing/relative-resolution/components/searchParams via Lexbor
- `_hidden` — `__feDriveStatic` promotes the unreached `@T` functions to `@H` by INVOKING them with opaque args: `fetch("/api/reached")`, `POST /api/hidden`, plus an opaque-URL entry where the URL is arg-derived (`endpoints=3`)
- `_gate` + jQuery 3.7.1 — `endpoints=2`, full per-field spread (POST /api/users with `role ∈ {guest, admin}`, `tier ∈ {FREE, PRO, ENT}`, `id=7`; GET /api/whoami with `fields=role,tier`)
- structured-body shape — `fetch("/api/items", {body:{name:"alpha", id:42, secret: location.hash}})` produces per-field params with `secret.valueSource="opaque"`, no invented value
- `_pump_test` (`fetch().then(...fetch())...`) — three @H records from a single forced run via `__hostMicrotaskDrain` inside the driver fixpoint

A regression in any polarity is a P1. The polarity gates are detector-correctness; they never substitute for real-site verification through the harness.

### Bind before build — don't reinvent what's vendored

A missing Web/spec capability is sourced in this strict order, never skipped:
1. **engine intrinsic** already in QuickJS-ng (e.g. `JS_AddIntrinsicAToB` for `btoa`/`atob` — note: wiring it into the *patched* context currently wedges it; that integration is an open bug, not licence to keep reinventing elsewhere)
2. **a Lexbor module already compiled into our wasm** — `url` (done), and the unused-but-present `encoding` (→`TextEncoder`/`TextDecoder`), `css`/`style` (→ real CSSOM / `getComputedStyle`)
3. **one audited single-file** vendored (e.g. a public-domain/BSD SHA for real `crypto.subtle.digest`) — never crypto/parsers written from scratch
4. **a faithful port of the spec algorithm** (e.g. WHATWG MIME Sniffing for CORB/asset classification)
5. only then hand-roll

The *only* things that are correctly ours: the analyzer-boundary fakes (record-only fetch/XHR/Headers shapes — a real network lib there would be wrong) and the research mechanism (forced-exec controller, opaque domain, event-loop pump, entry-point driver, SMT-directed pruning, structured body capture — paper-grounded, no off-the-shelf equivalent). Lexbor is Apache-2.0; QuickJS-ng MIT — both already vetted.

### Source maps belong to the OFFSCREEN document, not the service worker (authoritative)

A name like `e`→`owner` is recovered by running a source-map LIBRARY (`@jridgewell/trace-mapping`) on the finding's call-site position — never a bundle transform, never hand-rolled. The MV3 service worker is the WRONG place to fetch or hold a map: it is evicted after ~30 s idle, so any in-memory map/cache/dedup-set there is gone between the messages that wake it. The **offscreen document** (which owns the Web Worker and has its own IndexedDB) does it:
- It FETCHES the map using the **real `sourceMappingURL` the bundle ships** — which may be a relative filename (`chunk.js.map`) OR a full address (`https://…/chunk.js.map`); resolve relative→absolute against the chunk URL. The `<chunk>.map` sibling is only a fallback when the chunk ships NO pragma. Never ignore the provided URL.
- It SAVES both the fetched **map AND the chunk's full JavaScript** in IndexedDB, kept until API learning has COMPLETELY finished all stages for that page (then dropped) OR the user clicks the bin/Clear icon. This is transient per-page working state, not lifetime storage.
- The relabel resolves DURING LEARNING (no popup needed): the resolved name is written onto the endpoint param (`_sourceMapName`, the only persisted source-map-derived datum) so the popup just displays it. Dedup is self-correcting off that persisted name — never an SW-memory set.
- Lazy/deep-grind-DISCOVERED chunks (the login-gated `preheat` chunk the browser never loaded) get the same treatment: the offscreen side has the chunk JS (it drove it) and fetches its map by its own `sourceMappingURL`.

### Real interactive testing only — never fake the browser

Use the live Chrome harness (`testing/harness.js`) over CDP for every UI / popup / SW behaviour check. Never stub `chrome.*` APIs, never mock the service worker. JSDOM is allowed where useful (e.g. parsing/DOM scaffolding off the hot path) — it is not a substitute for verifying real SW/popup behaviour through the harness. If a harness command is missing for a check the reviewer needs, extend the harness — don't write a Node-side fake. Tests that bake in synthetic Chrome behaviour codify a fiction; the only ground truth is the real extension running in a real Chrome started via the harness. Extension must be realistically usable with decent performance and high quality.

**Verify by reading the rendered popup DOM, not by querying the SW.** The harness commands already exist — `start`, `page "<expr>"` (active web page), `popup "<expr>"` (popup context). Verification = read what the user SEES: `document.getElementById("send-ep-select").innerText`, drive a control like a user (`sel.value=…; sel.dispatchEvent(new Event("change",{bubbles:true}))`) then read `#send-form-fields`. **Never craft `chrome.runtime.sendMessage({type:"GET_STATE"|"DIAG_TAB"|"GET_ENDPOINT_SCHEMA"|"CLEAR_TAB"…})` yourself** — those read/mutate internal state and "fake" the verification; the popup messaging the SW as a side effect of its own rendering is fine, you doing it is not. **Never write ad-hoc Node/`.cjs` scripts** beside the harness; extend `testing/harness.js` instead.

### Clear the storage before verifying — stale data is the #1 phantom-bug cause

Storage is **GLOBAL** — `globalStore` (endpoints / discoveryDocs / scriptCache / securityFindings), merged into every tab's state; only the requests/log tab filters by tab (no per-tab storage, no per-tab clearing). It is **persisted (chrome.storage / IndexedDB) and RESTORED on every SW restart**, so findings ACCUMULATE across worker builds and `chrome.runtime.reload()` does NOT clear them — it restores the old store. Reading that accumulated mix (old-build results + scriptCache replay keyed by analyzer-fingerprint + full-script-set) is what burned hours on a phantom "Z3 bug" that was only stale data. **Before concluding ANY engine/Z3/code bug from extension output, CLEAR the storage and re-verify on fresh data.**

Retention is intentional ("System must not delete past findings … to review it again based on the full scripts combination") — do NOT make the system auto-delete and do NOT "fix" the fingerprint to force-invalidate. Clearing is the TESTER's job: **the harness never clears**, so click the real button via the popup command — `node testing/harness.js popup "document.getElementById('btn-clear').click()"` (→ `clearGlobalStore()`) — then trigger a fresh analysis, then read. Never craft a `CLEAR_TAB`/`GET_STATE` message yourself (see the testing-policy section). Note `chrome.runtime.reload()` picks up `background.js`/staged-worker edits and a per-page `tab.reload()` does NOT re-analyze (browser-cached scripts content.js doesn't re-ship), but neither clears storage — only the Clear button does. Never wipe `testing/profile/`, never kill Chrome; drive every verify run from the persistent profile + persistent harness Chrome.

### `window.open(...)` from `chrome.scripting.executeScript({world:"MAIN"})` has NO user gesture

Chrome's popup blocker drops it silently. The call returns `null`, no request is issued, the target tab never opens, downstream `win.postMessage(...)` is a no-op, and the probe wrongly reports NOT REPRODUCED even when the analyzer's verdict was REAL_EXPLOIT. The orchestrator pattern is `chrome.tabs.create({url: targetUrl, active: false})` (extension API is privileged) + `chrome.scripting.executeScript` on the target tab dispatching `window.postMessage(payload, "*")` from the target's own window. Same-window postMessage reaches the bundle's handler identically — handlers gate on `e.data` shape; origin pattern `"*"` matches. When a probe path returns NOT REPRODUCED despite a complete witness, look first for a `window.open` or other gesture-required API being called from a non-user-activated injection context; the fixtures-server access log (see `testing/fixtures_server.cjs`) is a fast way to confirm zero target fetches.

### Build a standalone reproducer in every host shape before blaming a vendored library

When something appears to behave differently across hosts (e.g. "Z3 model bindings differ between Chrome wasm and Node wasm with the same wasm bytes"), the very first concrete step is a minimal C/JS reproducer that exercises the vendored API the same way our code does, run in native + each wasm build + a real Chrome `new Worker(...)` (via the harness). If the reproducer is uniformly correct across hosts, the divergence is on our side — go investigate Φ accumulation / term registration / scheduler / host-edge stubs / orchestrator / cached state — NOT the library. Only after the standalone reproducer itself diverges across hosts is "blame the third party" honest. The Z3 @P investigation cost hours of churn precisely because configuration / build-flag / SMT-solver-swap hypotheses were tried before the standalone reproducer that would have ruled them all out.

### Read the real source — don't generate blind

Patch sites in `quickjs.c` are edited against the real handler (Read it, match its single-exit idiom). The engine is rebuilt (`node engine/build.mjs native|worker`) and the change is re-verified on real jQuery + the realistic-gate fixture before any claim. Native and every wasm target are built from one source — no test-vs-ship divergence.

### Driver-gap ownership

A host call whose URL/arg has no concrete value on any forced path, where the source shows it WOULD be concrete on a path the driver didn't explore, is a P1: extend the forced-execution decision-vector / entry-point driver / host-edge model to reach it. Don't paper over with placeholders, don't say "unresolvable", don't blame "dynamic".

## Ideas for what to do during continuous work (rotate; don't stay in one)

In priority order for the goal:

1. **Endpoint completeness on real vendor pages** — per visited Github/MS/Apple/Google page, the analyzer should yield ALL of: declared endpoints (HTML attrs), reached endpoints (forced execution `@H`), unreached-but-statically-extractable endpoints (`@T` with URL-literal), live-traffic endpoints (captured XHR/fetch). Coverage gap on any of the four is a P1.
2. **Per-field example values** — for every learned param, at least one of: real-execution computed value, captured live-traffic value, bytecode-literal enum, vendor-schema example. If a param has none, the record marks it `valueSource:"opaque"` with shape only — never invented.
3. **Required-header capture per endpoint** — fetch `init.headers` + XHR `setRequestHeader` flow through the learner as transport metadata. The captured set is whatever the bundle ACTUALLY attached, with per-header literal/opaque provenance. No hardcoded "vendor X needs header Y" — the bundle's own code is the truth.
4. **HTML attribute extraction** — `<form action>`, `[formaction]`, and convention `[*-url|-href|-src]` from the Lexbor-parsed SSR document, via `document.querySelectorAll`. Real spec DOM walk, no bytecode pattern matching.
5. **Authenticated replay loop (`schema.verify`)** — autonomous: for each learned endpoint with concrete examples, re-issue credentialed through the active page, diff response, refine. Without this loop the analyzer is fire-once.
6. **Static-function driving (`__feDriveStatic`)** — invoke each `@T` bytecode function (unreached webpack chunk) with as many SYNTH-opaque args as its declared `arg_count` AND an opaque `this` (class methods read `this.fooUrl`; this=undefined throws before fetch). **NO `__feMute`** — the driven functions' branches must be explored so branch-conditional fetches in not-yet-used features are reached. The function's host-edge calls then fire FOR REAL and emit @H with whatever URL real execution produces. Coverage multiplier for module-bundled apps where most fetches live inside lazily-loaded closures not on `window`.
7. **Protocol classification of captured bodies** — Protobuf / JSPB / JSON / gRPC-Web / GraphQL / SSE / NDJSON from magic-byte sniffing + content-type, never URL-suffix heuristics. The analyzer captures bodies; the classifier identifies the wire format.
8. **Service grouping quality** — group methods under the right host/path prefix. No cross-origin misattribution from concat tricks.
9. **API vs static asset classification** — magic-byte sniffing + content-type. No URL-suffix heuristics.
10. **Security issue detection** — AST-traced taint from host-edge sources to host-edge sinks. Same execution as API learning; one pass, two outputs.
12. **Exploit probe** — prove execution end-to-end: NOT REPRODUCED / TAINT REACH ONLY / REAL EXPLOIT. Active payloads (img onerror) set a per-marker flag the probe checks via `chrome.scripting`.
13. **Website JS review** — follow each learned endpoint and each security finding back to the original JS (sourcemap-resolved). Every per-hop code snippet is captured at analysis time.
14. **Verifying & reviewing output quality** — endpoints and findings are re-read against real JS; `schema.review` shows every leaf's example + provenance.
15. **UI review** — the popup and viewer render the learned endpoints (per-method, per-field, with example spread) and the same taint-path the reviewer would want; both inspected end-to-end with the harness before claims are made.
16. **Per-endpoint drill-down** — `endpoint`, `endpoint.func`, `endpoint.callers`, `endpoint.view`, `endpoint.examples`, `endpoint.headers` together produce enough context that no guesses are needed.
17. **Harness reviewer context** — every harness command gives ground-truth AST/execution data, not summaries: source snippets per hop, dim transitions, sanitizer report, preconditions, receiver type, example-value spread.
18. **Performance on real sites** — measure on a real 5 MB+ bundle. No change ships with regression > 10 % vs the previous real-site baseline.
19. **Facts not guesses** — every value the analyzer emits is traced structurally or grounded in one of the eight learning sources. No hardcoded strings, no depth caps, no magic numbers that paper over resolver gaps.
20. **Tooling context improvement** — when a review needed a manual step, the harness learns that step (hop snippets, receiverType, endpoint.view, etc.).

## Forced-Execution Analysis Policy

A value is whatever patched QuickJS *computes* when the unmodified bundle runs; a sink/source is what an *executed* call reaches at the host edge, never what it is named. No syntax/identifier matching (code is minified — names are meaningless), no regex on code, no scoring, no heuristics. Scope, prototypes, closures, framework internals are exact because the real engine runs them.

**No caps or depth limits**: 1 MB+ minified bundles must analyse without losing data — no size/step/depth/recursion cap, no schedule/run cap. Termination is structural: (a) schedule enumeration is over *distinct decision prefixes* and each forced run is a terminating program (opaque-gated loops fork → an arm exits); (b) the event-loop pump dedups callbacks by source identity, a monotone bounded set; (c) SMT-directed pruning kills infeasible flipped schedules at the source. A hung run is a real bug — a self-re-arming poll not source-deduped, an opaque value reaching a loop that should fork but doesn't, a host stub returning the wrong shape — find it; never add a limit. The host watchdog (a future QuickJS interrupt deadline, analogous to drive.mjs's `timeout:`) bounds wall-time of a wedged wasm instance — that is robustness, NOT an analysis cap.

**Depth without heat — the background scheduling model (authoritative; complements "No caps")**: completeness (learn the WHOLE unused-feature surface, incl. login-gated lazy chunks via the deep `@T → @H` orphan drive) is achieved WITHOUT pinning a core or overheating the device. Time is free — this is a background worker; a maxed core is not. The model has five load-bearing parts, none of which may be removed to "go faster":
- **Throttle (low CPU duty)**: each work burst is ONE schedule / ONE small deep batch (`DEEP_BATCH` orphans), followed by an `await sleep ≈ burst-duration` (~50 % duty, capped). The device stays cool; the loop NEVER pins a core. Parallelism is the wrong lever (more cores = more heat) — keep it serial + throttled.
- **Two-tier preemptible scheduling**: a live page review (the page the user is ON = the most relevant work) is HIGH priority and PREEMPTS the LOW-priority background deep grind. A review arriving mid-grind sets a yield flag; the grind stops at the next batch boundary (its cursor is already persisted) and resumes after. The single-threaded worker runs exactly ONE task at a time — never two wasm instances / two drives concurrently (`ast-thread.js` `_pump`/`_runReview`/`_yieldDeep`/`_reviewQ`).
- **Cross-session resumability (eventual consistency)**: the deep grind persists the combined bundle ONCE + a per-batch cursor to **IndexedDB** (the offscreen worker's origin — the SW has none). On MV3 eviction OR a full browser restart the grind resumes from the saved cursor with the saved JS — no code re-fetch, no lost progress. `background.js` `onStartup`/`onInstalled` proactively recreate the offscreen doc so the resume kicks WITHOUT needing a new page visit. Every persisted grind eventually reaches `rem=0` (then its IDB record is dropped); none is ever abandoned. Newest-interest first: the resume picks the most-recently-active grind.
- **Relevance-first, function-level prioritisation (resume by per-function-ID driven-SET, not a cursor index)** — usefulness = `relevance × quality × effort`, lexicographic, no magic weights:
  - **Relevance = MOST-RECENTLY-VISITED page first** (authoritative; a CROSS-grind signal). `_resumeIncompleteDeep` (`ast-thread.js`) selects the incomplete grind whose page has the most-recent **`vts`** (visit timestamp: set once on the page visit, PRESERVED across resume batches — NOT the per-batch `ts`, which would let a still-grinding old page outrank a freshly-opened one). The page you're currently ON preempts via its live review. Each page is analysed in its OWN isolated engine instance (only that page's static + runtime-loaded JS), so cross-page prioritisation means choosing which page-context to boot — relevance picks it.
  - **Across grinds: ROTATE, don't get stuck** (`_resumeIncompleteDeep` + `forcedAnalyze` `maxBatches`). A grind advances at most `DEEP_ROUND` batches per cycle then RETURNS, leaving its driven-set persisted; the scheduler then takes the next page in a recency-ordered "round" (`_deepRound`), rebuilt when empty (picking up newly-visited pages first). So every incomplete page makes progress every round — no page runs to completion while others wait — while most-recent still leads each round. A new page visit resets the round so it leads next. (Trade-off: each cycle re-boots that page's bundle, so `DEEP_ROUND` is sized to amortise the boot.)
  - **Within a grind: SECURITY → QUALITY → EFFORT** (`qjs_deep_relevance_sort` in `quickjs.c`). This is a SECURITY tool, so the most-useful unused function is one that reaches a SINK (a candidate XSS/code-exec finding): tier 1 = `qjs_fn_reaches_sink` (eval/Function/timers/importScripts/innerHTML/outerHTML/insertAdjacent* — the `QJS_SINK_NM` subset of the host set). Tier 2 = QUALITY (`qjs_executed`: a reached function ran in the page's real context → CONCRETE values; a cold orphan yields only an opaque shape). Tier 3 = EFFORT (smaller bytecode first). The execution-DEPENDENT `qjs_executed` is usable in the order ONLY because resume is by a driven-SET, not an index (next point).
  - **Resume = per-function-ID driven-SET, NOT a cursor index.** The engine keys each function by a STABLE id (FNV of file:line:col, independent of order/execution), emits `@DD <id>` per driven function; the worker persists the union (`prog.driven` in feDeepDB) and on resume writes it to the engine's `/driven`, loaded so those functions are skipped (`qjs_fn_id`/`qjs_dd_*`/`qjs_deep_step_c`). Because progress is tracked by WHAT-is-done (id) not WHERE (index), the usefulness order can change freely across runs (even by execution state) WITHOUT ever skipping or re-driving — the index-cursor's fatal flaw (a reshuffled list skips orphans = lost coverage) is gone. Verified: full grind drives all 1108 residue fns (rem=0, preheat found); a resume given run-1's `/driven` drives a disjoint set (overlap 0).
  - ONLY reorders — every orphan still driven, depth never capped; SCHEDULING, never a value heuristic.
- **Memory is bounded like wall-time**: the deep drive's per-orphan memory backstop (scaled to the booted-heap size, not a magic constant) + post-orphan reclaim keep a runaway async continuation from ballooning the heap — same robustness rationale as the op-watchdog, NOT an analysis cap (an orphan that completes under budget keeps every endpoint it found).

The invariant a future change must preserve: **high quality/depth AND low CPU/memory, via relevance-prioritised, preemptible, cross-session-resumable, eventually-consistent background work** — never trade depth for a cap, never pin the core, never run drives concurrently, never lose persisted JS/cursor on eviction or restart.

**The bin/Clear button = a hard STOP + total RESET (authoritative)**: the toolbar bin icon must DELETE ALL extension data AND stop all work outright — never a cooperative "please stop" flag the worker can ignore while running on already-deleted data. Concretely: the offscreen doc (which OWNS the Web Worker) `terminate()`s it (killing the running wasm instance immediately), `indexedDB.deleteDatabase("feDeepDB")` wipes the resumable-grind state (the terminate closed the worker's only connections, so the delete isn't blocked), then a FRESH worker is spawned; the SW wipes `globalStore` (all maps incl. `deepResumeMeta`) + the persisted gapiStore + `chrome.storage.session` request logs + `_scriptBuffers` + the review queue. A monotonic `_dataEpoch` (bumped on Clear) is captured by every in-flight analysis / async source-map re-merge / resume merge, which abandons its write if the epoch moved — so work already in flight when Clear ran can't repopulate the just-wiped store. `_dataEpoch` is eviction-agnostic (a clear, not an SW restart, bumps it), so it never suppresses a legitimate post-eviction resume. This RESET is distinct from the **AST version system** (analyzer-fingerprint cache-miss → automatic rescan on code change) which must NEVER clear past findings — findings accumulate; only the explicit bin/Clear wipes them.

**Driver/resolver completeness**: every URL/method/body value comes from what the execution computed (or from the seven other learning sources). A target that is opaque on every forced path is recorded once on `resolverErrors` (the adapter detects the `[object Object]` opaque marker — never a false page-origin URL, never `"unresolvable"`). Closing it is a P1: the missing transfer is either a host-edge stub returning the wrong/concrete shape, or an `OP_*` the opaque should be infectious through but isn't (extend the `quickjs.c` patch set, mirroring the existing single-exit guards) — never a parallel resolver.

- **Network sinks**: `XMLHttpRequest#open/send` and `fetch` are recorded by `hostedge.js` as `@H {api,args,at}` (args = `[url, method, bodyStr, bodyShape]`) when the *executed* bundle reaches them. `ast-thread.js` / `drive.mjs` pair open→send PER forced run, aggregate example values across runs; the URL/path/param-name structure is learned even when a value stays opaque (structural learning, never a fabricated value).
- **Inter-procedural / framework**: nothing to model — QuickJS runs the wrapper/factory/HOF/Deferred bundled code itself; the host hook sees the native call it ultimately reaches.
- **Taint sources**: the WHATWG attacker set is the host-edge data made opaque in `hostedge.js` — `location.hash/search`, `document.cookie`, `*Storage.getItem`, `window.name`, `XHR.responseText/response/status`, `fetch` `Response` bodies, `postMessage` event `data`/`origin`. Opaque is infectious (get/call/`JSON.parse`) so it reaches branches and sinks through the bundle's real code. DOM *structure* stays concrete so frameworks boot.
- **Security sinks**: code-exec (`eval`/`Function`/`setTimeout`|`setInterval` string arg), open-redirect (`location.href=`/`assign`/`replace`/`window.location=`/`location.search=`), DOM-HTML (`innerHTML`/`outerHTML`/`insertAdjacentHTML`/`document.write`), and script-bearing `setAttribute` (`href`/`src`/`on*`/`srcdoc`/`formaction`). `hostedge.js` emits an `@S` record **only when the value is tainted** — `__isOpaque(v)` (the non-`OP_CMP` concrete primitive) or the concat-derived `[object Object]` marker. A concrete write (jQuery feature-detection `innerHTML`) is not a finding and costs nothing.
- **Exploit confirmation by Z3 path-satisfiability (security only — never API-value resolution)**: an `@S` record by itself is **TAINT REACH ONLY** — a candidate that may be false because guards on the path can make any exploit-shaped value unreachable. Z3 is linked directly into QuickJS (C, no JS bridge); at the tainted sink, the source→sink path constraints accumulated over the attacker-tainted `qjs_opq` identity are asserted and the solver is asked for an exploit-shaped witness: **SAT ⇒ REAL_EXPLOIT** (the model is the concrete attacker witness), **SAT(Φ) ∧ UNSAT(exploit) ⇒ TAINT_REACH** (path feasible but Φ pins the value to a non-exploitable literal), **UNSAT(Φ) ⇒ INFEASIBLE** (X-Force forced incompatible gates — adapter suppresses; never reaches the reviewer). The SAME Z3 also runs at TAINT F-frontier emission as the BFS-pruning filter; both uses are about path feasibility, never API-value invention.
- **Z3 failures surface as `Z3_ERROR` + `@E` — never silent**: a C++ trampoline (`qjs_z3_shim.cpp`) wraps the inner solve. A Z3 C++ exception is caught, the `typeid` + `what()` is reported via the `@E` channel (`{channel:"z3", sink, error}`), and the verdict is the distinct `Z3_ERROR` string — drive.mjs / ast-thread MUST NOT collapse this into TAINT_REACH. Inline `Z3_get_error_code` checks after each Z3 API call catch non-throwing failures (handler set via `Z3_set_error_handler`).
- **Honest current stubs (the record; close them via bind-before-build, never claim otherwise)**: `crypto.subtle.*` returns empty buffers (a real digest needs a vendored audited single-file SHA — bundles that hash a body get a wrong value until then); `TextEncoder`/`TextDecoder` are interim JS UTF-8 (→ Lexbor `encoding`); `element.style`/`getComputedStyle` are a map stub (→ Lexbor `css`/`style`, already compiled); `structuredClone` is `JSON.parse(JSON.stringify())` (loses Map/Set/Date/cycles). Real-site reach: github boots with **zero `@E`** but its fetches sit behind Catalyst/Turbo `connectedCallback` + React effects that only fire once the **real server-rendered HTML** is parsed into the Lexbor document and its custom elements upgraded/connected — the open entry-point/page-DOM cycle (parse real page HTML with Lexbor — the spec parser — then drive `connectedCallback`; not a stub snapshot). HTML-attribute extraction (priority #4 above) is the parallel path that recovers endpoints declared on the SSR HTML without needing the execution chain to reach them.
