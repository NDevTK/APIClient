**THERE IS NO GRIND. BFS IS THE ONE SYSTEM.** Orphan-driving (force-invoking a never-called function to surface its unused endpoint) is just another BFS FLOW — the same forced-execution as a boot fork or a branch-arm — ordered by the ONE WFQ, never a separate "deep grind" phase / `--fe-deep-grind` callMain / `while(driven<maxN)` loop / driven-set / head-tail / `@DPAUSE` machinery. "BREADTH first THEN DEPTH" is NOT two systems or two phases: it is ONE continuous BFS whose ONE WFQ merely ORDERS higher-value-of-information flows (the shallow fetch) ahead of lower (the deep residue), all in ONE queue, ONE registry, ONE loop. A second scheduler beside it — engine-side (silent-counts/fixpoints, a separate deep-step driver) OR host-side (`ast-thread.js` deep-grind loop, no-progress recycle, per-culprit abandon) — is the cardinal violation: DELETE it, never add another.
ONE WFQ POLICY (an ANYTIME-BANDIT priority: accumulated emitted VALUE (new @H+@S) + a UCB OPTIMISM bonus ∝ 1/(visits+1) so a never-run flow is never starved by a proven one − CPU-AGING so a monopolizer that burns CPU without emitting SINKS below productive+unrun flows. Additive, NOT a literal value/cpu ratio — the aging term already yields value-per-CPU behavior without the ratios 0/0 degeneracy on unrun flows. ORDER-only, never drops a work item) at BOTH levels. **Level-2, within a document**: the engine orders its flows (boot fork, branch-arm, orphan-invoke, loop/recursion arm) by weight — each a COW snapshot on the heap call-stack, preemptible per-opcode + cross-session-resumable; the running flow yields the moment a parked flow outranks it (value-driven, never after N opcodes). **Level-1, across documents**: one wasm instance per page (SECURITY.md) ⇒ cross-instance scheduling is inherently host-level, so the host orders live per-page engines by each engine's best-flow weight and runs the top engine until its best flow no longer outranks the RUNNER-UP engine (a VALUE yield-floor, never a dispatch count — the WFQ, not a clock, decides), then re-ranks. Engine creation is ADMISSION-GATED to the RAM working-set floor (no instance built until a slot frees); a fetching engine is skipped so one doc's network wait never stalls another; an engine self-parks its residue to the IDB cold tier under pressure so a long-runner never holds a slot. The cold tail (parked recipes across all origins) is NOT a separate loop: when live work drains and RAM has headroom, the SAME admission step rehydrates the highest-`frontierWeight` recipes back INTO this pool, where they interleave with (and are ordered by) the one WFQ. The `frontierWeight` estimator DIFFERS in FORM from the live `flow_weight` while sharing the POLICY: a PARKED frontier has no live per-opcode CPU to age by, so its future productivity is ranked by emit-per-VISIT (a guarded rate — the 0/0 the additive form avoids is a LIVE-flow concern, not a cold one), NOT the additive cpu-aged form. Same value-of-information attention, estimator adapted to each tier granularity. ONE policy, ONE loop, hot+cold tiers of the same queue — NOT two schedulers. UNBOUNDED until the disk floor; the single ATTENTION runs across all sites; non-FIFO (value-ordered) because plain FIFO explores less.
- **ONE GLOBAL, CONTINUOUS, CROSS-SESSION FRONTIER.** There is exactly ONE attention process for the whole extension, and its frontier is the UNION of every flow from every origin ever visited, persisted in IndexedDB and never reset. Visiting a new page does NOT start a new scheduler, a new run, or a fresh attention — it APPENDS that page's flows (boot fork + orphans) to the one global frontier, which the ONE WFQ then re-ranks against every already-parked flow from every other site and every prior session. A browser restart resumes the same frontier by global value-order; a high-value flow parked on site A last week outranks a low-value fresh flow on site B today. Learning is monotonic and never per-page/per-session-scoped: `netdiff --unused` is a GLOBAL cumulative surface, not a per-tab tally. "Proper BFS across all seen websites" = this single frontier, ordered by value-of-information, paged against RAM with the cold tail on disk. Any per-page/per-session/per-tab scheduler, registry, run-counter, or attention reset is the cardinal violation — there is only the one.
- **Overflow impossible by construction:** ALL calls trampoline onto the heap stack so any flow is heap-switchable at ANY call depth. The OP_call/return trampoline (quickjs.c `TrampFrame`/`do_tramp_call`/`do_return` + exception unwind) puts every call on a HEAP frame: `OP_call`/`OP_call_method`/tail-call pushes a heap frame and `goto restart` instead of recursing into `JS_CallInternal`, so the C stack stays flat and direct/method/tail recursion is unbounded — the substrate for snapshot/preempt/evict/replay at depth. Deep preemption fires at ANY tramp depth: `FLOW_YIELD_CHECK` (gated by `flow_base_activation` so only the base activation unwinds the C stack, never a nested C-recursive one) stashes the whole `tf_top` heap chain into `JSAsyncFunctionState.tramp_top` and unwinds the base activation off the C stack; the generator-resume path reconstructs the top frame and `goto restart`s at its saved pc/sp; `free_tramp_chain` evicts a deep-suspended flow (mirrors `do_return`'s per-frame teardown). Two competing deep flows preempt each other mid-descent (`@RESULT._switches` counts the interleaves) and both return the byte-exact reference value with frames intact; under a host quantum both evict via `free_tramp_chain` then park as replay recipes — so fairness and cross-session resume hold at ANY depth, not just the flow base. C-function re-entry (a C builtin calling `JS_Call`→`JS_CallInternal`) reaches the SAME no-C-recursion outcome by TWO mechanisms split by whether the builtin holds a C continuation. **TAIL-FORWARDS** (`.bind`, `.call`, `.apply`, `Reflect.apply`, and the `f(...args)`/`OP_apply` call-spread) hold NO continuation — they only re-dispatch — so the interpreter RESOLVES them AT THE CALL SITE (`js_tramp_forward_setup` unwraps the `.bind` chain / `.call`+`.apply` reslice / spread `build_arg_list` to the ultimate NORMAL target, spliced args copied into the callee frame, innermost bind's `this` winning) and trampolines the target directly — no C round-trip, unbounded recursion THROUGH a bound/`.call`/`.apply`/spread reference. **CONTINUATION-HOLDING re-entrants** (array iteration `forEach`/`map`/`reduce`/`sort`-comparator, `Proxy` traps, `String.replace`/`JSON.stringify` callbacks) keep loop/accumulator state ON the C stack between callback invocations, so they CANNOT be call-site-unwrapped; they reach no-C-recursion by being SELF-HOSTED as bytecode (the loop becomes a heap bytecode frame; the callback dispatches via the already-trampolined `OP_call`) — a call-site unwrap of a `forEach` is a category error. `sort` self-hosts like the rest, with ONE added rule: its ordering branch must CONCRETIZE an OPAQUE compare result to a definite order instead of forking on it — element order is meaningless for @H/@S (the C sort already collapses it via `JS_ToBool`), so forking every compare is a WRONG O(n·log n) fork-explosion, not exploration; the self-hosted sort STILL runs the comparator (trampolined, unbounded, so its emits/side-effects happen) and only collapses the meaningless order bit (a `__cmpConcrete` intrinsic). All make `JS_ThrowStackOverflow` impossible on their path; `js_check_stack_overflow` in `js_call_c_function` is DEAD for a re-entrant once its mechanism lands and is deleted then. Recursion is reviewed at every depth, never a RangeError — a recursive tree-walk via `children.forEach(walk)` overflows nowhere because the iterator is self-hosted. The per-flow heap+DOM COW DELTA swaps on context-switch (`JS_CowUnapply`/`Apply`/`BufTake`/`Load`/`Free` + `dom_unapply`/`dom_apply`), so a shared-state WRITER (heap OR DOM) is fully preemptible — no `JS_CowDepth` guard, no writer running to completion. Boot IS the first flow: captured as `g_boot_delta` (COW active during the page's inline scripts, mutation + global-CREATION entries incl. `let`/`const`), which a candidate flow UNAPPLIES to a true pre-boot heap and REAPPLIES after. Heap captures are IDENTITY-based: a property mutation records `(obj,atom)` and RE-RESOLVES via `find_own_property` at every unapply/apply/revert — pointer-safe across property-array realloc/compaction/delete (a raw `&pr->u.value` would dangle when the object grows), while closure captures keep their stable `var_ref->pvalue` slot. Global `let`/`const` CREATION is captured (`add_property` extends to `global_var_obj`). The per-flow DOM delta covers attr + node-insert; node-removal needs no capture (no host removal op exists — `innerHTML` is a sink recorder, not a DOM mutation); boot's DOM writes land in `g_boot_delta` like any flow's (boot IS the first flow), so a source STASHED IN THE DOM by boot or handler A reaches a sink in handler B by the same COW swap that carries heap taint.) A loop reuses one frame; deep recursion grows by heap segments — both yield per-opcode.
- **Shared state = per-flow heap+DOM COW DELTA.** Each flow/arm owns its OWN delta — the heap slots and DOM nodes IT wrote — layered over the shared baseline, never another path's heap. The delta captures both MUTATIONS (restore the old value on unapply) and CREATIONS (delete the added slot/node on unapply) across the JS heap AND the Lexbor DOM — ONE uniform primitive serving isolation, snapshot, eviction, per-arm exploration, and cross-session rehydration alike — over the JS heap AND the Lexbor DOM. For a reply-GATED branch to fork WITH the example, the fetch-initiating scope must RE-RUN as a forking STARTER when the reply is provided (BOOT-AS-FLOW): an orphan-driven callback forks but only ever with OPAQUE args, and a promise-RESUME carries the concolic reply but runs in a non-forking context — so ONLY a from-scratch starter re-run, with the reply now synchronously concolic, lets a gated arm keep its example (else the concolic value reaches ungated fetches only). Reply provision therefore ENQUEUES a forking boot re-run, not just a promise resolution.
- **Attention:** per-opcode RETURN-to-scheduler from `JS_CallInternal` — NOT a JSPI suspend (JSPI saves the C stack while frames live on the heap arena → teardown desync/double-free). Universal, boot included. The yield CHECK is per-opcode; the yield DECISION is VALUE-driven — suspend the running flow the moment a parked flow outranks it (or on an emit/fork/suspension that changes ranks), NEVER after N opcodes (a per-N/opcode-budget counter is a step cap, banned). A flow that stays top-ranked runs on with ~zero switch cost; the WFQ, not a clock, decides when to switch. Driving the call/object graph synchronously outside the scheduler (a boot epilogue) is the same sin as a bound — drive it per-orphan, yielding.
- **OOM:** snapshot/restore is ONE primitive (pause/resume, eviction, per-arm isolation). RAM = the hot working set; the cold/low-value tail moves to **IndexedDB** (not localStorage/`chrome.storage.local`). **Disk is the platform FLOOR — finite, real, NOT a bound to remove. IDB doesn't make OOM "impossible," it bounds RAM and moves the residue to a larger, slower floor. BFS is what makes that sound: it extracts the productive breadth before the floor is approached, so disk-pressure only ever touches the least-valuable starved tail, never lost productivity.**
- **PHYSICAL FLOORS CRASH LOUD; they are NOT masked.** Disk and RAM are the genuine physical limits of the unbounded BFS; the C stack is made a NON-limit BY CONSTRUCTION — trampoline every call, self-host every continuation-holding re-entrant (forEach/map/reduce/String.replace done; JSON.stringify next; `sort` via the concretized order bit above), so overflow is IMPOSSIBLE, not caught. Hitting a genuine floor is a resource wall — IDB filling up crashes as OOM. UNTIL a re-entrant's self-hosting lands, its residual C-recursion overflow CRASHES the SAME way (offensive programming: LOUD, findings discarded, `_engineCrashOccurred`), NEVER caught-and-continued into a soft RangeError (masking a bound, building on an uncertain instance). The fix is ALWAYS to COMPLETE the primitive so overflow cannot happen, NEVER to catch the overflow or cap the depth to look "robust" — the exact soft-fail this project forbids. A crash on a not-yet-self-hosted path is a TODO surfaced loud, never a design.
- **Cross-session resume is REPLAY, not live-graph serialization.** A parked flow has TWO representations: HOT = the live heap frame in RAM (`JS_FlowResume` on the async heap-frame substrate — cheap suspend/resume for interleaving); COLD = a compact REPLAY RECIPE persisted to IDB = (bundle-ref/hash + the flow's DECISION VECTOR + accumulated value). It does NOT persist server data: rehydration re-derives example VALUES from CURRENT sources (fresh `fromReply`) so a resumed flow reflects the CURRENT API surface, never a stale snapshot — the whole point of the tool is the live surface, so byte-identical replay of last-session's data would be the WRONG goal. Eviction drops the live frame, keeps the recipe; rehydration RECONSTRUCTS the flow by re-running boot to the baseline then REPLAYING the decision vector — never by deserializing a live continuation + reachable object graph. **COW isolation is exactly what makes this sound: a flow's DECISION PATH is a deterministic function of (post-boot baseline, its OWN decision vector, its own execution) and NEVER of another flow's writes, so replaying its decisions over a re-run boot reconstructs the same PATH — shared state and interprocedural effects included, because re-running boot re-establishes ALL of them natively; only the concrete data values track the current server, which is desired.** Literal graph serialization is the WRONG primitive: it must rebuild object identity/aliasing across shared mutable state (the exact case that breaks it), and quickjs has no continuation serializer; replay sidesteps both. Replay cost is bounded by the eviction policy — only SHALLOW, low-value, few-decision flows are ever evicted (BFS keeps the deep productive ones hot), so a rehydrated flow is always cheap to replay. The decision vector IS the serialized continuation, compact and robust. **A recipe self-identifies by FUNCTION SOURCE (`JS_OrphanHash` = FNV-1a over the orphan's `b->source`), NOT by a positional collection index — collision-free + position-independent, so on resume it locates THE SAME FUNCTION by what it IS, in ANY context (present → drive with its decision vector; absent/different-source → skip; NEVER the wrong function). This is the ROOT that makes the frontier key just a RELEVANCE grouping (origin | bundle = external script srcs), not a soundness boundary: over-merging same-bundle-different-context documents is SAFE — each recipe finds its own function or skips — so NO per-context sub-keying is needed (that was a workaround for the fragile positional locator; the source-identity fix DELETES it, and a coarse key gives better cross-visit resume). Shared state is re-established per document by re-running its OWN boot before replay; the same script in a different context is a different flow only because its baseline differs, and re-running that document's boot establishes exactly that. A positional index (or a filename+line+col hash) is the WRONG identity: script order / definition site shifts across contexts, silently pointing the recipe at a different function — the exact bug source-identity removes.**
- **Prioritization, never fixpoint termination.** Nothing terminates; the unproductive is starved to ~0 CPU, resumable. An overflow-prone forced recursion is usually an ARTIFACT — forced/opaque branches drive a continue-arm into a call stack real input could never reach; the opcodes see it soundly (`OP_if` on an OPAQUE value driving `OP_call`), the sound replacement for `recur_collapse`.
- **Boot IS the first flow.** The COW baseline is PRE-boot (post-env setup, before any page script); boot runs as the first flow and its heap+DOM creations+mutations land in a delta like any other flow's. So opaque exploration, a candidate/PoC search under a concrete input, and a cross-session-rehydrated flow ALL fork from the SAME pristine pre-boot baseline by re-running boot under their own input assignment + decision vector — a guarded init (`if(!window.d){window.d=src}`) re-fires because `window.d` is genuinely absent at the baseline, no special-casing. There is NO privileged post-boot baseline and NO single serial undo-log; the common boot(opaque) prefix is merely a CACHED checkpoint delta the opaque flows share, and cross-session resume re-runs boot then replays the decision vector over this same baseline. Persisted to IDB, this is what makes the frontier UNBOUNDED and resumable across browser restarts.

# The moat (optimize design for this)
"moat" should be ignored when a better design is planned if asked for architecture work your goal is to think of whats best assuming a rewrite not how to get the best looking moat
Run the page's UNMODIFIED bundle on patched QuickJS (Lexbor DOM) under forced multi-path execution; one run, two views — API records AND XSS/security verdicts. Surface INTERESTING UNUSED endpoints (login/click/route/flag-gated, dead-but-shipped, lazy-chunk) WITH computed example KEYS and VALUES. A sniffer shows what FIRED; this shows what the bundle CAN do but didn't. **Ideal: learn the LOGGED-IN API surface WHILE LOGGED OUT** — SPAs ship the same bundle to logged-out visitors, so it contains the auth/admin/billing code that never fires without state. Metric: `harness netdiff --unused` (learned-not-live) — a DIAGNOSTIC that the solver DOMINATES the live page, NOT the optimization target: the page firing requests is a WEAKER baseline than the solver, which reaches code-flow states (the logged-out→logged-in surface) the page never fires. Ideally netdiff is never needed; optimize the solver's REAL-VALUED learned surface, never the diff. Target JS-heavy app/feature pages, not marketing pages. A detected XSS yields a WORKING PoC because the engine is a CONCOLIC EXECUTOR: external input is a symbolic value carrying its per-flow PATH CONSTRAINTS (no transform-expression, no chain-inversion), and at the sink the engine SEARCHES concrete inputs through the REAL transforms/filters as flows until one breaks out, verified by replay — never a template, never external Z3. Rotate the value areas (endpoint coverage, example values, required headers, replay loop, render-cycle, security/PoC, UI, perf); security-FP cleanup is the addictive trap that starves the rest.
- **RUN, DON'T MATCH. COMPUTE OR SHAPE, NEVER INVENT.** Values are what QuickJS computes — no regex/name/identifier matching, scoring, heuristics, or bundler recognition (code is minified; names are meaningless). Opaque on every path ⇒ a param SHAPE (`valueSource:"opaque"`); a fully-opaque APP-OWNED URL (no computed base at all — the app builds every endpoint URL, so this is a DRIVING FAILURE) ⇒ a FATAL @WHY to fix, never a placeholder or a silent shape. A value known ONLY to satisfy a RANGE/prefix/regex gate is INVENTED, not computed ⇒ it stays a DOMAIN-ANNOTATED SHAPE (`{int>5}`), never a concrete pick; ONLY an EQUALITY-pinned value (`x===v`⇒`v`, the code pinned it) or a RUN-computed value is concrete (range/regex solving is an @S-only, replay-verified tool — never an @H example). A missing value = a missing host-edge stub or opaque-infectious `OP_*` transfer — never a parallel resolver or re-implemented language feature. Forms/custom-elements learned by EXECUTION (`.submit()`, `connectedCallback`), never by reading a DOM attribute.
- **The opacity boundary is the TRUST boundary, NOT "all fetch responses" — and a SHAPE is a DRIVING FAILURE, not an acceptable output.** Genuinely EXTERNAL / attacker-controlled input (`location.hash`/`search`, cross-origin `postMessage`, a cross-origin response) stays OPAQUE for control-flow + taint — must NEVER force a branch (fork / feasible-refine + @S taint instead) — and has NO single real @H value, so a shape there is honest. But the app's OWN same-origin resources are TRUSTED ground truth to be LOADED, never left a shape: a fetch whose body is JAVASCRIPT is ALWAYS fetched + EXECUTED (a lazy chunk/module reveals real endpoints + branches + values — the headline moat surface); a CONFIG / same-origin DATA fetch is ALWAYS loaded so its fields become CONCRETE param examples, while its use in a BRANCH still FORKS / feasible-refines (loading kills the shape WITHOUT collapsing exploration — a loaded `features.admin:false` must NOT concretize the `if(features.admin)` gate, or the admin endpoint the moat wants is lost; config is opaque-for-control-flow yet carries its loaded value as the example, EXACTLY like `location.search`); a reply field flowing into a param drives the bounded `fromReply` GET. All via ONE bounded safe GET per resource, one-per-endpoint cached, origin-scoped creds under safeFetch's SOP/CORS; `location.origin`/`host`/`protocol` (the principal) is CONCRETE for URL building. A SHAPE for any APP-OWNED value is therefore a DRIVING FAILURE — the fix is to LOAD the resource or close the drive (real-instance drive, SSR seed, render-cycle), NEVER to accept `{shape}`; only genuinely-external attacker input legitimately lacks a real value.
- **Active discovery is REQUIRED** (discovery docs + `req2proto` error-probes) — passive learning is too thin. Each active fetch is made FROM the document that learned the endpoint, CORS-bounded both ways to the page's own reachable surface, one-per-endpoint (no method is universally safe — GET can mutate via `/logout`, `/delete?id=`), never a blind sweep. Endpoints learned from runtime fetch/XHR hooks INSTEAD of QuickJS mean the core forced-exec is underperforming — fix the driving, don't lean on the hooks. **Static assets are NEVER endpoints** (magic-byte + content-type, not URL suffix) but still drive the code path. A STATE-MUTATING request (POST/PUT/DELETE, or a side-effecting GET like `/logout`, `/delete?id=`) is NEVER fired to learn — no `fromReply`, no probe, because the side effect is REAL — so its example values come ONLY from the local forced-exec path; that server-side-effect surface is the genuinely HARD frontier where forced execution must derive the request WITHOUT a real response, never by firing it.
- **Bind before build:** source a missing Web/spec capability host-runtime (JSPI) → engine intrinsic → existing Lexbor module → faithful spec port → hand-roll last (never crypto/parsers from scratch).
