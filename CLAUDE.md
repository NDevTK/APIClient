**NO COUNTS, NO BOUNDS — the BREADTH-then-DEPTH WFQ scheduler allocates ATTENTION (which paused flow runs next); it does NOT terminate anything, and termination is not a thing it needs. A bound is NEVER better than the scheduler, only worse: it merely TRUNCATES distinct work the scheduler would otherwise reach productively.** Banned outright: depth/step/time/run/memory limit, watchdog, idle/drain/no-progress count, pruning. **The ONE non-bound limit is FAITHFUL ENGINE REPLICATION (do not "fix" it as a banned bound):** a LOOP reuses one frame — never grows the stack, never overflows — so it is the PURE attention case, never bounded (an infinite loop that might eventually emit is starved, resumable). RECURSION grows the stack; a depth past the REAL engine's call-stack limit is an UNUSABLE code flow — NO real execution (logged-in or out) reaches it because the page's own code throws `RangeError: Maximum call stack size exceeded` FIRST — so the engine throws that SAME RangeError at ~the V8 depth. That declines UNREACHABLE work (a FALSE `--unused` endpoint no user could trigger), the OPPOSITE of truncating productive work the scheduler would reach; a recursion's real learning is reached SHALLOW via breadth (the base-case/fetch arm) regardless of depth. The heap call-stack's job for recursion is to make that RangeError GRACEFUL (no `Aborted()` crash) and the ≤-limit state SNAPSHOT-able — not to run unbounded. The model: run BREADTH first (BFS over forced schedules/frontiers = coverage) THEN DEPTH (the residue grind), every flow preemptible (JSPI stack-switch, no depth cap), cross-session-resumable, ordered by value-of-information — the ACTUAL output a flow emits (@H API endpoints AND @S XSS findings, weighted EQUALLY — never a static "reaches a network edge" guess; XSS reaches DOM/eval sinks, not the network) + a UCB-explore bonus for under-sampled flows + a fairness floor — so deep+wide RECURSION + INTERPROCEDURAL traversal is SPREAD over time, productive-first, never bounded. An unproductive flow is STARVED (~0 CPU, still resumable), never dropped; a YIELD only hands control back for the scheduler to pick the next flow; slow ⇒ fix the PRIORITISATION (resume-by-relevance), never the work. The synchronous-loop trap: anything that drives the call/object graph OUTSIDE the scheduler (a boot epilogue that walks it all in one blocking pass) is the same sin as a bound — it can't be preempted or starved, so it spins/stalls; drive it from the scheduler (per-orphan, yielding, captured-instance) instead.
- **The scheduler switches STATES, two levels under ONE policy — this IS the system: continuous productive XSS + API learning.** Same-script: each forced branch-arm is a snapshot-able CODE-PATH (its heap + the forced-state of branches taken); cross-page: each page analysis is a fiber. A switch = save/restore that state, picked by ACTUAL output. Snapshot-fork (vs today's re-boot+replay workaround) AND overflow-proof recursion BOTH require the call stack ON THE HEAP — a trampolined interpreter, never native C-recursion; a stack overflow is the proof the path-state isn't managed. **A stack overflow being IMPOSSIBLE is a DESIGN property, never a bound — the exact OPPOSITE of one: a depth cap TRUNCATES real paths the scheduler would reach, while the segmented heap call-stack lets the recursion RUN unboundedly (grow by segments) AND stay preemptible/snapshot-able. "Cap the depth" is the wrong answer; "manage the state" is the right one.** BUILD ORDER (underway): (1) frame locals on a segmented heap JS-stack — DONE; (2) heap-resident frame records; (3) trampoline OP_call/OP_call_method/OP_return (eliminate the C-recursion); (4) retire recur_collapse + the overflow-throw + the deep-grind abandon/no-progress caps they masked; (5) snapshot-fork the segmented stack to explore both branch arms. State-switching is the INFRA; the DRIVING (real receivers, computed values, reaching gated code) is the PRODUCER the scheduler governs — a flawless switcher over no driving learns nothing, so the driving is never sacrificed to the scheduler.
- **You NEVER skip or drop work — not even a cycle, and no "proof" licenses it.** A "this re-computes nothing" seen-set / cycle-break / forced-state fixpoint is a CAP wearing a proof: it exists ONLY because the traversal can't yet PAUSE — a synchronous walk would spin `a.b===a`/`window.self` into a crash before any yield. A pause/resume gap is a BUG TO BUILD (make the traversal yield so the scheduler owns it), NEVER a licence to skip or to ignore policy. A cycle / spin / non-converging flow is PAUSED + STARVED by VALUE-of-information — it emits no new @H/@S ⇒ ~0 CPU, still resumable — and the scheduler reads "nothing new" from emitted OUTPUT, never from an identity seen-set OR a same-args/same-state fixpoint. Those are UNSOUND on their own terms, not just a pause workaround: SHARED STATE (a global / the heap / closure state ONE function mutates and ANOTHER reads) means a re-entry with byte-IDENTICAL args can still PROGRESS, so "same input" NEVER proves "same result" — only emitted output does. (`recur_collapse` collapsing a same-args recursion IS this bug; the heap-stack that lets the recursion RUN and be output-starved is its root fix.) The overflow-prone recursion is itself usually a FORCED-EXEC ARTIFACT — forced/opaque branches drive a continue-arm into a call stack REAL JS could never reach (an ORPHAN driven with opaque args; no real input produced it) — and ONLY the ENGINE can see it: from outside you can't tell a forced artifact from a real recursion, but the OPCODES can (an `OP_if` on an OPAQUE value driving the `OP_call`), soundly, with NO same-args guess. That is the sound replacement for `recur_collapse`. The heap call-stack makes that forced recursion PAUSABLE ON THE HEAP (a snapshot-able, RAM-evictable frame chain — NOT a JSPI-suspended C stack, which would still hold the frames and still overflow); the per-call YIELD hands the scheduler control at EVERY level (so it is caught after a few levels, not at stack-full — the trampolined `OP_call` MUST keep that yield or a forced recursion runs heap-unbounded to OOM); and the scheduler STARVES it by output-value. A REAL concrete deep recursion (rare) instead RUNS to completion on the heap (productive). Z3 + the constraints decide arm satisfiability so BREADTH reaches the productive base-case (the fetch) first while the forced deep arm is the starved one. The pause/resume + WFQ starvation IS the whole mechanism — nothing terminates, the unproductive is just starved to ~0 CPU (resumable); where that infra is missing, BUILD it.
