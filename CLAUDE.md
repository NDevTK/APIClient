## OBSERVABILITY (no silent failure modes, no silent error swallowing)

Every zero-result analysis path MUST emit a diagnostic record explaining the silence — `0 endpoints + 0 errors` is the WORST output because it's indistinguishable from "didn't run". Required:
- `@WHY {phase, scriptCount, bytecodeObjs, hostAtomMatches, eventLoopRanCount, feSeed, reason}` whenever a phase finishes without producing the expected records.
- `_deepStats.steps=0` MUST be paired with a reason field — `"never_queued"`, `"all_orphans_already_driven"`, `"runtime_eviction"`, etc. — never bare zero. **A grind that is RUNNING (`grindRunning=1`) with `steps=0` while the fiber keeps being resumed is a NON-TERMINATING ORPHAN** — one drive never returns and starves every later orphan; the engine MUST surface the stuck fn id (file:line:col), never bare zero. An unidentifiable stuck orphan is the worst gap because it reads as "slow", not "hung".
- **Classify a live-only failure with a MEASUREMENT before hypothesizing its cause.** A freeze/hang/perf-cliff that can't be reproduced natively gets observability that splits its classes factually — e.g. the liveness heartbeat (a timer-driven post, independent of the work loop, read via the harness `offscreen` cmd): a STALE heartbeat = blocked event loop (one long sync C call, no yield point); a FRESH heartbeat with no work-progress = the fiber isn't advancing — and a resume counter then tells "not resumed" (scheduler) from "resumed but non-terminating" (the work itself). A root cause asserted from the mechanism without such a distinguishing signal is a GUESS, and each wrong guess costs a build+verify cycle.
- Stderr diagnostics from C code are first-class: `[@T-dbg]`, `[@WHY]` etc. surface through `printErr` to the worker's `self.stderr` and SHOULD be exposed in the popup's diagnostic view. Silent stderr is a regression.
- **Every `catch (e) {}` is a bug** unless it surfaces a diagnostic (logged @WHY, resolverError, or @E). A bare catch hides root causes; replace with a narrow handler that either fixes the cause or reports it.

## STRUCTURAL LIMITS ARE WORKAROUNDS (not just caps)

The "no caps" rule already bans magic numbers / depth caps / step caps. Extending: **any mechanism that bounds *engine* behavior to mask an underlying bug is a workaround**, even when it has no numeric constant. Examples that LOOK structural but ARE workarounds when used to hide a leak/abort/hang:
- Running `JS_RunGC` in a loop before `JS_FreeRuntime` to mask a module-cycle leak — the leak is the bug; collect the cycle the spec way, don't paper over it.
- Per-iteration GC sweeps to "minimize accumulation" of a known leak.
- Re-spawning the wasm instance per N callMains to dodge an OOM.
- Catching `Aborted()` from emscripten and pretending it didn't happen.

The acceptable shape of a structural primitive: it's there because the *spec* needs it (microtask drain, GC cycle collector on actual cycle creation, etc.), not because it sidesteps a leak/abort. If you can describe the change as "this makes the bug less visible", it's a workaround. Find the root cause.

## What this extension does (in service of the goal)

A Chrome Extension (MV3) that learns the *real* API surface of complex production web apps by running their unmodified JavaScript bundle on a forked QuickJS engine under forced multi-path execution. The deliverable for each visited page is per-endpoint records:

- `{method, path}` — recovered from real forced execution reaching the host-edge call, or from `__feDriveStatic` invoking an unreached function for real, or from a `<form action>`/`[*-url|-href|-src]` attribute in the parsed Lexbor doc
- `params` — query + body field names and locations; per-field provenance (`literal` value vs `opaque` attacker-input)
- `examples` — real values observed during forced execution OR captured network traffic. Never synthesized; never extracted from bytecode literal pattern matching
- `requiredHeaders` — fetch `init.headers` + XHR `setRequestHeader` captured per-endpoint as transport metadata, not body params. The header SET is whatever the bundle actually attached, with per-header literal/opaque provenance — NOT a hardcoded "Github needs X" list
- `provenance` — JS source spans (file:line:col) for every recovered fact, click-through to the bundle in `globalStore.scriptCache`

Security findings (XSS / open-redirect / code-exec) use the same forced execution + Z3 path-satisfiability filter — same instrumented run produces both API records and tainted-sink verdicts. The engine is one execution, two views.

## How the analyzer learns an endpoint (the seven sources, in order of preference)

A learned endpoint record is built up by combining whatever of these the analyzer can ground at analysis time. There is **no scoring** — every source either grounds a fact concretely (through real execution on the engine, real HTTP traffic, the real Lexbor DOM, or the real server's own response) or does not contribute to it. Bytecode literal-pattern extraction is explicitly NOT a source — it bypasses the engine and would lie about what the page actually does.

1. **Real forced execution reaches the host-edge call.** `@H` records emitted by `engine/qjs/hostedge.js` carry `{api, args, at}` — the URL, method, body shape, headers, and stack chain. This is the preferred source: it's the same code the real browser runs. Value resolution is automatic because patched QuickJS runs the bundle for real (closures, prototypes, framework state machines all evaluate with exact ECMA semantics). Per-field body/header provenance distinguishes `literal` (concrete value the bundle pushed) from `opaque` (attacker-controlled input flowing in).
2. **`__feDriveStatic` invokes unreached bytecode functions** — for every JS_CLASS_BYTECODE/GENERATOR/ASYNC/ASYNC_GENERATOR function whose body contains a host-edge get_var/get_field (the `@T` set), `js_fe_drive_static` calls it with as many SYNTH-opaque args as its declared `arg_count`, AND an opaque `this` (most real host-edge sites are class methods reading `this.fooUrl`/`this.src`; with `this=undefined` the first `this.X` throws and the method aborts before its fetch). **NO `__feMute`.** Muting frontier emission inside driven functions is a perf shortcut that BREAKS the goal: a feature's fetch is usually behind a branch (`if(cond) fetch(...)`), and muted the BFS never explores the other arm, so the branch-conditional endpoint + its body-field example values are silently dropped — the exact unused-feature surface code analysis exists to recover (audited on github: 92 fetch `@T` collapse to ~9 `@H` under mute). Learning a feature whose interaction has NOT happened is the whole point of forced execution, so the driven functions' branches MUST be explored. Termination is structural (distinct schedule prefixes + X-Force §3.2 fitness gating + SMT F-frontier pruning), never a mute/cap; a slow BFS is a fitness/pruning bug to fix, not a reason to stop exploring. The fetch/XHR/WebSocket inside the driven function fires and emits a real `@H` with whatever ECMA computed (literal/this-derived URL, body field names, computed values). This is the proper `@T → @H` promotion path — it RUNS the bundle's own code, never pattern-matches bytecode literals.
3. **Captured live-traffic from the active tab** — the user (or harness-driven popup) interacts with the page, the SW captures request/response, the analyzer threads them through the same learning pipeline as `@H` records. Real captured values beat any inference.
4. **REMOVED — was static HTML attribute extraction (parallel analysis, forbidden by the top goal).** `__feHtmlEndpoints` used to walk `document.querySelectorAll` for `[action]`/`[formaction]`/`[*-url|-href|-src]`/custom-element `src` and emit `@H` DIRECTLY from the attribute — bypassing the engine, exactly the shortcut "NO parallel analysis" exists to prevent. These endpoints are learned the right way, by EXECUTION: a `<form action>` when the bundle's submit fires (the formaction-submit driver in `hostedge.js` calls `owning.submit(...)`), an `<include-fragment src>` when `customElements.define`'s upgrade loop (`qjs_dom.c`) drives its `connectedCallback` against the real Lexbor element and the fetch fires with the concrete `src` (the CE-construction fix — `I()` not clobbering the `dom_ctor`-backed `HTMLElement` — is what makes that element real). Reading the attribute statically is never a source.
5. **Discovery-document probing** (`extension/lib/discovery.js` `buildDiscoveryUrls` + `convertOpenApiToDiscovery`) — sends real HTTP fetches to standard discovery paths (`/openapi.json`, `/.well-known/openapi.json`, `/swagger.json`, `/$discovery/rest`, `/swagger/v1/swagger.json`, version variants, `?labels=PANTHEON` for Google's visibility expansion, `X-Goog-Api-Key` / `X-Http-Method-Override: GET` for endpoints that reject plain GET). Any one that returns JSON gets parsed via the OpenAPI/Swagger 3.x/2.0 → Discovery converter and merged. Discovery URLs are PROBE strategies (try the spec/convention paths), not hardcoded "vendor X needs Y" recognition. The schema is whatever the real server returned.
6. **Error-message probing** (`extension/lib/req2proto.js` `probeApiEndpoint` + `sendProbe`) — sends a deliberate type-mismatched payload to the real endpoint, parses the server's error response (`Missing required field X at 'path'`, `Cannot bind query parameter`, `Invalid value for enum`), and rebuilds the schema from the server's own diagnostics. Recursive: nested message-type fields probed with indexed payloads (Go BatchExecute convention); repeated fields re-probed with index 1 appended; enums detected via "is not a valid enum value" responses. Pure server-grounded learning — the schema comes from the server's own validator, not from any external spec.
7. **Authenticated replay loop (`schema.verify`)** — for each learned endpoint with at least one example per required field, re-issue the request credentialed through the active tab, diff the response against the learned response shape, refine. A learned method is "real" only after at least one such replay confirms shape.

When a fact (URL, method, header value, body field value) can't be grounded by any of the seven sources for a given parameter, the record carries `valueSource:"opaque"` with NO synthesized value — the structural-learning discipline. A fully-opaque URL/method is a `resolverError`, never a fabricated endpoint.

**What is explicitly NOT a source** (and why):
- **Bytecode literal extraction** (static walk of `OP_push_atom_value`/`OP_push_const` between get_var and call to grab a URL prefix) — bypasses the engine. The literal might be in a never-taken branch, an init-object field value, a method string, a content-type. Static pattern matching at this layer fabricates facts. The proper path is `__feDriveStatic` (source 2): invoke the function for real; if it has a literal URL, real execution emits it.
- **String-concat fragment extraction** (capturing the leading literal of a template-literal URL like `` `${host}/api/${id}` `` as `urlPrefix`) — same reason. The literal IS in the bundle, but treating it as a URL prefix without proving it reaches the URL slot is a hack. Real execution under opaque args yields the resolved or opaque URL; static fragment grabbing presents partial-as-meaningful.
- **Identifier name matching, regex on code, scoring, depth caps, magic numbers** — the foundational rules. Code is minified; names are meaningless.

## The engine that makes this possible (foundation)

The analyzer's core is **forced multi-path execution on a forked QuickJS engine compiled to WebAssembly**, not a hand-coded interpreter. Re-implementing ECMA semantics on Babel (`extension/lib/ast.js`, now **deleted**) was a runtime-on-Babel dead end — an unbounded transfer-rule treadmill that could never match a real engine, which is why minified jQuery's `$.ajax`→transport never resolved. (V8 was evaluated and dropped: no first-class wasm target, and `jitless` negates its JIT edge, so a real engine with a tiny, portable patch surface — QuickJS-ng — was the correct choice.) The unmodified bundle is *executed for real* by patched QuickJS inside the extension's offscreen Web Worker; only the **host/environment boundary** is modelled, never the language. The boundary is two layers: `engine/qjs/qjs_dom.c` binds **Lexbor** (spec HTML5 parser + DOM + CSS selectors + WHATWG `URL`, compiled into the same wasm) so `document`/elements/`customElements`/`new URL()` are a real spec DOM, not stubs; `engine/qjs/hostedge.js` is the record-only Web-boundary shim (`XMLHttpRequest`/`fetch`/`eval`/`location`/storage/`MessageChannel`/…). API learning and XSS taint tracing share that one execution — no duplicate traversals, no parallel resolvers. `extension/lib/sourcemap.js` (sourcemap + TS-type extraction) is the only remaining genuinely-static helper. No shape matching on identifier names, no heuristic name lists; legacy code is deleted, not wrapped.

## Forced-execution engine — the deliverables (the record; no separate ledger)

All under `engine/qjs/` (a forked QuickJS-ng tree) + `engine/build.mjs`:
- `quickjs.c` — patched interpreter: the opaque sentinel + `__opaque`/`__isOpaque` globals; selective forcing in the 4 `OP_if_*`; opaque propagation in `OP_CMP`, `OP_get_field/2`, `OP_get_array_el/2`, `OP_call(_method)`, `js_json_parse`; SMT-directed BFS pruning helper `qjs_z3_check_flip_sat` (kills X-Force false-paths before drive.mjs enqueues them); `js_fe_static_sites` (location-only @T emission for unreached host-edge call sites); `js_fe_drive_static` (invokes each @T function with opaque args matching its declared `arg_count` so its host-edge call fires for real). ## Authoritative rules (NEVER overridden, including by the goal at the top)

These exist because they describe what makes the analyzer's output *trustworthy*. The goal at the top of this file is to *learn the API surface*; the goal is destroyed if the learned records contain invented or wrong values, so:

### Assume vs. solve — the dividing line (authoritative)

*API learning assumes; security solves.* Every URL/method/header/body part is what real forced execution computed, or — when opaque on every path, *including code no forced path reaches* (unrequired modules; the JAW `@T` static half) — a structural **shape**. It is never solved (Z3 is not used to invent API values) and never invented: we want the *hidden/unreachable* API surface, not only the reachable one, so an SMT solve over API values would be exactly wrong. **Z3 is invoked for two things only: (1) deciding whether a tainted `@S` source→sink path is satisfiable with an exploit-shaped value, and (2) BFS pruning — deciding whether a flipped-schedule frontier is feasible under current Φ; UNSAT ⇒ suppress F-emission.** Neither solves for API values.

A value opaque on every forced path is a param **shape** (name + location + `valueSource:"opaque"`), never invented. A fully-opaque URL/method is a `resolverError`. Adding *value* capability = a missing host-edge stub or a missing opaque-infectious transfer (an `OP_*` the unknown should flow through) — never a parallel resolver, never a solver, never re-implementing a language feature.

**The five learning sources above** all produce real grounded facts — by running the bundle on the real engine, by invoking unreached functions on the real engine, by capturing live traffic, by walking the real Lexbor DOM, or by replaying a learned method credentialed. These are concrete grounding through the engine, never bytecode pattern matching or external-schema pulls.

### Structural learning vs. value placeholders

`fetch("/api/check?nwo=" + encodeURIComponent(repo))` where `repo` is true attacker/opaque input → emit `GET /api/check` with param `{name:"nwo", location:"query", valueSource:"opaque"}` and NO synthesized value. Structure (path, param names, locations, methods, body field names) is fair game whenever the engine reaches the host call; values come only from what the real execution computed (or one of the eight sources above).

### Computed values are resolved by RUNNING the code on the real engine

Every URL part, header, body field, and call-site argument is whatever patched QuickJS computes when the unmodified bundle executes under forced multi-path exploration. Closures, prototype chains, `Function.prototype.call/apply/bind`, `for..in`, `Object.assign`/spread, getters, framework state machines (jQuery `$.extend`/`ajaxTransport`/Deferred) all evaluate with exact ECMA semantics for free, because it is a real engine, not a model. WHATWG `URL` is *not* ECMA — it is bound to Lexbor's spec `url` module in `qjs_dom.c` (parse/relative-resolution/components/`searchParams`/setters/`canParse`), so it is spec-exact without a hand-rolled parser. If a value doesn't resolve, the bug is in the forced-execution driver (a branch not explored, a host stub returning the wrong shape, an opaque value not made infectious) — fix the controller/host-edge, never fall back to placeholders, never call a value "dynamic" as if that excuses a gap.

### Always read real website JavaScript — never guess

Before claiming a fix or a finding is correct, open the actual minified bundle in `globalStore.scriptCache` (or via `finding.view` / `finding.func` / `finding.callers` / `ast.probe.finding`) and confirm the AST decision against the real source. No assumed shapes, no "probably the framework does X", no test-only validation. If a real-site bundle is needed and not yet captured, capture it via the harness; don't reason without evidence. Production code if traced following ECMA will contain everything it has to otherwise the page would not function.

### Bind before build — don't reinvent what's vendored

A missing Web/spec capability is sourced in this strict order, never skipped:
1. **the host runtime's own capability**, bridged via `EM_ASYNC_JS` + JSPI — the wasm suspends, the host (real Chromium) runs the real API, the wasm resumes with the result. This is how `crypto.subtle.digest` is real (→ `self.crypto.subtle` = BoringSSL); the alternative of vendoring/hand-rolling crypto was explicitly rejected (BearSSL is alpha-grade; a wrong digest in a signature header is worse than an honest throw). Outside Chrome (the wasm CLI under node, no host WebCrypto) it throws a clear "run via Chrome harness" error, never a fabricated value.
2. **engine intrinsic** already in QuickJS-ng (e.g. `JS_AddIntrinsicAToB` for `btoa`/`atob` — note: wiring it into the *patched* context currently wedges it; that integration is an open bug, not licence to keep reinventing elsewhere)
3. **a Lexbor module already compiled into our wasm** — `url` (done), and the unused-but-present `encoding` (→`TextEncoder`/`TextDecoder`), `css`/`style` (→ real CSSOM / `getComputedStyle`)
4. **a faithful port of the spec algorithm** (e.g. WHATWG MIME Sniffing for CORB/asset classification)
5. only then hand-roll (never crypto/parsers from scratch)

The *only* things that are correctly ours: the analyzer-boundary fakes (record-only fetch/XHR/Headers shapes — a real network lib there would be wrong) and the research mechanism (forced-exec controller, opaque domain, event-loop pump, entry-point driver, SMT-directed pruning, structured body capture — paper-grounded, no off-the-shelf equivalent). Lexbor is Apache-2.0; QuickJS-ng MIT — both already vetted.

**Keep the vendored bases in sync with upstream (not a question — DO it).** A QuickJS-ng / Lexbor version bump is maintenance to perform, not to defer: upstream ships real value we want (e.g. 0.15.0 = native `btoa`/`atob` + Uint8Array base64/hex builtins, the `JS_NewSymbol(NULL)` segfault fix, atom-leak fix). The fork is heavily woven through `quickjs.c`, so a bump is a 3-way merge (`git merge-file` against the old + new upstream bases), NOT a blind overwrite — re-apply every fork patch, rebuild all targets, and re-run the FULL polarity gate set + a real-bundle deep-grind (`_idxdocs`) before claiming it landed. A bump that builds and passes the small gates but freezes/crashes a real bundle is NOT done — the regression is the bug, fix it (fixpoint, never a cap). Record the landed version in [[reference_quickjs_version]].

### Extension process split — where state lives (authoritative)

The MV3 service worker is evicted on idle, so it CANNOT hold learned state. The split:

- **`background.js` — thin, STATELESS service worker, extension-page-only.** Its only jobs: (1) own the offscreen document's lifecycle (`ensureOffscreen` on `onStartup`/`onInstalled`/`webNavigation.onCommitted`, so the offscreen is alive before content.js ships), (2) forward the browser events the offscreen can't observe (`webNavigation`/`tabs` → `__evt` NAV/TAB_REMOVED/TAB_UPDATED), (3) perform privileged `chrome.*` the offscreen lacks, as `__rpc`: `tabs.*`, `scripting.exec` (the exploit-probe injectors live in the SW because a `func` can't cross a message boundary). **Cross-origin `fetch` is NOT a SW job** — COEP `require-corp` does NOT block `fetch` (it gates `SharedArrayBuffer`/high-res timers and requires CORP only for *no-cors subresources*); a CORS `fetch` with the extension's `host_permissions` reaches any host **straight from the offscreen document and its Web Worker**. External requests (lazy chunks, source maps, discovery probes) fetch directly through ONE function — `safeFetch` (`lib/safe-fetch.js`, shared by the offscreen brain via `<script>` and the analysis Worker via `importScripts`) — the single auditable place the network-security invariants live: **GET only, cookies omitted, http(s)-scheme only**. The ONLY thing that ever blocked direct fetch was an over-restrictive `connect-src` — the extension-pages + `ast-worker.html` CSP must allow `https:`/`http:`. The SW holds NO learned data and performs NO fetches (no `swFetch`/fetch RPC — removed).
- **`offscreen-brain.js` (formerly `background.js`, loaded by `ast-worker.html`) — the LEARNING BRAIN.** Runs in the offscreen document (stable lifetime + IndexedDB). ALL state + logic: `globalStore`, VDD schema learning, discovery, AST merge, request log, protocol classification, `handlePopupMessage`, export, persistence. Its only direct `chrome.*` surface is `chrome.runtime.{sendMessage,getURL,onMessage,id,lastError}`; every privileged `chrome.*` call goes through `swRpc(...)`. Cross-origin fetches are DIRECT via the single `safeFetch` (`lib/safe-fetch.js`; GET only, cookies omitted, http(s) only) — NO SW relay, since COEP doesn't block `fetch`. Credentialed same-origin requests (`schema.verify` replay) go through `pageContextFetch` (the page renderer via PAGE_FETCH), NOT the SW.
- **`ast-worker.js`** (same document) exposes `self.astDispatch` — the brain calls it directly (a `chrome.runtime` broadcast does NOT reach the sender's own document) — and merges the worker's streamed deep-grind results.
- **Content scripts and the popup message the offscreen brain DIRECTLY** (the broadcast reaches the offscreen with the real, browser-verified `sender`). The SW never relays content payloads.

**Trust boundary = `sender.url`, never `sender.id`.** Every `onMessage` sender carries our id (external senders go to `onMessageExternal`), so the id discriminates nothing. An extension-origin URL is trusted (popup/offscreen); a web URL is a content script (UNTRUSTED — a compromised renderer can send any shape with our id). So: the SW honors `__rpc` ONLY from the offscreen URL; the brain honors `__evt`/`__fromContent`-style routing ONLY from an extension origin; content `CONTENT_TYPES` are accepted ONLY from a web origin and handled as untrusted page data with the real `sender`. Never reintroduce an SW content relay (it would launder page data into a trusted origin).

**Storage:** `chrome.storage.local` is BANNED (a compromised renderer reading cross-site metadata). Learned state → IndexedDB in the offscreen (`uasr_store`/`gapiStore` via debounced `scheduleSave`; the deep grind → `feDeepDB`; analysis opts → the `uasr_store` `analysisOpts` key). The request log lives IN-MEMORY in the offscreen brain (the `chrome.storage.session` layer was removed as pointless once the offscreen document's lifetime became stable — closed-tab logs stay viewable for the offscreen's lifetime, wiped only by bin/Clear). `chrome.runtime.reload()` / the offscreen recreate re-read the on-disk files (unpacked) and restore learned state from IndexedDB (request logs do NOT survive an SW reload — they're memory-only by design); only the bin/Clear button wipes persisted data.

### Source maps belong to the OFFSCREEN document, not the service worker (authoritative)

A name like `e`→`owner` is recovered by running a source-map LIBRARY (`@jridgewell/trace-mapping`) on the finding's call-site position — never a bundle transform, never hand-rolled. The MV3 service worker is the WRONG place to fetch or hold a map: it is evicted after ~30 s idle, so any in-memory map/cache/dedup-set there is gone between the messages that wake it. The **offscreen document** (which owns the Web Worker and has its own IndexedDB) does it:
- It FETCHES the map using the **real `sourceMappingURL` the bundle ships** — which may be a relative filename (`chunk.js.map`) OR a full address (`https://…/chunk.js.map`); resolve relative→absolute against the chunk URL. The `<chunk>.map` sibling is only a fallback when the chunk ships NO pragma. Never ignore the provided URL.
- It SAVES both the fetched **map AND the chunk's full JavaScript** in IndexedDB, kept until API learning has COMPLETELY finished all stages for that page (then dropped) OR the user clicks the bin/Clear icon. This is transient per-page working state, not lifetime storage.
- The relabel resolves DURING LEARNING (no popup needed): the resolved name is written onto the endpoint param (`_sourceMapName`, the only persisted source-map-derived datum) so the popup just displays it. Dedup is self-correcting off that persisted name — never an SW-memory set.
- Lazy/deep-grind-DISCOVERED chunks (the login-gated `preheat` chunk the browser never loaded) get the same treatment: the offscreen side has the chunk JS (it drove it) and fetches its map by its own `sourceMappingURL`.

### Real interactive testing only — never fake the browser

Use the live Chrome harness (`testing/harness.js`) over CDP for every UI / popup / SW behaviour check. Never stub `chrome.*` APIs, never mock the service worker. JSDOM is allowed where useful (e.g. parsing/DOM scaffolding off the hot path) — it is not a substitute for verifying real SW/popup behaviour through the harness. If a harness command is missing for a check the reviewer needs, extend the harness — don't write a Node-side fake. Tests that bake in synthetic Chrome behaviour codify a fiction; the only ground truth is the real extension running in a real Chrome started via the harness. Extension must be realistically usable with decent performance and high quality.

**Verify by reading the rendered popup DOM, not by querying the SW.** The harness commands already exist — `start`, `page "<expr>"` (active web page), `popup "<expr>"` (popup context). Verification = read what the user SEES: `document.getElementById("send-ep-select").innerText`, drive a control like a user (`sel.value=…; sel.dispatchEvent(new Event("change",{bubbles:true}))`) then read `#send-form-fields`. **Never craft `chrome.runtime.sendMessage({type:"GET_STATE"|"DIAG_TAB"|"GET_ENDPOINT_SCHEMA"|"CLEAR_TAB"…})` yourself** — those read/mutate internal state and "fake" the verification; the popup messaging the SW as a side effect of its own rendering is fine, you doing it is not. **Never write ad-hoc Node/`.cjs` scripts** beside the harness; extend `testing/harness.js` instead.

### Clear the storage before verifying — stale data is the #1 phantom-bug cause

Storage is **GLOBAL** — `globalStore` (endpoints / discoveryDocs / scriptCache / securityFindings), merged into every tab's state; only the requests/log tab filters by tab (no per-tab storage, no per-tab clearing). It lives in the **offscreen brain** and is **persisted to IndexedDB (`uasr_store`/`gapiStore`; `chrome.storage.local` is BANNED) and RESTORED when the offscreen is recreated**, so findings ACCUMULATE across worker builds and `chrome.runtime.reload()` does NOT clear them — it restores the old store. Reading that accumulated mix (old-build results + scriptCache replay keyed by analyzer-fingerprint + full-script-set) is what burned hours on a phantom "Z3 bug" that was only stale data. **Before concluding ANY engine/Z3/code bug from extension output, CLEAR the storage and re-verify on fresh data.**

Retention is intentional ("System must not delete past findings … to review it again based on the full scripts combination") — do NOT make the system auto-delete and do NOT "fix" the fingerprint to force-invalidate. Clearing is the TESTER's job: **the harness never clears**, so click the real button via the popup command — `node testing/harness.js popup "document.getElementById('btn-clear').click()"` (→ `clearGlobalStore()`) — then trigger a fresh analysis, then read. Never craft a `CLEAR_TAB`/`GET_STATE` message yourself (see the testing-policy section). Note `chrome.runtime.reload()` picks up `background.js` + `offscreen-brain.js`/staged-worker edits (the offscreen is recreated on the next navigation) and a per-page `tab.reload()` does NOT re-analyze (browser-cached scripts content.js doesn't re-ship), but neither clears storage — only the Clear button does. Never wipe `testing/profile/`, never kill Chrome; drive every verify run from the persistent profile + persistent harness Chrome.

### `window.open(...)` from `chrome.scripting.executeScript({world:"MAIN"})` has NO user gesture

Chrome's popup blocker drops it silently. The call returns `null`, no request is issued, the target tab never opens, downstream `win.postMessage(...)` is a no-op, and the probe wrongly reports NOT REPRODUCED even when the analyzer's verdict was REAL_EXPLOIT. The orchestrator pattern is `chrome.tabs.create({url: targetUrl, active: false})` (extension API is privileged) + `chrome.scripting.executeScript` on the target tab dispatching `window.postMessage(payload, "*")` from the target's own window. Same-window postMessage reaches the bundle's handler identically — handlers gate on `e.data` shape; origin pattern `"*"` matches. When a probe path returns NOT REPRODUCED despite a complete witness, look first for a `window.open` or other gesture-required API being called from a non-user-activated injection context; the fixtures-server access log (see `testing/fixtures_server.cjs`) is a fast way to confirm zero target fetches.

### Build a standalone reproducer in every host shape before blaming a vendored library

When something appears to behave differently across hosts (e.g. "Z3 model bindings differ between Chrome wasm and Node wasm with the same wasm bytes"), the very first concrete step is a minimal C/JS reproducer that exercises the vendored API the same way our code does, run in each wasm build (`node qjs_wasm.js`) + a real Chrome `new Worker(...)` (via the harness) — native is banned, so it is never a host shape. If the reproducer is uniformly correct across hosts, the divergence is on our side — go investigate Φ accumulation / term registration / scheduler / host-edge stubs / orchestrator / cached state — NOT the library. Only after the standalone reproducer itself diverges across hosts is "blame the third party" honest. The Z3 @P investigation cost hours of churn precisely because configuration / build-flag / SMT-solver-swap hypotheses were tried before the standalone reproducer that would have ruled them all out.

### Read the real source — don't generate blind

Patch sites in `quickjs.c` are edited against the real handler (Read it, match its single-exit idiom). The engine is rebuilt (`node engine/build.mjs cli|worker`) and the change is re-verified on real jQuery + the realistic-gate fixture via the wasm CLI (`node qjs_wasm.js`) before any claim — native is banned. Every wasm target is built from one source — no test-vs-ship divergence.

### Driver-gap ownership

A host call whose URL/arg has no concrete value on any forced path, where the source shows it WOULD be concrete on a path the driver didn't explore, is a P1: extend the forced-execution decision-vector / entry-point driver / host-edge model to reach it. Don't paper over with placeholders, don't say "unresolvable", don't blame "dynamic".

## Ideas for what to do during continuous work (rotate; don't stay in one)

In priority order for the goal:

1. **Endpoint completeness on real vendor pages** — per visited for example but not limited to Github/MS/Apple/Google page, the analyzer should yield ALL of: reached endpoints (forced execution `@H`), `@T → @H` promoted endpoints (`__feDriveStatic` invoking unreached functions for real), and live-traffic endpoints (captured XHR/fetch) for cross-check. Coverage gap on any is a P1. ## Forced-Execution Analysis Policy

A value is whatever patched QuickJS *computes* when the unmodified bundle runs; a sink/source is what an *executed* call reaches at the host edge, never what it is named. No syntax/identifier matching (code is minified — names are meaningless), no regex on code, no scoring, no heuristics. Scope, prototypes, closures, framework internals are exact because the real engine runs them.

**No caps or depth limits, no watchdogs, no termination enforcement**: 1 MB+ minified bundles must analyse without losing data — no size/step/depth/recursion cap, no schedule/run cap, no wall-time cap, no op-budget interrupt, no memory backstop. The engine runs the bundle's natural ECMA semantics. Termination is by FIXPOINT, never by a cap — three monotone seen-sets, each bounded by a property of the program, not a magic number:
- **distinct decision prefixes** — each forced run explores a path the seen-set hasn't seen; finite because prefixes are distinct and programs terminate per run.
- **event-loop callback identity** — the pump dedups callbacks by source identity (`Function.prototype.toString`); a monotone bounded set.
- **SMT-directed pruning** — infeasible flipped schedules are suppressed at emission.

The one genuinely-unbounded case is an opaque-controlled loop (`while(opaque){…}`) where the predicate never concretises: the forced run revisits the SAME branch at the SAME forced-state (frame-id + decision-prefix) forever. That is NOT "correct non-termination to leave alone" — a fiber that never reaches a *new* forced-state never yields productively and silently STARVES every other page's grind (the scheduler rotates at yield boundaries, and this fiber's yields are all at one stuck state). The fix is the SAME fixpoint discipline applied intra-run: revisiting an identical `(frame-id, decision-prefix, pc)` forced-state is a terminating cycle (Cousot–Cousot monotone fixpoint — the doc already cites it), so the loop's opaque arm is taken finitely. This is a fixpoint, not a cap: it bounds re-visits of *identical* state, never distinct work. Never add a limit, a watchdog, an interrupt deadline, or a memory cap; if a page is slow, the scheduler rotates to other pages at the per-orphan / per-branch JSPI yield boundaries — it does NOT terminate the actual JS execution. A stuck SAME-SCRIPT path is likewise resumed-around (a higher-priority same-script orphan/schedule runs) — but the spin itself is closed by the intra-run fixpoint, never papered over by punting to a yield: a path that can't terminate must be made to terminate, not merely de-prioritised.

**Depth without heat — the unified scheduling model (authoritative; complements "No caps")**: completeness (learn the WHOLE unused-feature surface, incl. login-gated lazy chunks via the deep `@T → @H` orphan drive) is achieved by a resumable priority frontier — NOT by throttling work. **CPU usage is a USER CHOICE, and the DEFAULT is FAST: a free core is not left unused.** This is a security-RESEARCH tool — the user actively opened it and is WAITING on the API surface, so the default must USE the available core(s) (throttle DEFAULT = 0, no per-run sleep), not idle at 50% duty to be "polite". Cooling (raise the ⚙ "Yield throttle" slider; lower the worker pool) is an OPT-IN for users who want background-friendliness — and even then the focused page stays hot (the `_isActive` throttle exemption in `ast-thread.js`). The earlier "time is free, a maxed core is not / background worker" framing was the wrong default for an interactive research tool and is RETIRED; relevance-ordering + active-page focus already decide WHAT runs first, so full speed just means MORE learned sooner. ONE abstraction governs BOTH same-script and cross-page scheduling: **a resumable priority frontier, never a FIFO worklist.** FIFO forces the false choice the user rejected — run a path to completion OR cap it — because a FIFO item can't be paused and re-prioritised later. A priority frontier whose items carry a STABLE id (so progress is "what's done", not "where we are") runs the most-useful bit now, yields, and resumes the rest later with no cap and no lost work. The model has these load-bearing parts, none removable to "go faster":
- **Throttle (CPU duty), user-tunable — DEFAULT 0 (fast)**: the deep grind is ONE `--fe-deep-grind` callMain that drives every residue orphan, JSPI-yielding PER ORPHAN (and per opaque branch via `qjs_host_yield`). The deep grind itself is macrotask-paced (one resume per `_yieldMC` turn) and NOT throttled by the cap; the cap (`THROTTLE_CAP_MS`, `ast-thread.js`) only governs the SCHEDULE-BFS per-run sleep and now DEFAULTS TO 0 (no sleep — use the core). The popup ⚙ "Yield throttle" slider (`SET_ANALYSIS_OPTS.yieldThrottleMs`) raises it for users who want a cooler background; the `_isActive` exemption keeps the focused page hot regardless. There is NO `DEEP_BATCH` size knob and NO JS-side outer batch loop — the engine drives to exhaustion, the host paces it at yields.
- **Parallelism is across PAGES, not within one**: `ast-worker.js` owns a Web Worker POOL. Sticky routing pins a page to ONE worker, and within a worker exactly one wasm executes at a time — so a SINGLE page's grind uses ONE core no matter the pool size; extra workers only parallelise CONCURRENT pages (multi-tab research). The pool default stays 1 because the pool is PRE-ALLOCATED (each worker holds its own wasm linear memory, ~hundreds of MB) — pre-spawning cores-1 idle wasm instances for a single-page user wastes memory it can't use. The popup ⚙ "Analyzer workers" setting (`SET_ANALYSIS_OPTS.maxWorkers`) grows it for multi-tab parallelism. PROPER next step (so "don't leave a free core unused" extends to multi-tab WITHOUT the memory waste): LAZY pool growth — spawn a worker on demand when a NEW concurrent page needs one, up to ~cores-1, instead of pre-allocating. The single-page "fast" lever is the throttle default (above), not the pool. Sticky routing by pageKey keeps a page's reviews + grind on one worker so its in-worker fiber state stays consistent; new pages round-robin onto the least-loaded slot. WITHIN a worker, multiple page analyses are suspended JSPI fibers — exactly ONE wasm executes at a time per worker (no data race), but the scheduler interleaves them at yield boundaries by priority.
- **Preemption is the comparator, not a flag**: a live review's fiber competes in the suspended-fiber queue (`self._fiberQ`); `priority.js` `flowCmp`'s ACTIVE-PAGE-FOCUS tier wins every tie, so the page the user is ON resumes ahead of background grinds at the next per-orphan/per-branch yield — no `_yieldDeep` flag, no batch-boundary wait. The old serial two-tier `_pump`/`_yieldDeep` design is gone.
- **Cross-session resumability (eventual consistency)**: the deep grind persists the combined bundle ONCE + the driven-SET to **IndexedDB** (the offscreen worker's origin — the SW has none). On MV3 eviction OR a full browser restart the grind resumes from the saved driven-SET with the saved JS — no code re-fetch, no lost progress. `background.js` `onStartup`/`onInstalled` proactively recreate the offscreen doc so the resume kicks WITHOUT needing a new page visit. `_resumeIncompleteDeep` resumes incomplete grinds, re-entrancy-guarded by `_deepGrindRunning`. **KNOWN GAP — the model and the code diverge here, and it FREEZES:** the code currently runs ONE grind at a time (`if (_deepGrindRunning.size>0) return`) to bound wasm-instance memory, but a single un-preemptible live grind is a FIFO-ish violation of the priority-frontier invariant above — proven 2026-05-30 (liveness probe): a NON-TERMINATING orphan in the one live grind never returns, so the gate never clears and every other page's grind is starved (active page included). The principled target satisfies BOTH the frontier invariant and the memory bound: RELEVANCE-BOUNDED live instances (active page + a small set) with lower-relevance grinds SUSPENDED-to-IDB (driven-set persisted, instance freed) and rehydrated on focus — NOT "every grind concurrently" (memory blowup) and NOT "one serial" (freezes on a stuck orphan). PRECONDITION for any of this to matter: a stuck orphan must be MADE to terminate (the intra-run forced-state fixpoint above) — a preemptible frontier still can't finish a grind whose current orphan never returns; it only stops that orphan from freezing the OTHERS. Until both land, the active page wins via `flowCmp`'s focus tier only AFTER the current grind yields/exits, so a stuck grind defeats it. Goal unchanged: every persisted grind eventually reaches `rem=0` (IDB record dropped); none abandoned.
- **Relevance-first usefulness order** — `relevance × quality × effort`, lexicographic, no magic weights:
  - **CROSS-PAGE relevance = MOST-RECENTLY-VIEWED first.** Launch order (`deepRoundCmp`) and `flowCmp`'s tie-breaker both key on **`vts`** (visit timestamp: set on the page visit, PRESERVED across resume batches — NOT the per-batch `ts`, which would let a still-grinding old page outrank a freshly-opened one). `vts` tracks VIEW recency: switching to an already-loaded tab (`chrome.tabs.onActivated` → `__evt TAB_ACTIVATED` → `_onTabActivated` → `DEEP_FOCUS`) bumps that page's `vts` so the tab you're reading leads. The page you're ON also wins via `flowCmp`'s active-page-focus tier.
  - **CROSS-PAGE fiber order (`flowCmp`)**: active-page-focus > reaches-host-edge > recent ENDPOINT emissions (`@H`) > recent SECONDARY emissions (`@T`/`@S`) > visit recency > anti-starvation ts. Endpoints (goal #1) outrank structural candidates and security sinks (goal #10) of equal count — a fiber producing real `@H` records resumes ahead of one producing only `@T`/`@S`.
  - **SAME-SCRIPT orphan order: ENDPOINT → QUALITY → SECURITY → EFFORT** (`qjs_priority_deep_relcmp` for the build-time sort, `qjs_priority_live_orphan_better_bits` for the per-pick LIVE scan, both `priority.h`). Tier 1 = **ENDPOINT** = `qjs_fn_reaches_net` (fetch/XHR/WebSocket/EventSource/sendBeacon/send) — the login-gated `preheat` fetch lives here; ordering sinks first once buried it at driven-position ~1008/1108. Tier 2 = **QUALITY** = `qjs_executed` (body RAN in real context — concrete closure/module state — but host SITE guard-skipped, `qjs_h_fired=0`: the preheat shape; resolves CONCRETE URL/body values where a cold orphan yields only an opaque shape). Tier 3 = **SECURITY** = `qjs_fn_reaches_sink`. Tier 4 = **EFFORT** (smaller bytecode first). The live-pick is non-FIFO: at each pick it scans the residue for the highest-priority not-yet-driven fn, reading CACHED net/sink bits (`qjs_deep_net`/`qjs_deep_sink`, computed once) + the LIVE `qjs_executed` — so a fn whose body ran mid-grind promotes immediately, with no per-compare bytecode walk (the O(N²·bytecode) cost is gone; net/sink are static so they're hoisted out of the loop).
  - **Resume = per-function-ID driven-SET, NOT a cursor index.** The engine keys each function by a STABLE id (FNV of file:line:col, independent of order/execution), emits `@DD <id>` per driven function; the worker persists the union (`prog.driven` in feDeepDB) and on resume writes it to `/driven`, loaded so those functions are skipped (`qjs_fn_id`/`qjs_dd_*`/`qjs_deep_step_c`). Because progress is WHAT-is-done (id) not WHERE (index), the usefulness order can change freely across runs (even by execution state) WITHOUT skipping or re-driving — the index-cursor's fatal flaw (a reshuffled list skips orphans = lost coverage) is gone.
  - ONLY reorders — every orphan still driven, depth never capped; SCHEDULING, never a value heuristic.

The invariant a future change must preserve: **high quality/depth AND low CPU/memory, via a relevance-prioritised, preemptible, cross-session-resumable, eventually-consistent priority frontier (never FIFO)** — never trade depth for a cap, never lose persisted JS/driven-SET on eviction or restart. Serial-vs-parallel and throttle duty are USER cooling choices (popup ⚙), not hardcoded.

**The bin/Clear button = a hard STOP + total RESET (authoritative)**: the toolbar bin icon must DELETE ALL extension data AND stop all work outright — never a cooperative "please stop" flag the worker can ignore while running on already-deleted data. Concretely (`AST_CLEAR` in `ast-worker.js`): the offscreen doc (which OWNS the Web Worker POOL) `terminate()`s EVERY pool worker (killing any running wasm instance immediately), `indexedDB.deleteDatabase("feDeepDB")` wipes the resumable-grind state (the terminates closed the only IDB connections, so the delete isn't blocked), then a single FRESH worker is spawned (the user's pool size re-applies on the next `SET_ANALYSIS_OPTS`); the brain (`offscreen-brain.js`) wipes `globalStore` (all maps incl. `deepResumeMeta`) + the persisted `gapiStore` in IndexedDB + the in-memory request logs (the `chrome.storage.session` layer was REMOVED — the stable offscreen document holds logs in memory now) + `_scriptBuffers` + the review queue. A monotonic `_dataEpoch` (bumped on Clear) is captured by every in-flight analysis / async source-map re-merge / resume merge, which abandons its write if the epoch moved — so work already in flight when Clear ran can't repopulate the just-wiped store. `_dataEpoch` is eviction-agnostic (a clear, not an SW restart, bumps it), so it never suppresses a legitimate post-eviction resume. This RESET is distinct from the **AST version system** (analyzer-fingerprint cache-miss → automatic rescan on code change) which must NEVER clear past findings — findings accumulate; only the explicit bin/Clear wipes them.

**Driver/resolver completeness**: every URL/method/body value comes from what the execution computed (or from the seven other learning sources). A target that is opaque on every forced path is recorded once on `resolverErrors` (the adapter detects the `[object Object]` opaque marker — never a false page-origin URL, never `"unresolvable"`). Closing it is a P1: the missing transfer is either a host-edge stub returning the wrong/concrete shape, or an `OP_*` the opaque should be infectious through but isn't (extend the `quickjs.c` patch set, mirroring the existing single-exit guards) — never a parallel resolver.

- **Network sinks**: `XMLHttpRequest#open/send` and `fetch` are recorded by `hostedge.js` as `@H {api,args,at}` (args = `[url, method, bodyStr, bodyShape]`) when the *executed* bundle reaches them. `ast-thread.js` / `drive.mjs` pair open→send PER forced run, aggregate example values across runs; the URL/path/param-name structure is learned even when a value stays opaque (structural learning, never a fabricated value).
- **Inter-procedural / framework**: nothing to model — QuickJS runs the wrapper/factory/HOF/Deferred bundled code itself; the host hook sees the native call it ultimately reaches.
- **Taint sources**: the WHATWG attacker set is the host-edge data made opaque in `hostedge.js` — `location.hash/search`, `document.cookie`, `*Storage.getItem`, `window.name`, `XHR.responseText/response/status`, `fetch` `Response` bodies, `postMessage` event `data`/`origin`. Opaque is infectious (get/call/`JSON.parse`) so it reaches branches and sinks through the bundle's real code. DOM *structure* stays concrete so frameworks boot.
- **Security sinks**: code-exec (`eval`/`Function`/`setTimeout`|`setInterval` string arg), open-redirect (`location.href=`/`assign`/`replace`/`window.location=`/`location.search=`), DOM-HTML (`innerHTML`/`outerHTML`/`insertAdjacentHTML`/`document.write`), and script-bearing `setAttribute` (`href`/`src`/`on*`/`srcdoc`/`formaction`). `hostedge.js` emits an `@S` record **only when the value is tainted** — `__isOpaque(v)` (the non-`OP_CMP` concrete primitive) or the concat-derived `[object Object]` marker. A concrete write (jQuery feature-detection `innerHTML`) is not a finding and costs nothing.
- **Exploit confirmation by Z3 path-satisfiability (security only — never API-value resolution)**: an `@S` record by itself is **TAINT REACH ONLY** — a candidate that may be false because guards on the path can make any exploit-shaped value unreachable. Z3 is linked directly into QuickJS (C, no JS bridge); at the tainted sink, the source→sink path constraints accumulated over the attacker-tainted `qjs_opq` identity are asserted and the solver is asked for an exploit-shaped witness: **SAT ⇒ REAL_EXPLOIT** (the model is the concrete attacker witness), **SAT(Φ) ∧ UNSAT(exploit) ⇒ TAINT_REACH** (path feasible but Φ pins the value to a non-exploitable literal), **UNSAT(Φ) ⇒ INFEASIBLE** (X-Force forced incompatible gates — adapter suppresses; never reaches the reviewer). The SAME Z3 also runs at TAINT F-frontier emission as the BFS-pruning filter; both uses are about path feasibility, never API-value invention.
- **Z3 failures surface as `Z3_ERROR` + `@E` — never silent**: a C++ trampoline (`qjs_z3_shim.cpp`) wraps the inner solve. A Z3 C++ exception is caught, the `typeid` + `what()` is reported via the `@E` channel (`{channel:"z3", sink, error}`), and the verdict is the distinct `Z3_ERROR` string — drive.mjs / ast-thread MUST NOT collapse this into TAINT_REACH. Inline `Z3_get_error_code` checks after each Z3 API call catch non-throwing failures (handler set via `Z3_set_error_handler`).
- **Honest current stubs (the record; close them via bind-before-build, never claim otherwise)**: `crypto.subtle.digest` (SHA-1/256/384/512) is REAL in the wasm worker — host-bridged via `qjs_host_digest` (`EM_ASYNC_JS` + JSPI) to the host runtime's `self.crypto.subtle.digest` (Chromium BoringSSL when loaded in Chrome), so a body-hash signature header (`X-Hub-Signature`, AWS SigV4, MS Graph) carries the correct digest; the wasm CLI under node has no host WebCrypto so it THROWS a clear "run via Chrome harness" TypeError rather than returning a fabricated value (verified against NIST FIPS 180-4 `SHA-256("abc")`).
