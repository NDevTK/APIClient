# Invariants
- **NO BOUNDS.** Never add or keep a depth/step/time/run/memory/recursion cap, watchdog, idle/drain/no-progress/recycle count, seen-set, or same-args/same-state fixpoint. A bound truncates distinct work the scheduler would otherwise reach productively. Delete it; the WFQ STARVES the unproductive flow by emitted output — pause ~0 CPU, resumable, snapshot, evict. The engine never throws its own depth RangeError; recursion is reviewed at every depth. A "re-computes nothing" proof is a cap in disguise: shared state (a global/heap/closure one function mutates and another reads) means byte-identical args can still PROGRESS, so only emitted output — never identity — proves a flow is done.
- **Only EMITTED OUTPUT proves progress** — new @H (endpoint) / @S (XSS sink), weighted equally; never a static "reaches a network edge" guess, identity, fixpoint, or count. The WFQ reads it to choose what runs vs what starves. A diff counts only if it moves `netdiff --unused`, lands a verified capability the metric will then show, or names the exact next diff — flat-with-no-named-next-diff is the addiction trap.
- **Find the ROOT; never mask it.** If a throw/overflow/abort shouldn't happen, make it IMPOSSIBLE (complete the primitive), then delete the workaround because it is DEAD — never keep it as a stopgap or pre-tune around its absence (no GC-loop-before-free, per-N respawn, swallowed `Aborted()`, placeholder, recycle/abandon count).
- **NEVER revert a correct fix** to dodge a regression or verification — break first, build the proper fix.
- **VERIFY on the REAL thing:** live Chrome harness (`testing/harness.js` — use `restart`, not `start`: `start` no-ops when Chrome is already up and reuses a persistent profile, so it runs a stale wasm against a poisoned IDB) over real bundles + served fixtures (`testing/fixtures/*.html`). Native + node-CLI banned (no JSPI/safeFetch/Chrome-crypto → false confidence); never stub `chrome.*`. One TARGETED minimal single page test of design correctness only — regression tests don't show design quality; a metric held flat across commits is benchmaxxing, banned. Clear storage before concluding any bug (stale global state is the #1 phantom). Read the real minified JS before claiming a fix; dogfood the rendered popup DOM, not offscreen internals. Root cause narrowing should not use the REAL thing until fully ready
- **No silent failure.** Every zero-result path emits `@WHY{phase,reason}`; every catch surfaces `@WHY`/`resolverError`/`@E`. "0 endpoints + 0 errors" is the worst output. Measure before hypothesizing — a root cause asserted without a distinguishing signal is a guess that costs a build+verify cycle.
- **Own the push.** Commit + push VERIFIED work to main yourself. Engine is the submodule `engine/qjs` = fork `github.com/NDevTK/APIClient-quickjs` (remote `origin`) branch `apiclient-v2` (the clean-upstream v2 rebuild; the old 262-commit `apiclient-fork` is preserved but dead), kept in sync with `quickjs-ng/quickjs` (remote `upstream`, tracks `upstream/master`). # The coupled mechanism (#5–#10 = ONE design)
**THERE IS NO GRIND. BFS IS THE ONE SYSTEM.** Orphan-driving (force-invoking a never-called function to surface its unused endpoint) is just another BFS FLOW — the same forced-execution as a boot fork or a branch-arm — ordered by the ONE WFQ, never a separate "deep grind" phase / `--fe-deep-grind` callMain / `while(driven<maxN)` loop / driven-set / head-tail / `@DPAUSE` machinery. "BREADTH first THEN DEPTH" is NOT two systems or two phases: it is ONE continuous BFS whose ONE WFQ merely ORDERS higher-value-of-information flows (the shallow fetch) ahead of lower (the deep residue), all in ONE queue, ONE registry, ONE loop. A second scheduler beside it — engine-side (silent-counts/fixpoints, a separate deep-step driver) OR host-side (`ast-thread.js` deep-grind loop, no-progress recycle, per-culprit abandon) — is the cardinal violation: DELETE it, never add another.
ONE WFQ POLICY — `priority.js`'s (weight = 1 + epRate + UCB-explore + fairness-floor; ORDER-only, never drops a work item) — at BOTH levels: the host's cross-page fibers (one wasm instance per page ⇒ cross-instance scheduling is inherently host-level) AND the engine's within-page flows alike — boot fork, branch-arm, orphan-invoke, loop/recursion arm — each a COW snapshot on the segmented heap call-stack, every flow preemptible + cross-session-resumable, ordered by value-of-information. UNBOUNDED until the disk floor; the single ATTENTION runs across all sites; non-FIFO (value-ordered) because plain FIFO explores less.
- **ONE GLOBAL, CONTINUOUS, CROSS-SESSION FRONTIER.** There is exactly ONE attention process for the whole extension, and its frontier is the UNION of every flow from every origin ever visited, persisted in IndexedDB and never reset. Visiting a new page does NOT start a new scheduler, a new run, or a fresh attention — it APPENDS that page's flows (boot fork + orphans) to the one global frontier, which the ONE WFQ then re-ranks against every already-parked flow from every other site and every prior session. A browser restart resumes the same frontier by global value-order; a high-value flow parked on site A last week outranks a low-value fresh flow on site B today. Learning is monotonic and never per-page/per-session-scoped: `netdiff --unused` is a GLOBAL cumulative surface, not a per-tab tally. "Proper BFS across all seen websites" = this single frontier, ordered by value-of-information, paged against RAM with the cold tail on disk. Any per-page/per-session/per-tab scheduler, registry, run-counter, or attention reset is the cardinal violation — there is only the one.
- **Overflow impossible by construction — THE unbuilt core, top priority:** the goal is to trampoline ALL calls onto the heap stack so any flow is heap-switchable at ANY call depth. STATUS (measured, do not overstate): NOT done. `OP_call` still C-recurses into `JS_CallInternal` (quickjs.c ~18622), so normal recursion overflows at depth ~1500 and throws `JS_ThrowStackOverflow` — the async heap-frame substrate (`JS_FlowNew/Resume`) only makes a flow switchable at its OWN await/yield boundary, NOT at nested sync call depth. This single gap is why "resumable heap switching, fair to all documents" and "cross-session resume of deep flows" are only PARTIAL: a flow deep in sync calls can neither be preempted for another document nor evicted+replayed (replay would re-overflow). The milestone is the OP_call/return trampoline: turn `JS_CallInternal`'s recursive call into push-heap-frame + `goto restart` (reusing the async `JSStackFrame` heap-frame representation) and OP_return into pop+restore, so the C function returns only when the frame stack empties. C-function re-entry (`apply`/Proxy/array-callbacks via `js_call_c_function`→`JS_Call`→`JS_CallInternal`) is the SAME residue on the C-builtin path. Complete both and the overflow→recycle/abandon workarounds + every `JS_ThrowStackOverflow` become dead code to delete; the engine then never throws its own depth RangeError. A loop reuses one frame; deep recursion grows by segments — both yield per-opcode.
- **Shared state:** each flow/arm owns its OWN COW snapshot (never reuse another path's heap); context-switch = restore that snapshot.
- **TWO VIEWS, one run: @H (API) and @S (SECURITY), weighted equally.** @S = an XSS/injection SINK (innerHTML/outerHTML/insertAdjacentHTML, document.write, eval, `el.href`/`.action` javascript:, `setAttribute` on-handler/url) reached by OPAQUE (external-input-tainted) data — opacity IS the taint. But **@S detection is only the TRIGGER; the DELIVERABLE is a WORKING PoC compiled by REVERSING the traced flow, using the SAME forced-exec engine — never a template.** The design: opaque values carry PROVENANCE (source + the exact transform chain applied: substring/concat/decodeURIComponent/replace… + the constraints from every forced branch on them). At a sink, `sinkValue = chain(source)` + the sink CONTEXT (HTML body / raw JS / URL). (1) INVERT the recorded chain to get `source = chain⁻¹(payload)` — most chains are directly invertible; a char FILTER (`.replace(/</g,'')`) is a constraint that either forces a filter-safe payload or PROVES the flow safe. (2) Build the payload from the ACTUAL sink context (the concrete surrounding text from provenance), not a canned template. (3) VERIFY by re-running forced-exec with the CONCRETE candidate source — the engine verifies its own PoC by deterministic replay (marker fires / breakout survives). **NO Z3.** The hard constraints inversion can't invert directly (correlated/nonlinear/regex) are solved by FORCED-EXEC SEARCH — candidate sources are explored as ordinary FLOWS in the ONE scheduler, ranked by "reaches the sink with a live payload," refined by what the REAL code does on concrete replay (the branch the candidate actually takes, guided by the recorded constraint). This handles arbitrary complexity — interprocedural effects and SHARED MUTABLE STATE that a symbolic solver cannot even model — because it runs the real code, so it is strictly MORE capable than Z3, not a fallback to it. Foundation to build = opaque-WITH-PROVENANCE (replace the single sentinel; every opaque-propagating op records its transform + branch constraint).
- **FORCED EXECUTION IS THE WHOLE CONSTRAINT+VALUE ENGINE — NO Z3, NO SEPARATE SOLVER.** Running the real code — with interprocedural effects and SHARED MUTABLE STATE that a symbolic solver cannot even model — is strictly MORE capable than symbolic solving, so a bolted-on solver is a best-design violation to delete, never a residue. Real example VALUES come ONLY from RUNNING the code (computed values, `location.origin`, `fromReply` server data, executed lazy-chunk code) — a solved value would be a FABRICATED example. PATH work: force BOTH arms of every opaque branch; the WFQ starves the unproductive one. CORRELATED constraints (`x>5` then `x<3` → a PHANTOM endpoint if the arms are forced independently): a lightweight range/interval tracker on the opaque value (part of provenance) catches the contradiction and prunes the arm — and the genuinely hard residue (regex/string/nonlinear) is solved by FORCED-EXEC SEARCH (candidate concrete inputs explored as ordinary FLOWS in the ONE scheduler, kept/refined by what the REAL code does on replay), which subsumes the solver because it handles shared state + interprocedural flow the solver can't. The whole thing is ONE scheduler: value discovery, path exploration, constraint satisfaction, and PoC search are all just flows it orders by value.
- **Attention:** per-opcode RETURN-to-scheduler from `JS_CallInternal` — NOT a JSPI suspend (JSPI saves the C stack while frames live on the heap arena → teardown desync/double-free). Universal, boot included. The yield CHECK is per-opcode; the yield DECISION is VALUE-driven — suspend the running flow the moment a parked flow outranks it (or on an emit/fork/suspension that changes ranks), NEVER after N opcodes (a per-N/opcode-budget counter is a step cap, banned). A flow that stays top-ranked runs on with ~zero switch cost; the WFQ, not a clock, decides when to switch. Driving the call/object graph synchronously outside the scheduler (a boot epilogue) is the same sin as a bound — drive it per-orphan, yielding.
- **OOM:** snapshot/restore is ONE primitive (pause/resume, eviction, per-arm isolation). RAM = the hot working set; the cold/low-value tail moves to **IndexedDB** (not localStorage/`chrome.storage.local`). **Disk is the platform FLOOR — finite, real, NOT a bound to remove. IDB doesn't make OOM "impossible," it bounds RAM and moves the residue to a larger, slower floor. BFS is what makes that sound: it extracts the productive breadth before the floor is approached, so disk-pressure only ever touches the least-valuable starved tail, never lost productivity.**
- **Cross-session resume is REPLAY, not live-graph serialization.** A parked flow has TWO representations: HOT = the live heap frame in RAM (`JS_FlowResume` on the async heap-frame substrate — cheap suspend/resume for interleaving); COLD = a compact REPLAY RECIPE persisted to IDB = (bundle-ref/hash + the flow's DECISION VECTOR + the origin's one-per-endpoint `fromReply` cache + accumulated value). Eviction drops the live frame, keeps the recipe; rehydration RECONSTRUCTS the flow by re-running boot to the baseline then REPLAYING the decision vector — never by deserializing a live continuation + reachable object graph. **COW isolation is exactly what makes this sound: a flow's state is a deterministic function of (post-boot baseline, its OWN decision vector, its own execution) and NEVER of another flow's writes, so replaying its decisions over a re-run boot reconstructs it byte-for-byte — shared state and interprocedural effects included, because re-running boot re-establishes ALL of them natively.** Literal graph serialization is the WRONG primitive: it must rebuild object identity/aliasing across shared mutable state (the exact case that breaks it), and quickjs has no continuation serializer; replay sidesteps both. Replay cost is bounded by the eviction policy — only SHALLOW, low-value, few-decision flows are ever evicted (BFS keeps the deep productive ones hot), so a rehydrated flow is always cheap to replay. The decision vector IS the serialized continuation, compact and robust.
- **Prioritization, never fixpoint termination.** Nothing terminates; the unproductive is starved to ~0 CPU, resumable. An overflow-prone forced recursion is usually an ARTIFACT — forced/opaque branches drive a continue-arm into a call stack real input could never reach; the opcodes see it soundly (`OP_if` on an OPAQUE value driving `OP_call`), the sound replacement for `recur_collapse`.
- **Boot is the hard gap:** single-path + frees-on-silent because the COW baseline is established post-boot — needs an in-flux baseline so boot forks become snapshot-able like every other BFS flow (boot is just the first flow, not a privileged phase).
