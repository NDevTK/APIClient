**THIS FILE CARRIES NO STATUS. Comments are not valid for follow ups it must crash or be built. **THE ONE EXCEPTION IS A NAMED RESIDUAL, AND IT IS AN EXCEPTION BECAUSE THE CODE IS RIGHT RATHER THAN UNFINISHED.** §C-stack already requires it — "record it BY NAME so the next attempt starts from building the named thing, never as a silent narrowing" — and read strictly against the sentence above that is a contradiction, so here is the line between them. A comment standing in for work that could be done NOW, or describing a gap in prose a reader cannot act on, is the banned thing: it is documenting a gap instead of fixing it, and a DCHECK belongs there. A NAMED RESIDUAL is different in kind: the code is CORRECT for what it does and NARROWER than the spec, so there is nothing to crash on — the crash would fire on a case the engine handles correctly. It earns its place only by being falsifiable, so it states three things at the site: exactly WHAT is not covered, WHAT the next diff builds, and HOW ITS ABSENCE WOULD SHOW. A residual missing any of the three is prose, and prose goes. The test is mechanical: **if the code is WRONG right now, crash; if it is RIGHT but narrower, name it; if you cannot say how you would know it fired, you have not understood it well enough to leave it.** Worked examples that are residuals and not TODOs: a cross-origin child navigable loading uncredentialed where a browser sends cookies (correct for same-origin, narrower than §7.4, shows as a logged-out reply from a peer document); an injected `src` and an `import()` reporting one token where Fetch §2.2.5's DESTINATION separates them (correct CORB for both today, shows the day a destination-specific rule differs). **AND THE "WHAT THE NEXT DIFF BUILDS" CLAUSE IS A CLAIM ABOUT THIS TREE, SO IT ROTS EXACTLY LIKE A `DFAIL`'S — WITH ONE DIFFERENCE THAT MAKES IT WORSE.** The three clauses are not alike in what they can be wrong about: WHAT IS NOT COVERED and HOW ITS ABSENCE WOULD SHOW are statements about the SPEC and about OBSERVABLE BEHAVIOUR, and a reader who acts on either finds out. WHAT THE NEXT DIFF BUILDS names a MECHANISM, and naming one asserts what this codebase already contains — the stale-`DFAIL` failure mode arriving through the clause this file REQUIRES, rather than through a crash. The difference is who reads it: a `DFAIL` is read by everyone the crash stops, so a wrong one meets traffic, while a residual's next-diff clause is read by exactly one person, once, at the moment they have already decided to do the work — so a wrong one is not caught, it is EXECUTED. Measured: a hand-off said the counter its next diff needed could be "driven from the per-opcode attention check that is already the one thing counting a flow's own progress", and that check COUNTS NOTHING — the poll's own comment says "nothing counts and nothing is bounded here", at the entry the clause named. The refutation was sitting at the site, which is where `error_event.c`'s was too. So the clause states what must EXIST AFTERWARD and never what to reach for; where it names a mechanism as already present it is a claim under the same rule as a `DFAIL` naming another file — GREP THAT ENTRY BEFORE WRITING THE CLAUSE, and grep it again before obeying it, because the interval between those two readings is the whole of the time the tree had to move. **AND A CLAUSE THAT NAMES A LINE BY NUMBER IS CHECKED BY READING ITS CALLERS, NOT BY CONFIRMING THE LINE IS THERE** — the line is usually right, and what the clause is wrong about is its ROLE. Measured, and caught one read before it landed: a residual said "this file's argument-side check goes; the one at the other line stays", and the line number was exactly correct — but it sat inside a shared helper with THREE callers, so the argument path was one of them and deleting it would have removed the same spec step from a record's value and from both elements of a sequence, flipping a WPT test that exists and passes today from throwing to not throwing. Confirming the line exists would have passed; only reading who calls it caught anything. **This is the §AN-ASSERT-THAT-NAMES-A-REMEDY defect arriving in a hand-off instead of in a crash**: a shared helper looks like a single-purpose call at its own site, and a coordinate is exactly the form that hides how many roads lead to it. So a residual naming a site names WHAT IT DOES AND FOR WHOM, and a receiver acting on one counts the callers before deleting anything.

# Disposition
- **Best long-term design over everything** — over speed, safety, passing tests, and existing code. The design is never perfect; never stop improving it, never paper over a problem. One concrete landed diff per turn minimum. The stop-hook is a "go", not "did I do enough?". Context length is not a stop signal. Keep going — no drift toward closure, no quick-fix exits.
- **Biggest mechanism change comes FIRST.** Deferring progress to dodge risk is always wrong. A task's SIZE is never a licence to defer ("major undertaking", "own session", "fresh budget" are banned — there are no fresh sessions). The bigger the goal, the SMALLER the first concrete diff: decompose and land it THIS turn. A probe that localises the trap IS the diff; a verified narrowing IS the diff. A goal that stays a LABEL never progresses.
- **Regressions are encouraged**, never a reason to defer — regression risk COMPOUNDS every turn the wrong system stays load-bearing. Break first, then build the proper fix. Never revert a correct fix to dodge a regression. No bulk sweeps.
- **A superseded system is DELETED in the same diff, never kept as a fallback** (not behind an `if`, not a "safety net", not tried-then-overridden). A legacy fallback hides the new system's gaps and re-accretes dual-system rot; the new system must stand alone and CRASH where incomplete (the forcing function). "pre-existing" does not exempt code from removal.
- **Fix the ROOT; never mask it.** Make an impossible state impossible (complete the primitive), then delete the now-dead workaround. Fix limitations — never document a gap instead of fixing it, never a comment where a DCHECK belongs. Ask only to resolve genuine intent ambiguity, then follow up until resolved.
- **A `DFAIL` OUTLIVES THE ABSENCE IT DESCRIBES, AND THEN IT LIES.** The crash that names what to build is the right mechanism, and its failure mode is the mirror of a stale comment rather than the same one: the text stays accurate about the SPEC and goes wrong about THIS TREE, so it reads as authoritative while sending the next reader to build what is already there. Three in one session: `rendering.c` said report-an-exception "is a component this engine does not have" while `error_event.c`'s own comment recorded that this very DFAIL is why it was written; `shadow_root.c` said "this engine has exactly one registry" in three places after `CustomElementRegistry` became constructible; a DFAIL instructed the next person to build `tooLong`/`tooShort` from `minlength`/`maxlength`, which §4.10.19.3/.4 make unreachable without a user edit — the instruction was SPEC-WRONG and had been followed once. So a DFAIL naming another file is a claim about that file, and the claim is CHECKED before it is trusted and RE-CHECKED before it is repeated: grep the entry it names before writing the code it asks for, and when you build the thing, delete every site that named it — the one that crashes and the prose that agreed with it. A capability whose crash you cannot find is a capability you must assume exists. **AND A FIX THAT RETIRES AN ARGUMENT FALSIFIES EVERY SITE WHERE THAT ARGUMENT WAS WRITTEN DOWN, SO ITS CODE DELTA IS NOT ITS SIZE.** This is the same rot arriving from the opposite direction: not a claim going stale as the tree moves, but a diff MAKING claims stale the instant it lands — and it is the failure mode a codebase gets MORE of the better it is at recording its reasoning, which is why it belongs here rather than nowhere. Measured: a root fix was relayed as "one line in `quickjs.c`", and it was — one line of CODE, which made FOUR landed prose sites false across THREE files, one of them another lane's, because the retired argument had been written into a bracket comment, a `DCHECKF` message and two header field docs by the people who had reasoned it out. Every one of those would have gone on instructing the next reader in a rule the tree no longer obeys. So before landing a fix, grep for the ARGUMENT it retires, not only the symbol it changes; rewrite each site to the rule that now holds rather than deleting it, since a reader who re-derives the retired reason will re-introduce it; and when someone hands you a root fix priced by its code delta, treat that price as a floor. A relay that says "one line" has measured the edit and not the diff. **AND THE CLAIM ALSO TRAVELS BY REFERENCE, WHICH PUTS IT WHERE NEITHER INSTRUMENT LOOKS.** Everything above is about a crash that names another FILE, and the cure is to grep that entry. What it does not reach is a crash — or a comment — that names a DOCUMENT as its authority on what is missing, and that is exactly where the residue of a FIXED incident survived: three components cite one section of a design note BY NAME as the standing statement of an absence, and that section still said this engine has exactly one custom-element registry long after the constructible one landed. Every C site had been repaired; the sentence they DEFER to had not, so the stale claim was re-imported into the tree by reference and all three files read as agreeing with it. It was invisible to both mechanisms at once — `citegen.mjs` read `.c`/`.h` and no `.md` at all, and a grep for the capability finds the code that HAS it while the prose denying it sits under a heading number nobody greps. THE AUDITOR HALF IS CLOSED AND THE GREP HALF NEVER WILL BE: a `.md` inside the audited tree is now read exactly like a C file, so a design note's own citations and quotations are checked against the standards' text like any other prose — but nothing mechanical can ask whether a document's CLAIM ABOUT THIS TREE is still true, which is the half this bullet is actually about. So **a `.md` that a C file cites by name is CODE for the purposes of this rule**: it is re-checked when the capability is built, it is deleted with the crash it agreed with, and a diff closing an absence is NOT FINISHED while any document the tree points at still describes it. The tell is the pointer itself — wherever a comment or a crash says "see §X of \<doc\>", that document holds a claim about THIS TREE, and nothing mechanical will ever tell you it has gone stale.
- **A FINDING RELAYED FROM ONE AGENT TO ANOTHER SAYS WHERE TO LOOK AND NEVER WHAT IS THERE, AND IT MUST ARRIVE SAYING SO.** The rule above is about a claim a CRASH makes; this is the same claim travelling by hand, and it is more dangerous for one reason — a `DFAIL` at least sits in the file it is wrong about, while a relayed finding arrives detached from its evidence, wearing the authority of whoever passed it on and none of the reading that produced it. The receiver then builds on a summary of a summary. Measured, in one session, on findings relayed between lanes that had each done real work: a citation described as RENUMBERED had never been right in any edition (so there was no old number to restore); a set called "nine interfaces" was nine call sites and TEN interfaces; a member called a step-machine accessor was a plain C getter, which inverted what the fix had to be; a claim that the SET and HAS paths were reachable was false for those receivers; a co-occurrence offered as a lead was DISJOINT BY CONSTRUCTION, since one abort per spawned process means two signatures cannot share a run; and a two-branch framing ("either the audit over-charges or the chain is unbuilt") had BOTH its premises wrong. Every one was caught, and every one was caught the same way — because the receiving brief said to verify it. **SO THE RELAY IS WORTH MAKING AND THE LABEL IS WHAT MAKES IT SAFE**: pass the finding, name who found it, quote it rather than paraphrasing it, and say plainly that it is a claim to be checked — then the receiver's first act is to re-derive it, and a wrong relay costs one reading instead of one wrong diff. **AND WHEN THE RECEIVER REPORTS BACK THAT THE RELAY WAS WRONG, THAT IS THE MECHANISM WORKING, NOT A LANE BEING DIFFICULT** — record the correction where the original claim was made, because the next reader of that file is the one who will otherwise repeat it. **AND STATE A RELAY AT THE STRENGTH YOU ACTUALLY VERIFIED IT, BECAUSE AN OVER-CLAIM IS REFUTABLE IN A WAY THAT DISCARDS THE TRUE PART WITH THE FALSE.** A relay carrying "never", "only", "none" or "no such" invites the receiver to do the one cheap thing — grep for a counterexample — and ONE hit ends the reading. The finding then dies of a clause nobody needed: measured, a relay said a tool "never touches `m.arguments`", the receiver grepped, found exactly ONE read, and the receiver itself wrote that anyone doing that "would have found a hit and disbelieved the whole relay" — while the substance (the tool audits nothing about what a member ACCEPTS, so 903 dictionaries and every argument list are invisible to it) was entirely true and was what mattered. An absolute is a promise about everything you did not look at, so it is the one part of a relay you are least entitled to make. Say what you READ and where you read it — "the collection loop tests four kinds and dictionary is not among them" survives a counterexample elsewhere in the file, and "it never touches X" does not.
- **THE INDEX IS SHARED, SO `git add` IS A PUBLICATION AND STAGING MUST BE ATOMIC WITH COMMITTING.** A shared checkout means `git commit` sweeps whatever is in the index, including another agent's `git add` that landed between your edit and your commit. `git add <explicit paths>` does not protect you. When a file holds your hunk AND someone else's work in progress, stage the hunk (`git diff -- <file>` → keep yours → `git apply --cached`), never the file. **AND THE SUBMODULE IS THE SAME SHARED CHECKOUT, WHICH IS WHERE THIS RULE GETS READ AS SATISFIED WHILE BEING BROKEN.** `git commit -- quickjs.c quickjs.h` inside `engine/qjs` FEELS like the disciplined form — a different repository, a named pathspec, a message about the lanes you know are there — and it sweeps a third lane's uncommitted ABI change into a commit that does not mention it, exactly as `git commit -- <paths>` does upstairs. There is one working tree; a nested `.git` does not partition it. So the pathspec is never the protection: the protection is that the CONTENT you commit is content you filtered, and a file two agents are editing gets `git diff -- <file>` → keep yours → `git apply --cached`, in the submodule as in the parent. **AND A SUBMODULE COMMIT IS NOT A HALF-LANDING YOU CAN TAKE ALONE.** Pushing the submodule while the superproject's gitlink stays put looks like a safe way to preserve at-risk work, and it is — until the swept-in hunk was an ABI change, at which point the gitlink bump can only be committed together with the host hunks that call the new signature, and the "safe" partial landing has silently created a diff that must not be split. **`git commit --only -- <paths>` and `git commit -F - -- <paths>` are the same trap wearing a pathspec: they take WORKING-TREE content for those paths, not the index**, so a path you verified is not the content you commit. EIGHT sweeps happened in one session, and two of them defeat the older form of this rule, which said verifying `git diff --cached` immediately before committing was enough: (a) an agent DID verify immediately before, and the index still changed between that command and `git commit` — two commands are not atomic; (b) an agent staged its hunks and kept working while it waited on a build, and a different agent's commit published them under a message about something else entirely — the whole cold tier landed inside a commit titled for @S reproduction envelopes. So the rule is not "verify late", it is **stage and commit as ONE uninterrupted operation, or do not stage at all**: hold your work in the working tree, and when you are ready, `git apply --cached` your filtered hunks and `git commit` with nothing in between. **AND THAT PROCEDURE IS NOT ATOMIC EITHER — IT IS TWO COMMANDS, AND THE RACE HAS BEEN LOST BETWEEN THEM, SO THE COMMIT IS VERIFIED AFTER IT IS MADE.** A lane followed this rule exactly and a peer's `git add` replaced the shared index between its `git apply --cached` and its `git commit`; the commit that resulted carried ITS MESSAGE over ANOTHER LANE'S ENTIRE DIFF, and neither lane's work was lost or corrupted — only the message described the wrong change. There is no spelling of these two steps that closes the window, because git offers no way to name the tree and the message in one operation that this file has not already banned for deleting the repository. So the closure is not a better command, it is a CHECK: after committing, read what you actually committed — **BY THE SHA `git commit` RETURNED, NEVER BY `HEAD`** — and confirm it is your change (`git show --stat <sha>`, and the hunks if the file list surprises you). **NAMING `HEAD` RE-INTRODUCES THE EXACT RACE THE CHECK EXISTS TO CLOSE, ONE COMMAND LATER, AND IN THE DIRECTION THAT IS HARDEST TO DISBELIEVE.** `HEAD` is a MOVING REFERENCE in a shared checkout, so a post-commit read that names it asks about whatever the ref points at NOW rather than about the commit you just made — which is an ordinal over a set other lanes mutate, the §THE-FILTER-ITSELF-HAS-AN-ORDINAL defect arriving in the verification step instead of in the staging step. The commit `git commit` reports is IMMUTABLE and is the only name that still means your commit after a peer commits. Measured: a lane's post-commit `git show --stat HEAD` showed NINE unrelated files under its message and it read that as a catastrophic index sweep; nothing had swept anything — HEAD had simply moved to a peer's commit between the two commands, and the lane was reading a stranger's commit through a ref it had assumed was its own. **THE FALSE-ALARM DIRECTION IS THE DANGEROUS ONE**, because this file's prescribed response to a sweep is to push it as it stands and state the mis-attribution, so a false positive spends a report on an incident that did not happen — and its neighbour, a peer's commit that happens to LOOK like yours, is a false negative that certifies a commit nobody read. **WHEN IT IS NOT, THE ANSWER IS NEVER AN AMEND OR A REVERT** — a swept-in diff that is COHERENT and whole-landed is pushed as it stands, because reverting it destroys a peer's work and amending it rewrites history under them; state the mis-attribution in the next commit's message and in the report. What must be checked before pushing is not authorship but COHERENCE: a cross-boundary diff that arrived half-staged is the one case that must not go out, and that is a question about the content, which you can answer, rather than about who wrote it, which you cannot. A `git add` you leave sitting is not a private note, it is an offer. **Never rewrite pushed history to fix attribution** — an amend or a revert-and-recommit under other agents is strictly worse than a commit whose message under-describes it; state the mis-attribution in the report instead, and rely on the code carrying its own explanation at every site. **AND THE FILTER ITSELF HAS AN ORDINAL IN IT, WHICH IS THE LAST PLACE THIS DEFECT HIDES.** Everything above is about WHEN you stage; this is about HOW you choose, and it defeats the discipline while looking like it. A filtered stage picks hunks out of a diff, and the obvious way to name one is its POSITION — the third hunk, the one at line 2635. But a hunk index is an ORDINAL OVER A SET OTHER LANES MUTATE, so it is §AN-INDEX-NAMES-A-THING-ONLY-WHILE-THE-SET-IS-FIXED wearing a patch: a peer's edit landing between the `git diff` you read and the `git diff` you filter renumbers every hunk after theirs, and your carefully-filtered patch then stages THEIR hunk under YOUR message. It is quiet in the usual way — the patch applies, the commit succeeds, the file list looks right, and only the CONTENT is wrong. Measured twice in one session, independently: one lane's positional pick took a peer's `#include` into its commit when a file was edited between its hunk listing and its hunk selection, and a second reported "hunk selection by line number failed twice" and switched to content markers on its own. So a filtered stage selects by CONTENT — a distinctive string from the hunk you wrote — never by position, and the post-commit read stays mandatory because content matching is not proof either. The tell that you are about to do this: you are about to write a number that refers to a diff you produced in a DIFFERENT command than the one you are about to run.
- **THE WORKING TREE IS SHARED STATE TOO, SO `git reset --hard`, `git checkout -- <paths>`, `git stash` AND `git clean` ARE BANNED — they destroy other agents' uncommitted work with NO record and NO recovery.** The staging rule above is only the WRITE side: it says an index entry is a publication. This is the READ side, and it is the half that keeps being learned the expensive way — THREE separate lanes lost complete diffs to one `reset --hard` in a single session, one of them a nine-file change and another a large threat-model rewrite, and the lane that ran it was tidying its OWN state and could not see whose work it was taking. That is the asymmetry that makes this a rule rather than a caution: the operation is local and ordinary in a private checkout, and in a shared one its blast radius is invisible from the command line. Nothing in git records it — there is no reflog entry for a working-tree file that was never committed, so the loss is discovered by the victim, later, as an absence. **THE COROLLARY IS THAT HOLDING WORK IN THE WORKING TREE IS NOT SAFE EITHER, and the two halves of that are not in tension — they are the same fact.** Staging early offers your hunks to the next commit; leaving them unstaged offers them to the next checkout. The resolution is not to pick a safer place to wait, it is NOT TO WAIT: reach a committable state and commit it, in one uninterrupted operation, rather than accumulating a large diff that any peer's ordinary command can erase. A diff you cannot land yet is one to make smaller, never one to park. If a peer's state genuinely must be restored, that is a conversation with the agent that owns it, never a command that silently answers for them.
- **AND THE ONE FILE `git diff origin/main` CANNOT SEE IS THE GITLINK, SO THE STALE CHECKOUT ABOVE HAS A FORM WHOSE PRESCRIBED REMEDY IS BLIND TO IT.** The rule above ends in an instrument — confirm `git diff origin/main -- <path>` holds only your hunks — and that instrument answers about FILE CONTENT. A submodule is not content in the superproject; it is a recorded COMMIT ID, and when the working checkout of `engine/qjs` sits at an older commit than the one `origin/main` records, `git diff origin/main -- engine/qjs` is **SILENT**. Not quiet-because-clean: silent about a difference that exists. A commit made from that state moves the gitlink BACKWARD, and a backward gitlink is not a no-op — it REVERTS every submodule commit between the two, under a message about something else, which is the shared-index sweep arriving through a pointer instead of through a file. Measured: a lane's checkout was one commit stale, its first parent commit would have reverted a peer's landed citation fix, and the diff-against-`origin/main` check that CLAUDE.md prescribes reported nothing wrong. It was caught only by the OTHER rule — reading `git show --stat HEAD` AFTER committing — which is the second time that post-commit read has been the thing that worked when a pre-commit check could not. So: **the gitlink is verified by reading the ID, never by diffing the path.** `git rev-parse origin/main:engine/qjs` against `git -C engine/qjs rev-parse HEAD` before you commit, and `git show HEAD -- engine/qjs` after — and if the two commits differ, establish which is an ANCESTOR of which, because behind and ahead look identical in a pointer and only one of them is yours to move.
- **A CROSS-BOUNDARY DIFF IS ALREADY HALF-DEPLOYED THE MOMENT IT IS WRITTEN, SO AN UNLANDED ONE IS NOT NEUTRAL STATE — IT IS THE WORST OF THE THREE STATES, AND WAITING IS CHOOSING IT.** The rule above says an unstaged diff is exposed to the next checkout; this is the sharper half, and it is about the TREE BEING A RUNNING SYSTEM rather than a pile of pending work. The two zones do not go live at the same instant: the trusted zone's JavaScript is INTERPRETED FROM THE TREE, so an edit to it is deployed on WRITE, while the engine's C is live only after somebody builds. A change that spans the seam therefore deploys ITSELF ASYMMETRICALLY — the JS half starts speaking a protocol the shipped WASM does not implement, on a field the engine does not yet state, and the very DCHECK the diff added to make the contract explicit is what fires, in the half that IS live, naming a contract the half that is NOT live would have satisfied. Whole-unlanded and whole-landed are both coherent; the state in between is the one where the product does not run and the assert points away from the cause. **SO THE QUESTION IS NOT WHO OWNS IT, IT IS WHICH HALF IS LIVE ON WRITE** — ask that at every change touching both zones, and land the two halves together or not at all. When the author does not come back, the diff is READ, VERIFIED and LANDED by whoever is standing there, with the attribution stated in the message: history is never rewritten to fix attribution, and the tree is never reverted to "restore" cleanliness, which is the banned destroy wearing a tidy-up. **AND ASKING PERMISSION IS NOT AN EXEMPTION.** A question whose answer does not change what a careful engineer would do is deferral with a question mark on it, and every turn it is asked the half-deployed state persists — the escalation that is worth making is the one about INTENT, never the one about risk this file has already decided.
- **WORKTREES AND PRIVATE INDEXES ARE BANNED, AND THE PROCEDURE THAT USED THEM DELETED THE REPOSITORY.** Work happens in the ONE checkout. The frozen-worktree-plus-`hash-object`/`update-index`/`commit-tree` landing this file used to prescribe is gone, because it had a trapdoor nobody could see: `GIT_INDEX_FILE` named with `$$` is a DIFFERENT PATH IN EVERY SHELL, and each tool call is a separate shell — so staging wrote one index and `git write-tree` read another, ABSENT one. **`git write-tree` on an absent index does not fail; it returns the EMPTY TREE `4b825dc6`**, and `commit-tree` commits it. That is exactly what happened: one commit deleted EVERY FILE IN THE REPOSITORY on BOTH refs, and it was reported as landed and verified. Use ordinary `git add <explicit paths>` and `git commit` — never `git add -A` or `git add .`, which sweep whatever else is in a shared tree — and check `git status` before committing so another agent's work in progress is not swept into your message.
- **AND IT IS NOT WHERE WORK IS READ EITHER, BECAUSE NOBODY CHECKS IT OUT — SO IT IS ALWAYS STALE AND `git diff HEAD` IS SILENT ABOUT IT.** The rule above closes the write; the read is the half that keeps landing. Every lane lands through a private index and nothing advances the shared HEAD, so that HEAD sits dozens of commits behind `origin/main` and every file under it is a version that was true once. The tell is MECHANICAL and it is the reverse of the usual one: `git status` and `git diff HEAD` are QUIET or report a file as merely "modified", while `git diff origin/main` is loud — because the tree is BEHIND, not ahead, and a diff against the wrong base cannot tell those apart. Three measured this session: an agent's `git ls-files` called two committed files untracked and it nearly reported a lane's landed commit as one that does not compile; a lane's working copy of `test_forced.c` was stale by two other lanes' commits, so `git diff origin/main` showed **−48 lines** and staging it would have reverted both under a message about ECMAScript §12 — and that lane wrote down that `git diff HEAD` would have shown nothing wrong at all; and a stop-hook reported "uncommitted changes" every turn for files whose blobs were byte-identical to landed commits. **DIFF AGAINST `origin/main`, NEVER AGAINST `HEAD`**, and before hashing any shared-tree file confirm `git diff origin/main -- <file>` contains ONLY your hunks. Before believing a shared-tree file at all — a grep, a line number, a "this function does not exist" — READ IT AT `origin/main` (`git show origin/main:<path>`), because a claim about the tree derived from a stale checkout is a claim about a program no revision contains. And a file that differs from `origin/main` is not therefore unlanded: check whether its blob equals some landed commit's (`git rev-list origin/main -- <path>` and compare `git hash-object`), because stale-behind and work-ahead look identical in `git status` and only one of them is yours to save.
- **VERIFY A PUSH BY CONTENT, NEVER BY POINTER.** `git ls-remote` confirms a SHA, and a SHA says nothing whatever about a tree — the empty-tree commit above PASSED an `ls-remote` check and was reported as proof. After pushing, read the tree: `git ls-tree -r <sha> --name-only | wc -l` against the count you expect, and confirm the blobs you changed are actually present at that sha. The same rule holds before committing: a `git diff-index --cached` run in one shell says nothing about what a `write-tree` in the next shell will see.
- **Do subproblems IN ORDER** — never jump to a problem before its subproblems. If a shortcut was taken, remove that code.
- **Aggressively delete non-perfect code, riskiest first** — that shows you care how the system works; dead-code removal takes no risk and shows nothing. Delete anything a browser engineer or solver engineer would not fully endorse.
- **A LEGACY FALLBACK IS A `DFAIL`, NOT A REPORT.** Logic not designed for suspend/resume that still runs is an unbuilt capability, and the file already has the mechanism for that: it CRASHES at the site, naming what to build. Do not invent a register, a hit counter, or a harness line that lets the suite stay green while a non-suspending path keeps running — that is choosing a green result over the forcing function, and it is the same risk-avoidance as keeping the legacy body. The conversion sequence ends in the DFAIL: widen the selector, build what the failures name, DELETE the body, and the C entry becomes `DFAIL("… reached its C entry with an ITERABLE source — route that call site")`. If several directories go red at once because the fallback is still reached, that is the correct state and the work queue, not a reason to build a softer mechanism. A site that is a genuinely DIFFERENT algorithm (Array.from over an array-like: length+indices, no @@iterator) is not a fallback at all and must not be tracked as debt — mislabelling it manufactures an obligation to delete something that should stay.
- **A REJECTED OR INTERRUPTED TOOL CALL MAY HAVE ALREADY RUN — verify the tree, never assume.** A compound command (`git checkout … && gcc … && …`) can execute its first stage before the rejection lands. Twice this has destroyed committed-quality work whose loss was then REPORTED AS "the revert didn't happen" — a false claim about the state of the repo, which is worse than the lost work. After any rejection, interruption, or surprising result: `git status` / `git diff` / `grep` for the symbol you believe you changed, and state what the tree ACTUALLY contains. The same rule covers every "same place / already fixed / not a regression" claim — CHECK THE DIFF, never a snapshot of the current file, which shows where a line IS and proves nothing about where it WAS.
- **A PROCESS PATTERN MATCHES THE SHELL THAT NAMES IT, SO `pkill -f`/`pgrep -f` OVER A COMMAND STRING IS SELF-REFERENTIAL — ADDRESS A PROCESS BY PID.** The argument is the pattern, so the pattern is IN the argument list of the process doing the matching, and of every wrapper between it and the kernel. It has bitten in both directions in one session and the two failures look nothing alike, which is why one rule has to cover both: a `pkill -f` took out ITS OWN compound command mid-sequence, loudly, leaving the tree in a state the caller then had to reconstruct under §A-REJECTED-OR-INTERRUPTED-TOOL-CALL; and an `until ! pgrep -f <cmd>` wait-loop matched its own shell and therefore NEVER FIRED, silently, so a job that had finished long before read as still running and the work waiting on it simply did not happen. The silent direction is the dangerous one, because a monitor that never fires is indistinguishable from a job that never ends, and the mistake is invisible in the output of the very command that embodies it. **THE DISCRIMINATOR IS TO LIST RATHER THAN TO MATCH** — `ps -eo pid,args | grep <pattern> | grep -v grep`, read the rows, and act on the PIDs you actually meant; a count from `pgrep -c` answers a question about a pattern and not about a job. This is the same defect as the loaded-machine one, moved into the tool: an artifact of HOW you asked, reported as a fact about WHAT you asked.
- **AN EXIT STATUS BELONGS TO THE PROCESS THAT PRODUCED IT, AND BACKGROUNDING INSERTS A PROCESS — SO A COMPLETION NOTICE FOR A BACKGROUNDED JOB IS A STATEMENT ABOUT THE WRAPPER.** The rule above is about ADDRESSING the wrong process; this is about BELIEVING one, and it is the same family as verifying a push by pointer: a proxy answered, the answer was well-formed, and it was about something else. A shell that backgrounds a job and prints its PID exits the instant it has done so, successfully, whatever the job goes on to do — so the harness reports the job "completed, exit code 0" while the job is still compiling, or has already exited 1. Measured: a build was launched that way, the wrapper's 0 was reported as the build's, and the build had in fact exited 1 on a missing toolchain seconds earlier — two processes, two statuses, and the one that got reported was the one that could not fail. **THE 0 IS THE DANGEROUS DIRECTION BECAUSE IT READS AS SUCCESS AND IS ALWAYS AVAILABLE**, and it does not stop at a wrong belief: acting on it started a SECOND concurrent build, which is precisely the state §Testing's one-builder rule exists to prevent, so a misread status manufactured the condition that rule is about. It also produces the emptiest possible artifact — a "successful" build that compiled nothing — and §MEASURE-WHAT-THE-SHIPPED-PATH-WRITES already says an absent result and a zero result are different facts that must never be averaged. **THE DISCRIMINATOR IS TO WAIT ON THE PID AND THEN READ THE JOB'S OWN ARTIFACT** — `while kill -0 <pid>; do …; done`, then the log it wrote and the file it was supposed to produce — never the status of the thing that launched it. A job's exit code is worth having; it is just never the one the launcher hands you.
- **PUSH BACK — sycophancy is a design failure, exactly like a defensive fallback.** Agreeing because something was asserted (by me, you, or the existing code) rather than because it is SPEC-TRUE is the same evil as swallowing a crash. When a claim conflicts with the spec (ECMAScript/WHATWG) or the real code, say so and prove it (`JSON.parse(location.hash)` throws `SyntaxError` in V8 — the honest answer, never a fabricated reason it doesn't). Deferring to authority over spec is a bug. Treat positive feedback as always-to-be-worked-on. Approximations are worthless. Avoid the word "genuinely" — it is a cop-out.
- **Own the push, AND PUSH TO BOTH REFS — a push to `main` alone is REVERSED by the next merge of the session branch.** Commit + push VERIFIED work yourself, to `main` AND to the session's designated branch (`claude/…`), every time. They are ONE line of history, not a trunk and a fork: the session branch is where the work is reviewed and merged FROM, so a `main` that is ahead of it is a `main` whose extra commits the next merge silently undoes. This is not hypothetical and it is not small — the session branch sat 280 commits behind `main` with ZERO commits of its own, so every landing of an entire session existed only on the ref nobody merges. It was a strict ancestor, which is the ONLY reason it cost a fast-forward instead of a reconstruction. **VERIFY BOTH REFS AFTER PUSHING** (`git log --oneline -1 origin/main` and the same for the session branch); a push that reports success for one ref proves nothing about the other, and the two-ref state is exactly what nobody thinks to look at. Before starting subagents, SYNC FIRST and confirm both refs agree — several agents committing onto a ref that is already behind multiplies the divergence by the number of agents. Engine = a clean quickjs-ng-delta fork (submodule `engine/qjs`, branch `apiclient-v2`, synced to upstream `quickjs-ng/quickjs`); the host/scheduler lives OUTSIDE the submodule (`engine/host/main.c`) to keep the fork a minimal delta. Build: `node engine/build.mjs`.

# Offensive programming — the mechanism is `engine/host/check.h` (mirrored on the JS side by `extension/check.js`)
Always safe to ship DCHECKS! If crashing thats a blocking issue to support properly. Pre-existing flaws must be fixed when order is right.
- **Every error/crash/abort in a DEV build is CORRECT, never softened.** It is exactly one of: (1) an UNEXPECTED STATE — an invariant the design must guarantee, eliminated at the ROOT so it cannot arise; or (2) a FEATURE THAT SHOULD EXIST but does not yet — BUILT at the root as a proper system. NEVER caught / swallowed / logged-and-continued / clamped / `?:`-past, never wrapped in try/catch for "browser-faithfulness". A crash is the system doing its job (forcing the root fix). A page's own uncaught throw aborting boot is INTENTIONAL — the engine has not yet faithfully implemented that capability; build it at the root. In release we cannot fix or add features, so the same error is ALSO correct (it fails because the capability isn't supportable outside dev); the release exemption never licenses a dev-mode fallback.
- **`DCHECK(cond,msg)` / `DFAIL(msg)`** = DEV-ONLY should-never-happen (design invariant, not-yet-built capability, COW-host gap). Aborts loud at the origin emitting `@WHY` with cond+file:line; compiled out in release (`-DAPICLIENT_DEV=0`) — condition MUST be side-effect-free, never recoverable control flow. Asserts "the engine's OWN logic is correct."
- **`CHECK(cond,msg)` / `CHECK_FAIL(msg)`** = ALWAYS fatal (dev AND release, emits `@E`) for a universal invariant that must hold in production: OOM/allocation (a dropped flow corrupts the frontier), a physical RAM/disk floor, a security/authorization boundary, data integrity. Asserts "we must not PROCEED even in production." When unsure, it is a DCHECK. **BUT A DIFF THAT MAKES A DCHECKED POINTER LOAD-BEARING IN RELEASE HAS SILENTLY PROMOTED THAT DCHECK, AND FAILING TO FOLLOW IT TRADES A DEV ABORT FOR A RELEASE SEGFAULT.** The choice above is made once, against the invariant as it stands; this is the obligation a LATER diff creates, and it is invisible because the assert reads unchanged while the code beneath it does not. The trigger is mechanical: a DCHECK guards a pointer, the pointer is dereferenced only on dev-only paths, and your diff adds the FIRST release-mode dereference of it. The check is then compiled out in exactly the build where the dereference now happens — the guard and the thing it guards have been separated by the edit rather than by anybody's decision. Measured: a rung write added at a delivery seam became the first release dereference of a flow pointer a `DCHECK(f != NULL)` had been covering, and was upgraded to a `CHECK` in the same diff. So when you add a dereference, ask which build the guard above it survives in — and if the answer changed because of your line, the promotion is part of your line.
- **Assert EVERY invariant EAGERLY at its origin; too FEW asserts is the failure.** A bad state caught late is a bug you built on; caught where born it is a fix. Never a `?:`/`if(bad)return`/clamp/default past a broken invariant; never a try/catch that swallows one. Migrate every raw `abort()`/hand-rolled `@E`/`@WHY`/`assert` to the right macro. The goal is ZERO `@WHY`, reached by fixing the root — never by muting the check. DCHECKs are always safe to ship (no production effect). NOT a `@WHY` (do not assert these): a forced-exec flow THROWING on opaque/attacker input, and an unsolved `@S` sink (a parked search) — those are the exploration surface, not broken invariants. Learnings from a non-best design are worthless — known-incomplete logic is still a should-never-happen DCHECK. **AND THE DISCRIMINATOR THAT DECIDES THIS IS WHOSE BYTES STATE THE VALUE, WHICH IS A QUESTION ABOUT EVERY ZONE AND NOT ONLY THE ENGINE'S.** A `DCHECK` asserts "this codebase's OWN logic is correct", so it may only ever stand on a value THIS CODEBASE COMPUTED; a value a stranger's server stated is not an invariant that can be violated, it is INPUT, and the answer to a malformed one is a REFUSAL yielding the record's declared absence — never an assert, and never a default that turns the absence into a plausible datum. The two failure directions are not symmetric and both are live: asserting on foreign bytes hands a remote party an abort switch for the TRUSTED zone, while defaulting past them is §A-FIELD-A-CONSUMER-DEFAULTS. Measured, in the trusted zone rather than the engine: a target's own error reply — a `google.rpc.Status` this project never produced — reached a store record whose shape check is a `DCHECK`, so `{"metadata":{"service":7}}` from any third party fired OUR assertion mechanism and aborted the zone that holds the network policy; alongside it, a `(constructor)` where a proto type belongs made the parsed `type` the `Object` CONSTRUCTOR, which `structuredClone` refuses, so ONE probe answer poisoned the store and stopped every popup open for that profile. Neither is a field-name contract, so the record-field gate is structurally blind to both — its own banner says a zero over a boundary with no producer in the corpus is "silent about that boundary, not clean about it". So: at every boundary, ask who authored the bytes; refuse what a stranger stated, assert only what you computed, and where an assert guards a value YOU wrote, assert its TYPE and not its content — a path this codebase composes is legitimately empty, and demanding non-empty re-introduces the remote abort switch one field over.
- **AN ASSERT THAT NAMES A REMEDY BUT NOT A SITE IS A CRASH NOBODY CAN ACT ON, AND A SHARED HELPER IS WHERE THE SITE GOES MISSING.** A DCHECK stamps the file and line it is WRITTEN at, so an invariant checked INSIDE a helper reports the helper for every caller — one line for every transition in a file, one line for every read in a tree — and the message's remedy ("route this read", "route this call") then names an action with no object. **THE REASON THIS SURVIVES IS THAT THE CRASH READS AS COMPLETE**: it states a correct spec fact and a correct instruction, and only when someone tries to obey it do they discover there is nowhere to apply it. That is the stale-`DFAIL` failure mode with the coordinates missing instead of wrong, and it is worse in one way — a wrong file sends you to the wrong place, where you at least find out; no file sends you to read hundreds of call sites, which nobody does, so the crash is rediscovered instead of fixed. It has been rediscovered four times here, at two scales: a coercion and a property read each reachable from a thousand-odd C callers, and, one level down in the same session, two transition helpers whose six and three callers shared one reported line. Every cure was identical and every discovery was independent. **SO THE SITE TRAVELS WITH THE OPERATION** — a `__FILE__`/`__LINE__` pair captured at the CALLER and threaded to the check, never derived at the helper, and never captured at an intermediate that would name one forwarding function for the whole tree. **AND AN INVARIANT OVER A TRANSITION IS A MACRO EXPANDED AT EACH SITE, NEVER A FUNCTION CALLED FROM THEM**; a wrapper introduced to "share the check" re-creates the defect it was reaching for. Internal callers pass a NAMED sentinel rather than a null, so a caller that was never converted cannot masquerade as one that has nothing to say. The tell is mechanical and worth asking before writing any should-never-happen: **count the call sites that can reach this abort — if that number is larger than you would read by hand, the ADDRESS is part of the assert, not decoration on it.**
- **Confident change = small components × two-sided asserts** — ONE system, not two. An isolation-testable component is a narrow interface you exercise with ONE fixture AND whose invariants crash loud when violated. Without the asserts it silently corrupts; without the boundary the asserts have no contract. Split every over-large file until each piece is one assertable contract; give each component its own DCHECKs. Metric: can you exercise this with one fixture AND does a violated assumption crash at its origin?
- **A FIELD A CONSUMER DEFAULTS IS A FIELD NOBODY WILL NOTICE IS NEVER WRITTEN, and the default is not the symptom — it is the concealment.** `x || 0`, `x || []`, `x || {}`, `x ?? d`, `x?.y`, a `catch {}` around a read, an `if (kind === N)` on a value the producer never returns: each turns "the producer does not produce this" into a plausible datum, and a plausible datum is indistinguishable from a measurement. SEVEN instances surfaced in ONE session, every one a live product defect and not one of them visible as a crash. `qjs_result` had NO CALLER and `result || {}` made that `{success:true}` with zero endpoints — a false clean bill from a run that learned nothing. `bridge.js` branched on `st === 1` for NEED_FETCH while `qjs_step` returns only DONE(0)/YIELD(2), so the whole `qjs_pending → safeFetch → qjs_provide` reply path was UNREACHABLE in the shipped extension and every flow a page's `fetch()` parked stayed parked forever — §Attacker-sources calls learning from replies "the POINT", and it had never once happened. The popup read `cspBlocked` where `solve.c` emits `cspBlocks`, so EVERY finding badged HIGH and a breakout real Chrome's CSP kills was reported as a clean XSS. `canVerify` required a `shape` field carrying a `{hash}` vocabulary the engine has never spoken, so live verify rendered for ZERO findings ever emitted. `resolverErrors || []` dropped every engine-recorded page error (`pageErrors`). `_orphans`/`_work`/`_parked || 0` were three names nothing emits, so the interleave diagnostic read zero forever. `@RESUMED` had a reader and no writer, so the number written to prove the cold tier read its residue back was `0` for every session there has ever been. **THE TELL IS GREPPABLE AND THE RULE IS MECHANICAL: a name that is READ somewhere and WRITTEN nowhere is a broken contract, and a default is what stops it being a crash.** So a consumer NEVER defaults a producer's field — it DCHECKs the field's presence and shape (`extension/check.js` mirrors `check.h` for the JS side), and a value the producer can legitimately omit is a POSITIVE statement the consumer reads as one (absence of `cspBlocks` IS `policy_allows` returning true), never a hole a `||` fills. When you add a reader, grep for its writer; when you rename a field, the old name must not survive on either side. **AND THE TWO HALVES CAN CONCEAL EACH OTHER, WHICH MAKES REPAIRING EITHER ONE ALONE A REGRESSION RATHER THAN A PARTIAL FIX.** The rule above treats read-with-no-writer and write-with-no-reader as two defects; they can be ONE, and the pair is invisible in a way neither half is. Measured: a lookup composed its key in a shape the only mint never produced, so the arm behind it could not run — and that arm's body wrote a field whose name occurs EXACTLY ONCE in the whole tree, at that write, with no reader anywhere and a record constructor that REJECTS it by name. Each half made the other unfalsifiable: the field was never read because the writer never fired, and the writer never firing went unnoticed because nothing downstream missed the field. **Repairing the key alone would have begun writing a constructor-forbidden name onto live records that the persistence layer carries into IndexedDB** — a regression delivered as a fix, and one that outlives the session that shipped it. So a dead path raises a SECOND question before it is revived: what would it have done had it run? A path nobody has executed is not working code, it is untested code, and reviving it is a behavior change owed the same scrutiny as writing it. The tell is cheap — grep every name the dead arm WRITES, not only the one that made it dead.
- **A PREDICATE THAT ANSWERS TWO QUESTIONS IS DECIDED BY THE STRICTER ONE, AND THE COST LANDS SILENTLY ON THE OTHER.** Two facts about one thing get ONE bit because at the site that introduced it they agreed; later a case arrives where they DIFFER, the bit keeps whatever the stricter question needs, and the looser question is refused with nothing anywhere to say it was ever asked. This is the defaulted-field defect with no field in it: the refusal is a real answer to a real question, so it reads as correctness rather than as loss, and no name is missing for a grep to find. **THE TELL IS A REFUSAL WHOSE STATED REASON IS ABOUT A DIFFERENT QUESTION THAN THE CALLER'S** — an exclusion justified by "X states its own extent, so a member it lacks is not unknown" standing at a site asking "may the walk descend through X and NAME what is inside it", which are not the same question and do not have the same answer. So when a predicate refuses, read its reason against the CALLER's question, and where they are two questions, split them into two predicates over the ONE bit: the bit is a FACT and each predicate is a QUESTION asked of it, which is also what stops the split becoming two bits that can disagree. Measured: a server's injected state is records inside LISTS, and one membership bit meant every record inside a list was unreachable and answered `undefined` — while the bit that would have named it was already set on it.

# Architecture — the C engine IS the browser; JS is only the irreducible platform edge
- **Lexbor (DOM) + quickjs (JS) in C own ALL semantics** — DOM parse, JS exec, forced-exec scheduler, endpoint/`@S` detection, document identity (bundle id via a real Lexbor `<script>` scan, never a JS regex), frontier logic, moat aggregation — used directly like a real renderer, isolated per document/flow (COW). A JS orchestration layer is unwanted context-switching across the JS↔WASM boundary; DELETE it. The ONLY irreducible JS is a BRIDGE (never logic), dictated by SECURITY.md: the untrusted WASM bundle cannot fetch (all network via the trusted `safeFetch` chokepoint), cannot touch IndexedDB/`chrome.*`, cannot paint the popup. So JS is: relay safeFetch/IDB/chrome to host-edges, load the WASM, render the popup. WORKING JS IS NOT MOVED INTO C ON THIS RULE'S SAY-SO. A migration mandate here is what produced a session of untested C replacing JavaScript that worked: content-type sniffing taken out of `safeFetch` — which SECURITY.md assigns the CORB gate to by name — and an asset classifier taken out of `discovery.js`, neither of which any flow needed, both landing in C whose first build found four undeclared globals and whose parser bugs that week were two arenas handing out each other's memory. TYPE SNIFFING STAYS IN JAVASCRIPT, in `safeFetch`, where SECURITY.md puts it. What legitimately lives in the engine is what a FLOW needs mid-execution — a parser or decoder the engine runs while executing a page, whose answer must differ per forked arm and must park and resume with the flow, which JS cannot do because it is outside the COW delta. Anything the trusted zone computes once, before or between flows, stays where the failure mode is a wrong answer rather than a corrupted heap. **AND THERE IS NO LIST OF WHICH-JS-IS-WHICH — a per-file ledger of "when does this file become C?" is BANNED.** Such a gate is the migration mandate's enforcement arm outliving the mandate: prose can be re-read, a red gate is an instruction the next reader obeys. Rewriting one to report-instead-of-fail is still the wrong artifact — a ledger classifying files against a boundary that no longer moves is a map of a settled question, and it goes out whole rather than being kept accurate. What survives is the TEST in the sentence above, applied per change, at the change. Every retained bridge edge gets a DCHECK on the engine↔JS contract (a null/malformed engine result crashes in dev, never an `if(!x)return`).
- **Use browser / JS-engine developers' concepts and names — never coin a system when an established one exists.** `DCHECK`/`CHECK` are right because they ARE Chromium's `base/check.h`. Inspect values/heap/leaks with quickjs's existing dump infra (`JS_DumpValue`, `JS_DumpGCObject`, `JS_DUMP_*`, the `-d`/`ENABLE_DUMPS` path) and V8-style native-syntax debug intrinsics — never a bespoke page-global tool (fingerprintable, duplicative). **THE DCHECKs ARE THE GATE.** The engine asserts its own invariants at their origin and aborts loud where a capability is missing, so a change is verified by whether the asserts stay silent — not by a suite going green. `node engine/build.mjs cow` is too slow to run as a check; test262 under `FORK_PREEMPT=1` is how you EXERCISE code so the asserts get a chance to fire (and its `gc_obj_list` walk counts a leaked GC object as a failure), never the thing that certifies the change. An assert that fires names the exact unbuilt mechanism — that is the signal to build it, and a passing suite with a silent assert proves nothing it did not exercise. A memory bug (UAF/double-free/refcount/leak) is found by READING the ownership contract at the site that breaks it, then asserting it: a struct copied field-by-field must dup EVERY owned field, so adding a field creates an obligation at every clone/free/finish site — a DCHECK at the clone is what makes that impossible to miss, not a sanitizer run after the fact. Inspect with the existing dump infra (`JS_DumpValue`, `JS_DumpGCObject`, `JS_DUMP_*`) and gdb. A `printf`/marker probe is BANNED — it perturbs a timing-sensitive bug and reinvents existing infra. Use targeted Asan for memory crashes.
- **Don't code browser features in JavaScript.** Browser features are C engine components. (This is why continuation-holding builtins are HOOKED into the flow machinery, not re-hosted in JS — see §C-stack.)

# Browser half — a SOLVED problem: follow the spec, build like a browser
- **The project in one sentence: a browser with a BFS time-travel solver. Two halves, never blurred.** The browser half must look, behave, and be BUILT exactly like a browser — every semantic traces to a SPEC (WHATWG percent-encode sets, HTML5 tree-construction insertion modes, ECMAScript, CSP, Trusted Types, mXSS re-serialization), implemented as a COMPONENT (`location.c`, `domparser.c`, `dom_element.c`, Lexbor parse, quickjs exec) with a DCHECK asserting the spec invariant. **THE SECTION NUMBER IS PART OF THE CITATION — "per HTML" is not a citation, `HTML §13.2.5.43` is.** A named spec with no number cannot be looked up, so it cannot be checked, so it is indistinguishable from a recollection; the number is what makes the claim falsifiable by the next reader, which is the whole value of tracing to a spec at all. **AND A CITED NUMBER CARRIES AN OBLIGATION TO BE RIGHT — a wrong one is WORSE than none**, because it reads as authoritative and sends the reader to a section that does not say what the code claims. That is the stale-`DFAIL` failure mode with a spec behind it: true-sounding, unverified, and load-bearing. Numbers RENUMBER, so a citation names the section's TITLE beside its number (`HTML §13.2.5.43 comment start state`) — the title survives an edition the number does not, and a mismatch between the two is then visible instead of silent. VERIFY the number against the spec text before writing it, never from memory: `§13.2.5.41` was written here for "comment start state" minutes after this rule was set, and §13.2.5.41 is the BOGUS comment state. **THE OBLIGATION HAS AN INSTRUMENT AND IT IS `engine/citegen.mjs` — RUN IT ON WHAT YOU WRITE.** An obligation with no instrument named beside it is discharged by whoever happens to remember it, which is how a rule this file states twice still produced four wrong numbers in one session and one comment that was spec-WRONG and got acted on. It resolves each citation against a committed per-standard index and reports `UNKNOWN-SECTION` / `MISATTRIBUTED` / `TITLE-MISMATCH`; it does not fetch, so an upstream edition cannot redden the tree — only `--regen` reaches the network, and it prints `RENUMBERED §was → §now` per moved section. **ITS BLIND SPOTS ARE PART OF THE INSTRUCTION, because a checker trusted past its evidence is worse than none:** it indexes SECTIONS, never `<ol>` items, so a wrong STEP number is invisible to it (one file carried 110 citations, produced zero findings, and had a whole cluster off by one) — **AND THE OBVIOUS WAY TO COUNT STEPS BY HAND IS WRONG IN THE SAME DIRECTION, so the one check the tool cannot make is also the one a careless reader fails**: a spec's steps are TOP-LEVEL `<li>`s of one `<ol>`, and a step containing a nested `<ol>`/`<ul>`/`<dl>` is ONE step whose sub-items a flat `<li>` count silently promotes to peers. Measured: an algorithm whose real length is 36 counts as 39 that way, because four sub-items of one step are counted as four steps — so a crash citing step 36 reads as citing a step that does not exist, and the reflex is to "correct" a number that was right. TRACK LIST DEPTH when you count, and when a hand count disagrees with a citation, suspect the count first. **AND THE REASON THIS HAZARD SURVIVES THE RULE THAT NAMES IT: THE SHIFT STARTS ONE STEP LATER THAN ANYBODY CHECKS.** A nested list promotes its sub-items to peers only from the promoting step ONWARD, so every citation at or before it is still RIGHT — and a reader spot-checking a cluster reads the first number, finds it correct, and stops. Measured: four citations of one algorithm were all off by one in the same direction because step 2.3.2 holds a nested one-item list (`Assert: directory is a directory entry`), and **`2.3.2` itself was exactly right**; the drift began at 2.3.3 and ran to the end, including a printed stage label a park carries across a resume. So a cluster of sub-numbers is verified from its LAST member backwards, or by counting the whole list once with depth tracked — never by sampling, because sampling is biased toward the half that cannot be wrong. **AND DEPTH IS NOT ENOUGH, BECAUSE ONE STEP CAN HOLD SEVERAL SIBLING LISTS AND EACH RESTARTS AT 1** — a step written as a catching list, then "Then, perform the following steps, regardless…", then "Finally, if the above steps threw…", is ONE step containing THREE `<ol>`s, so a bare `10.2` names three different steps and the reader cannot tell which. That is worse than an off-by-one: an off-by-one is wrong and checkable, while an ambiguous sub-number is UNFALSIFIABLE — every candidate reading confirms it. So a sub-number is only ever written where the step holds exactly one list; where it holds several, the citation NAMES the list in the spec's own words (`§4.13.5 step 10's regardless-list`) and the convention is stated once at the algorithm's banner rather than re-derived at each site; once a citation states the section's own title nothing later can overturn it, so a correctly-numbered, correctly-titled claim about what the section SAYS is structurally unseeable — that is the one that must be read; **AND THE SHARPEST FORM OF THAT IS A QUOTATION, WHICH IS THE PART A READER TRUSTS MOST AND VERIFIES LEAST.** A quoted sentence beside a number is the strongest evidence a comment can offer — it appears to remove the need to open the spec at all — and for a long time it was checked by nothing: the number resolves, the title matches, and no instrument asked whether those words occur in that section. IT IS CHECKED NOW, ON EVERY RUN, AND THAT IS NOT A DETAIL OF THE TOOL BUT THE POINT OF THE RULE: `citegen.mjs` compares every quotation of six or more words against the cited section's own committed text, and it does so unconditionally rather than behind a flag, because a check reached by REMEMBERING it catches what it catches by luck — the CSSOM View fabrication below was caught only because one lane happened to pass the flag that day, and the same run turned up an older site making the identical false claim that nobody had passed it for. Measured: a site cited CSSOM §6.1.1 beside the quotation *"the disabled attribute … whether the style sheet is applied"*, and **that sentence appears nowhere in CSSOM**. A wrong number sends a reader to the wrong place, where they find out; a fabricated quotation tells them not to go. So a quotation is pasted from fetched text or it is not written, and when you verify a citation you verify its QUOTE first — the number is the cheap half and the one an instrument can already do for you. a standard with no committed index is COUNTED and never CHECKED, which is a silent zero rather than a clean bill; and a quotation that is REAL BUT CUT is VERIFIED, so a quote trimmed where the sentence turns — DOM §2.2's set-the-canceled-flag ends "and do nothing otherwise", and that clause IS the passive-listener guarantee — passes in silence, which is why the QUOTE you verify is the whole sentence and not the part that suits the comment. **AND A CITATION IS NOT ALWAYS A COMMENT — PROSE LIVES INSIDE CODE, SO A CITATION EDIT IS COMPILED LIKE ANY OTHER.** A spec number appears in comments AND in the string literals of every `DCHECK`/`DFAIL` message, and a mechanical edit — a `sed` over a section number, a rename of a term — cannot tell the two apart. Adding a TITLE to a citation is the dangerous shape, because a title is quoted: substituting `§2.2 Requests` with `§2.2.5 "Requests"` inside a message string closes the literal early and the rest tokenizes as a bare identifier, and the shared tree then does not compile for everyone until somebody notices. That is exactly how it happened, and the reason it got through is worth more than the incident: the edit FELT like documentation, so the compile check felt unnecessary. It is not — `clang -fsyntax-only` on every touched file is the same obligation for a citation diff as for a logic diff, and it is cheap enough that there is no case for skipping it. It is deliberately NOT a build gate: its finding count is a noise floor that would mute it, and a citation is prose, so a build that cannot land a spelling fix stops every lane. Real Chrome is CONFIRMATION, never the source of truth — the spec is. A browser-fidelity gap is always "implement the spec at the root," a bounded known-answer task. The browser half should be BORING and spec-locked; a surprise there is a fidelity bug.
- **ORDER and NARROW behavior ARE the spec, not details to approximate** — event-loop task/microtask ordering (Promise/`await` resumption), insertion-mode order, parse-then-execute script order, DOMContentLoaded-then-load; the per-component percent-encode SET, `<template>`/RCDATA/foreign-content parsing, `[[Get]]` frozen-property, `slice(1)` on the source's real leading char. The solver runs ON TOP of these, so a wrong order or fudged edge silently corrupts what it solves. Most "solver gaps" are really the browser behaving slightly wrong.
- **A PER-REALM FACT IS ANSWERED PER REALM, AND A MODULE-STATIC PROTOTYPE IS A WRONG ANSWER — not a wrong identity.** `js_call_c_function` does `ctx = p->u.cfunc.realm` (and `js_callee_realm` does it for every step machine), so a member installed ONCE answers every document's question with the DEFINING realm's `ctx` forever. That is not the pedantic half of §3.7 — it is how `window.locationbar.visible` reported every popup a tab (the root navigable is not a popup and the root is whose ctx arrived, and the 51 subtests split exactly along that line), and how a shared `EventTarget.prototype` registered every iframe's unqualified `addEventListener('load', f)` on the ROOT window. The MECHANISM is quickjs's own per-context class-proto slot (`JS_SetClassProto`/`JS_GetClassProto`), built EAGERLY at the realm's creation beside `JS_AddIntrinsicDOMException` — never lazily on first read, which creates a baseline object inside whichever flow happened to touch it first. A runtime-lifetime FUNCTION OBJECT carries a realm the same way: mint it in the realm that uses it (per fire, per call) rather than holding one in a static. The defect class is ONE fact answered from ONE place for MANY agents — a module static, a hardcoded string, a remembered global — and the fix is always to ask the realm, never to set the static from more places. **The list of per-realm intrinsics must live in ONE place that EVERY realm goes through, including the agent's first one** — a `_install` line hand-copied into each host's child-realm builder is the hand-picked list `build.mjs` warns about, and a component missing from one copy silently shares another realm's prototype with nothing to say so.
- **NO STUBS.** A shape-only object with noop methods, or a getter returning bare opaque WHERE THE SPEC COMPUTES A REAL VALUE (a `getComputedStyle` that returns opaque, an IndexedDB `put` that drops its value), is a fidelity gap marking where the real impl belongs — fill it in its real-browser-named component (`intersection_observer.c`, CSSOM, `indexeddb.c`), never a generic bag file. A web API not yet built is honestly ABSENT (the page's own throw on a missing global is the forcing function).
- **A QUESTION SOME ENTRIES ASK AND OTHERS DO NOT IS ONE MISSING CAPABILITY WEARING TWO NAMES, AND THE NAME YOU MEET FIRST IS THE WRONG ONE.** A dispatch deciding WHAT A SET OF BYTES IS — which document a response loads as, which parser a stream gets, which decoder a body needs — must be asked at EVERY entry that builds the thing out of them. An entry that skips it does not report an absent capability; it reports an UNRELATED SUBSYSTEM failing on input that subsystem should never have been shown, which is the §DFAIL failure mode with the crash landing in the wrong file. Measured: one loader ran HTML §7.4.5 Populating a session history entry's load-a-document type dispatch and crashed by name for the arm it had no loader for, while a second handed every response it fetched to the HTML parser — so ONE XML file was "§7.5.3 Loading XML documents is not built" through one door and "a page `<script>` did not COMPILE" through the other, because `<![CDATA[` is XML §2.7 CDATA Sections under an XML parser and PROGRAM TEXT under HTML §13.2.6.4.4 The "in head" insertion mode, which switches the tokenizer to §13.2.5.4 Script data state. The compile message was TRUE ABOUT THE BYTES and pointed at the JavaScript compiler for a document that was never JavaScript, which is worse than silence: it is a plausible diagnosis. So the dispatch is a COMPONENT with N callers and never an `if` at one of them, its INPUT is computed by that same component (an entry that can only reach the classification computes the input itself, and then there are two answers), and the closure is an assert AT THE CONSUMER — the parser is unreachable for a type it does not serve, asserted where the parse is, so a route added later FIRES instead of silently widening the old wrong answer.
- **Web APIs are defined by WEB IDL — the IDL is a GAP AUDITOR, not a stub generator.** `engine/idlgen.mjs` reads the real `.idl` (`@webref/idl` via `webidl2`), flattens inheritance + mixins, and at build time DIFFS the spec member list against what each component installs — printing MISSING members to implement at the root. Every member is real C (a computed value; the concolic value only where the value is unknown, e.g. `AbortSignal.aborted`; a dedicated documented no-effect ONLY where the SPEC ITSELF STATES THE STEPS ARE TO DO NOTHING, e.g. `Window.blur()`, whose HTML §6.6.6 Focus management APIs text is verbatim "The Window `blur()` method steps are to do nothing"). `js_noop` as an interface member is BANNED — it is the lazy stub the audit exists to expose. Use the IDL's TYPES (coercions, nullability, `[Reflect]`, `[CEReactions]`) as the spec of behavior to implement, never as codegen that fabricates it. **AND BEFORE WRITING AN AUDITOR FOR A PROPERTY, ASK WHETHER A CORPUS ALREADY IN THIS TREE TESTS IT — AN ORACLE YOU HAVE BEATS ONE YOU BUILD, AND IT IS ALREADY WRITTEN, ALREADY MAINTAINED, AND NOT YOURS TO BE WRONG ABOUT.** `idlgen.mjs` audits which members EXIST and nothing about what they ACCEPT: `grep -c variadic` is 0 across all three IDL tools, `idl_members.mjs` returns member NAMES, and the consequence is that `DOMTokenList: complete` was printed over a wrong signature and a 468-site arity defect was invisible to every gate in the tree. WPT's `idlharness.js` — checked out, present, with `idlharness*` files across a dozen areas — reads `.length` off every member and diffs the whole surface against the published IDL. It is the oracle for exactly the property no local instrument could see, and nobody had pointed it at this. The tell that you are about to build a redundant auditor: the property you want to check is stated IN THE IDL rather than in this codebase's own vocabulary, which is precisely what a conformance corpus exists to check. Build the auditor only for what the corpus CANNOT ask — installation constructs, engine-side declarations, this fork's own invariants — and when a gate's output is BYTE-IDENTICAL before and after a fix, say so plainly: that result is consistent with the fix AND with no fix, and naming what would actually confirm it is part of reporting it. **AND AN AUDITOR DERIVES THE RULE IT CHECKS FROM THE CODE THAT OWNS IT, NEVER RESTATES IT — A RESTATED RULE IS A SECOND COPY, AND THE ONE THAT DRIFTS IS THE COPY NOBODY RUNS AGAINST REALITY.** `idlgen` is trustworthy because it reads the real `.idl` through `webidl2` rather than a table of member names somebody typed; an auditor of this fork's own invariants earns the same standing only by parsing the declaration the engine already obeys. Worked example: the type-crossing audit derives its set of crossing types by **parsing `idl_concolic_rule`'s own switch**, so the day a type is added the audit knows, and a hand-kept list would have been the third copy of a fact whose second copy is what the audit exists to catch. **AND THE AXIS IS THE POINT, BECAUSE AUDITORS PARTITION AND EACH IS BLIND WHERE THE OTHERS LOOK**: names, argument COUNTS, and argument TYPES are three questions, and every one of the three here was built only after a defect walked past the other two — a wrong signature under `DOMTokenList: complete`, a `remove` that survived a length audit because its length was right, and seventy string coercions no member-list diff could see. So when an auditor reports zero, the honest sentence names the axis it asked about; and when a defect escapes every instrument, the question is which axis has no instrument yet, not which instrument was wrong.
- **Headless is not valueless — MODEL the state with mock-backed IO, don't shrug to opaque.** The only missing piece is a physical IO device; the spec still defines behavior without one. File System Access presents a MOCK filesystem that ROUND-TRIPS — `file_system.c` is the FS Standard's own model (file/directory entries, binary data, the lock and its shared count), reached through `storage_manager.c`'s bucket root and `file_system_handle.c`, and a byte written through a `FileSystemWritableFileStream` is a byte a later `getFile().text()` reads back. This line used to point at a `storage.c` that has never existed in this tree, which is why the file it named must be one you can open; `HTMLMediaElement` is a real state machine that plays with no device; `matchMedia` resolves a default viewport for its `.matches` example yet stays CONCOLIC (a branch still forks the alternate-viewport world); `getComputedStyle` layers UA-default + inline; `AbortSignal` is the real aborted-state machine; a `[CEReactions]` op RUNS custom-element reactions. Opaque is reserved for the UNKNOWABLE (attacker input, server-injected absent state), never for "there is no device." Never collapse a modelable value to bare-concrete either — that deletes the fork and its coverage; the concolic value is opaque-for-control-flow yet carries the concrete example. Err toward MORE exploration (the WFQ starves the unproductive arm).

# Solver half — the NOVEL contribution: forced multi-path concolic execution on time-travel primitives
- **Every value is CONCOLIC — a triple of (source-identity provenance, a constraint-DOMAIN of what it can be, a concrete EXAMPLE when the code pins/computes/learns one). There is no binary "opaque" sentinel** — that oversimplification is deleted. "Unknown external input" is the MOST GENERAL concolic value: unconstrained domain, no example yet, tagged by source. The solver's whole job is to NARROW the domain and FILL the example. Every predicate narrows (`x=='p'`, `startsWith('http')`, `<3`); every op propagates the example (`"/api/"+cfg.region ⇒ /api/us-east-1`, never `/api/{region}`). The example propagates because the engine RUNS THE REAL OP on the concrete (the `+` actually concatenates) — NOT because a carried label/note is derived by a propagation hook. The triple RIDES the value the interpreter already computes; it is not a second value-class shadowing it. A separate tagged-value class whose result-note a `Combine`-style hook derives at each op IS the recorded transform-expression §Re-execution forbids (it cannot see interprocedural/shared-mutable state), a redundant WORSE taint tracker beside the sound re-execution search — building one is the cardinal misread of this line, not an implementation of it. `JS_IsConcolic` (domain-carrying) is the only predicate; a re-introduced know-nothing branch is a regression.
- **Forced multi-path (J-Force lineage) FUSED with a per-flow path constraint (DART/SAGE/Kudzu lineage).** Concrete execution is the GROUND TRUTH that grounds all shared/interprocedural state, so the constraint is only ever over INPUT variables — which is why "a solver can't model shared state" is a category error (the solver never sees state). Control flow is FEASIBLE-REFINED by the domain, not blind fork-both: where the domain permits both outcomes BOTH arms run (reaching gated/admin code); a contradicted branch is pruned (sound-only — uncertainty keeps the arm). **CONCRETIZE-ON-PIN**: once `x==='admin'` pins the value, a later READ of that source returns the pinned bytes, so a later branch on it is decided by RUNNING the real predicate on a real string and does not fork at all — the pin is a fact about the VALUE and the concretization is the interpreter's ordinary work, never a second evaluator that re-decides predicates from a recorded constraint. Symbolic contradiction detection is only the unpinned residue (an open interval like `x>5 then x<3`), keyed by the PREDICATE's own identity — operator and both operands — so the flow's record of one predicate decides that predicate and never its neighbour. The scheduler asks the substrate ONE feasibility seam and holds zero constraint logic.
- **`@H` and `@S` share the explorer + constraint but DIVERGE at emission — conflating them is a dumbing-down.** `@H` must NEVER INVENT: a param pinned by `x==='v'` concretizes to `v` (the code determined it); a param gated only by range/prefix/regex stays a DOMAIN-ANNOTATED SHAPE (`{int>5}`, `{startsWith:/api}`) — inventing `6` for `x>5` fabricates an observed key. **A SHAPE STATES TWO FACTS AND CARRYING ONLY ONE OF THEM IS A WRONG REPORT, NOT A PARTIAL ONE.** PROVENANCE is where the value entered the program, composed as the expression the run actually built (`String({location.hash}.slice())`), and it says WHO must supply the parameter. DOMAIN is what this flow's own predicates narrowed it to, and it says WHAT the value must look like. Neither substitutes for the other, and the failure is asymmetric: a shape carrying provenance alone renders an UNCONSTRAINED parameter and a range-gated one with identical bytes, so its silence about the gate is read as the positive statement "anything goes" — the defaulted-field defect performed in a report, where nothing crashes and the consumer's request merely fails at a server. Emitting the domain is not inventing: `x>5` on the arm this flow took is a fact the run OBSERVED, exactly as a pin is, and the line between them is whether a VALUE was determined, never whether a constraint was. `@S` SOLVES/SEARCHES freely for a firing input (equality tokens, in-range values, negative/blocklist constraints, gate-guided breakout) because emission is WORKING-POC-ONLY and fire-verified — a wrong solve simply never fires and is discarded, so completeness beats purity.
- **Re-execution discharges the constraints — NO external Z3, NO taint tracker, NO recorded transform-expression, NO chain-inversion** (a transform-expression cannot model interprocedural + shared-mutable-state code; running the real code subsumes it). Not because running code is stronger at algebra (it is not), but because @H never solves (algebra's use is gone) and the @S constraint is "breaks out at the REAL sink after the REAL transforms," which only re-execution decides soundly and re-running the candidate makes safe. NO state-merging (veritesting) and NO function summaries (unsound under shared mutable state) — path explosion is handled by WFQ starvation + re-execution. Opacity SURVIVES numeric coercion (`+x`/`Number`/`parseInt`), so control flow keeps forking rather than collapsing to NaN.
- **A JS-engine encoding builtin is modeled FAITHFULLY, never re-implemented or enumerated by the solver.** `JSON.parse`/`stringify`, `encode/decodeURIComponent`, `escape`/`unescape`, `btoa`/`atob` are spec builtins like `+`: the engine runs the REAL codec (concrete truly encoded; concolic flows through shape-preserving). The solver must not hand-roll base64/percent/JSON nor emit encoder-inverted candidate variants (wrong layer, redundant). A builtin that can THROW runs and throws faithfully like V8 — `JSON.parse(x)` on opaque input FORKS a feasible success arm AND a throw arm (the real `SyntaxError` propagating to a `catch`→sink, or aborting visibly when uncaught); the leading `#` makes `JSON.parse(location.hash)`'s success arm infeasible so it throws exactly as V8 does. Special-casing a builtin's result to bare opaque is a double fidelity bug.
- **Learning from replies is the POINT, never suppressed.** The JS/JSON a server returns is the richest source of real example values; a consumed reply is ALWAYS fetched to fill examples (JS bodies additionally EXECUTED for their endpoints). ONE concolic value carries both the forking symbol AND the concrete example — never split into separate passes (a gated endpoint would then lack the gate-independent values the other pass knew). At a branch the example marks the real arm PRIMARY; the forced sibling drops the contradicted example, so only gate-DEPENDENT values degrade to a shape while gate-independent values stay concrete. Safety is NOT the sandbox's job: the untrusted WASM holds no network/security policy and learns freely; `safeFetch` alone enforces SOP/CORS/method/credentials. A safety `if` inside the engine is a layering violation.

# The scheduler — BFS + time-travel, each code flow run fairly
All code flows types such as long-running loops at ANY time and depth must be suspend/resume never drive-to-completion!
- **A "code flow" is a path through the program, isolated by its per-flow COW delta and captured as a SNAPSHOT.** BFS runs flows by value-of-information, FAIRLY — no flow monopolises; a deep loop suspends and yields so siblings run, then resumes. Time-travel: a COW snapshot holds any flow's state; suspend parks it, resume continues it from the exact point — hot in RAM or cold on disk, identically. A large loop is just fair BFS work, always suspend/resumable.
- **NO BOUNDS, ever.** Never a depth/step/time/run/memory/recursion cap, watchdog, idle/drain/no-progress/recycle count, seen-set, or same-args/same-state fixpoint. A bound truncates distinct work. Only EMITTED OUTPUT — never identity — proves a flow is done: shared state means byte-identical args can still PROGRESS, so a "re-computes nothing" proof is a cap in disguise. The engine never throws its own depth `RangeError`; recursion is reviewed at every depth. **A BOUND IS NOT A GRANULARITY, AND READING THEM AS ONE BUYS COST FOR NOTHING.** A bound decides work will not happen; a granularity decides only how often a flow OFFERS to rest, and an offer declined costs one predicate. So "never a step cap" does not license resting at the finest unit the substrate can express: a component that takes the extreme to avoid naming a constant has still chosen, and has chosen the expensive one — a per-BYTE rest point in a document load is one scheduler round trip per byte, where the spec's own sentence hands over a network task's worth of them. Take the unit the SPEC names (a task's bytes, a token, one tree-construction op), and state it as a POLICY INPUT the scheduler owns rather than a constant the component hides, so it can be tuned without touching the component and so two components cannot disagree about it silently. What must never be tunable is whether a span can rest AT ALL — that is BFS versus drive-to-completion, which is a different JavaScript and DOM engine rather than a setting, and it is the one thing in this paragraph that is architecture.
- **ONE WFQ policy at both levels** — an anytime-bandit priority: accumulated emitted VALUE (new @H+@S) + the flow's own SEARCH-FITNESS where it carries one (§@S's distance: a fraction, READ at the pick and never accumulated, so it orders two items standing at different distances — which is the one thing the reward term structurally cannot do) + a UCB optimism bonus ∝ 1/(visits+1) so a never-run flow is never starved − CPU-AGING so a monopolizer that burns CPU without emitting sinks below productive+unrun flows. Additive (not a literal value/cpu ratio, which degenerates 0/0 on unrun flows), ORDER-only, never drops a work item. **EVERY TERM IS CARRIED BY A FORK, AND A FORK IS RANK-NEUTRAL** — a sibling is its parent's path with one arm appended, so it is worth exactly what the parent is worth at the instant of the branch; any term a fork does not carry is a way for a flow to change its own rank by branching, which is reset-by-splitting and is the same defect as a bound. Assert that equality AT the fork, over the whole weight rather than over a list of fields, so the assertion is what forces the next term to be carried. **BUT THAT EQUALITY IS A CLAIM ABOUT ONE INSTANT, AND IT DOES NOT COMPOSE — WHICH IS WHY "CARRIED BY A FORK" IS NOT THE TEST AND A COPY IS NOT THE MECHANISM.** The assertion compares a parent with the arm born HERE, so it is structurally blind to the pair it never compares: two arms of ONE parent forked at TWO instants. Those must also be worth the same, because neither of them did anything between the branches — and a term COPIED at the fork instant makes them differ by exactly what the PARENT did in between. That difference is BIRTH ORDER, and an order read descending on birth order is LIFO wearing a bandit's vocabulary: newest-first, DFS, the frontier entered and never drained. Every assert passes, the fork is rank-neutral at every branch, and the queue is still a stack. **SO THE TEST FOR A WEIGHT TERM IS NOT "DOES A FORK CARRY IT" BUT "WOULD TWO ARMS OF ONE PARENT, FORKED AT TWO INSTANTS, READ IT THE SAME" — and a term that fails it does not belong on the FLOW at all; it belongs on the ACCOUNT the fork chain shares, read through one pointer, where there is nothing to copy and therefore nothing a fork can carry differently.** **AND THE CREDIT AND THE DEBIT LIVE AT THE SAME ACCOUNTING UNIT OR NEITHER TERM MEANS ANYTHING.** A reward minted once and PRESENTED N times against an aging charged ONCE is not a scheduler, it is a moat: the credit inflates by the page's own fork factor, the debit does not, no silence at any price pays it off, and §NO BOUNDS forbids bounding N. The reward's spread is then unbounded while every other term's range is at most one emission — so **"a never-run flow is never starved" is TRUE AMONG MEMBERS OF EQUAL REWARD AND AMONG NO OTHERS**, which is arithmetic and not a policy anyone chose. That is not a reason to weaken the guarantee; it is the reason the reward is held per ACCOUNT: members of one account read one reward, the gap the guarantee is tight in is then identically zero WITHIN a fork family, and the guarantee holds outright exactly where it is needed — a real page's whole frontier is one family. What survives as a reward comparison is then BETWEEN accounts, which is what a bandit ordering is for, and each account pays its own silence off at its own rate. The measured shape of getting this wrong: a frontier growing many-fold inside a reward band frozen at both ends, thousands of members minted at the top and none of them reaching the tail, with the ledger's own top not advancing once — a scheduler whose reward term names nothing anybody standing in it had done. **The corollary is that a JUSTIFICATION RESTING ON A DRAIN IS NOT A GUARANTEE**: "the buried tail is reached when the tree above it drains" is a sentence to MEASURE before it is believed, and on a frontier that grows it is the same starvation with a reason attached. **Level-2 (within a document):** the engine orders its flows (boot fork, branch-arm, loop/recursion arm, orphan-invoke), each a COW snapshot on the heap call-stack, preemptible per-opcode, suspend/resumable across sessions; the running flow yields the instant a parked flow outranks it. **Level-1 (across documents):** one WASM instance per page, so the host orders live per-page engines by best-flow weight, runs the top until its best flow no longer outranks the runner-up, then re-ranks. Engine creation is admission-gated to the RAM working-set floor; a fetching engine is skipped so one doc's wait never stalls another; an engine self-parks its residue to the IDB cold tier under pressure. Cold-tail resume is the SAME admission step (not a separate loop), ranked by a `frontierWeight` estimator (emit-per-visit, since a parked flow has no live CPU to age by).
- **ONE global, continuous, cross-session frontier** — one attention process for the whole extension; the frontier is the UNION of every flow from every origin ever visited, persisted in IndexedDB, never reset. A new page APPENDS its flows (boot fork, and one drive per function the bundle shipped and never called); it does not start a new scheduler/run/attention. **A DRIVE OF UNCALLED CODE IS THE ONE FLOW A DECISION VECTOR CANNOT REPRODUCE, so its recipe carries a CROSS-SESSION NAME FOR THE FUNCTION beside its path** — every other recipe is (path, reward) and a resume re-runs the DOCUMENT under it, which is precisely the run that never calls an uncalled function. The name is composed of what the BUNDLE determines and the session does not (the script, the position in it, the body's own text); a live function object, a heap-walk index and a hash of the SOURCE TEXT ALONE are all wrong, the last because a minified bundle repeats one-line bodies dozens of times and the name would identify a SET. The resumed flow replays the document like any other member — which is what re-creates the closure and consumes its recorded arms — and takes the body that name matches at the point its work runs out. **AND THE TAKE MUST ROUTE, or the recipe is inert:** every flow that runs out of work reaches the same heap, so without routing the first arrival takes the body a recorded drive was waiting for, drives it from a fresh path, and the recorded drive finishes having called nothing — the function is still driven and the loss is invisible. **AND THAT NAME IS ALSO WHAT THE DRIVE'S UNKNOWNS ARE CALLED, because a replay compares the QUESTION each recorded arm answers and a question is composed of the source identities in it.** An argument named by a SESSION-LOCAL ORDINAL therefore asks a different question at the drive's very first branch, and every arm it recorded inside the function is discarded as a divergence — the drive comes back and its PATH does not, which is the same loss one level down and reads as ordinary exploration. Two drives of one body sharing the name is correct, not aliasing: they are the same call of the same function with the same unknowns. **AND THE RULE GENERALISES TO EVERY RECORDED ORDINAL: AN INDEX NAMES A THING ONLY WHILE THE SET IS FIXED, AND OVER A MUTABLE SET A REPLAYED INDEX SILENTLY RENAMES ITS REFERENT.** Above, a session-local ordinal costs a DIVERGENCE — the question does not match, the arm is discarded, and the loss at least has a shape. Over a set the PAGE mutates it is worse, because every arm stays in range and the flow acts on the wrong member with nothing to say so. Measured, caught before landing: a fork over "which live timer does this handle name" was designed to ask ONE N-way question whose completions were positions in the map, and the seam composes a completion's key from `"%d"` of its position — so a flow answering "it is the entry at rank 0" and clearing it would, at a second call with the map one shorter, replay its recorded *not-rank-0 / yes-rank-1* against the SHIFTED enumeration and cancel a timer no answer of its own ever named. Every arm in range, every assert satisfied. A position is a fact about the operand ONLY where the set is the machine's own and fixed at its definition (a registry of algorithm names is; a global the page writes is not). So a completion over a mutable set carries the member's OWN NAME in the operation string — the identifier the platform assigns, monotone and stable across a park and a resume — and the N-way ask collapses back into the ordinary elimination chain, which is what makes this a naming fix rather than a second mechanism. A browser restart resumes the same frontier by global value-order. Any per-page/per-session/per-tab scheduler, registry, run-counter, or reset is the cardinal violation.
- **THERE IS NO GRIND — BFS is the one system.** Orphan-driving (force-invoking a never-called function to surface its unused endpoint) is just another BFS flow. "Breadth first THEN depth" is ONE continuous BFS whose ONE WFQ merely orders higher-value-of-information flows ahead of lower — one queue, one registry, one loop. A second scheduler beside it (engine-side silent-counts/fixpoints/deep-step driver, or host-side deep-grind loop / no-progress recycle / per-culprit abandon) is the cardinal violation. **The @S candidate re-fire is a FLOW in this ONE BFS, never a separate executor.** A standalone verify driver (a `flow_exec_once`-style `while(JS_FlowResume){}` that runs one candidate start-to-finish with preemption OFF) is the same cardinal violation twice over: a SECOND scheduler beside the BFS, AND a drive-to-completion (an unbounded candidate loop hangs, non-parkable — violating §scheduler's suspend/resume-at-ANY-depth). A candidate re-fire is seeded as a candidate-session flow on the ONE frontier, preemptible and parkable like every other flow; the sink firing is observed by the same detectors during its scheduled run. No verify subsystem, no carve-out — the same ONE loop verifies as explores.
- **AN OPERATION THAT BECOMES A WORK ITEM TAKES ITS INPUTS WITH IT — anything it reads back off the object it acts on is read at the wrong TIME.** This is the defect that arrives with every conversion from a call to a job, and it arrives silently because the wrong value is a REAL value belonging to that object. §7.3.1.3 Child navigables' create-a-new-child-navigable step 14's load is the worked example. As a call it fetched the address it was given; as a job it read the address off the navigable, which is right for the create that named the navigable after its destination and WRONG for `open("post-to-top.html","iExist")` — a navigation whose target is a srcless frame whose own address is `about:blank`. The destination was discarded, the frame materialized empty, and the only symptom was a test waiting for a message. The same sentence covers §7.1.7 Policy containers' inherited policy (whose clone it is depends on the OPERATION — the creator's for a create, the initiator's for a navigation — never on the state of the thing being loaded) and §2.4.3 Document base URLs' base URL (resolved by the INITIATING document, which by the time the job runs is the document being replaced). What the target's state may still decide is what is genuinely a fact about the target and not about the operation — here, the document's IDENTITY. **AND THE OBJECT'S OWN STATE MUST BE THE PRE-OPERATION STATE, which the spec already says.** §7.3.1.3 Child navigables creates a navigable holding the initial `about:blank` and navigates it afterwards; storing the destination there instead was harmless while the load was synchronous and became a DOUBLE LOAD the moment it was not — a read reaching through before the job ran built the destination early, the job then found a materialized navigable and loaded the address again into a second document. Two fetches, two realms, one navigable, nothing to say so. When you make something asynchronous, re-derive every field from the spec's ORDER, never from what the synchronous version happened to leave lying around.
- **A CAPABILITY MATERIALIZED PER FLOW AND NEVER RECLAIMED IS A CEILING, and the probe that cannot afford it is the measurement, not the problem.** A per-flow realm, navigable or arena is asked for once per flow that reaches the construct, so ONE fixture statement can ask for one per flow and the heap runs out. The response is NEVER to soften the probe, and never to defer the materialization that made it honest: it is to NAME the ceiling in the assert that fires — the reader of a `@WHY` is standing at the allocation, and "OOM" alone tells them nothing about WHAT ran out — and to BUILD the reclamation, which for a destroy means the spec's algorithm and not a `free`, because a flow may be parked inside the thing being destroyed. **THE DEFECT SHAPE, WHICH IS THE PART THAT DOES NOT ROT: A FLAG THAT REPORTS AN OUTCOME INSTEAD OF PERFORMING IT.** Setting a `closed` bit announces a destruction that has not happened and never will — the document, its Window, its realm, its queued tasks and its whole subtree are left exactly as they were — and **THE ANNOUNCEMENT IS WHAT MAKES THAT INVISIBLE**, which is why it is a STUB in §NO STUBS' sense rather than a partial implementation. The same object may legitimately report that flag afterwards; it reports it BECAUSE the destruction ran, never INSTEAD of it. A destroy is a spec algorithm with an ORDER, and its halves may not share a tempo — a container's half can be synchronous while the document's half is a job — so collapsing them is HOW a flag comes to stand in for the work. **AND THIS BULLET IS WHERE THAT RULE WAS LEARNED TWICE, THE SECOND TIME AGAINST ITSELF.** Every coordinate it once carried — that the realm is "released only with the agent", that the reclamation was unbuilt, that the OOM assert did not name realms — was TRUE WHEN WRITTEN and FALSE within days, and the three together sent a reader to build what the tree already had, out of the one file whose own first paragraph forbids status. **A STALE SENTENCE HERE OUTRANKS A STALE `DFAIL`**: a crash is read by everyone it stops, so a wrong one meets traffic and gets corrected, while this file is read as the standing description of where the work is and a wrong one is BELIEVED. So: the rule is the rule, and the tree is never described here. If a sentence names a file, a function, or the state of the work, it is status — it belongs in the report beside the revision it was measured at, and a reader who finds one here checks it against `origin/main` before acting on it.
- **Attention: per-opcode RETURN-to-scheduler from `JS_CallInternal`** (not a JSPI suspend — JSPI saves the C stack while frames live on the heap arena → teardown desync). Universal, boot included. TWO orthogonal decisions at the one per-opcode check: (1) the **VALUE yield** — suspend the moment a parked flow outranks (or on an emit/fork/suspension that changes ranks), never after N opcodes (an opcode-budget counter is a step cap, banned); a top-ranked flow runs on at ~zero switch cost. (2) the **COOPERATIVE-QUANTUM yield** — about THREAD-SHARING not value: after a bounded slice of CPU ACTUALLY CONSUMED the flow suspends (same COW-snapshot path) and `scheduler_run` RETURNS to `qjs_step` so the host pumps messages / interleaves engines / streams findings / snapshots, then resumes the SAME top flow on the byte-identical frontier. Required and universal (a lone engine otherwise freezes in a non-returning `qjs_step`). **THE BUDGET NEEDS AN ASYNCHRONOUS SOURCE, AND THIS LINE SAID "WALL-CLOCK SLICE" WHILE IT HAD NONE.** A yield-request bit polled at every opcode makes the suspend point universal; it does NOT make the budget expire, because the hook that reads the clock runs only where something RAISED a request, and everything that raised one was a shape of the PAGE'S OWN BYTECODE (back-edge, call, fork). Straight-line call-free code therefore did not merely mis-measure the slice, it never EVALUATED it — a budget noticed only when the debtor volunteers. So the quantum is a COMPONENT (`solver/quantum.h`), it raises the request from OUTSIDE the flow's instruction stream (natively `timer_create(CLOCK_THREAD_CPUTIME_ID, SIGEV_THREAD_ID)`; the handler raises the bit and decides NOTHING), and it is measured in CPU because §Testing says so and because a DESCHEDULED thread denies nobody the thread — the host that would use it is that same thread. **WHAT EACH HOST CAN MEASURE IS ASKED, NEVER ASSUMED** (`quantum_measure`/`_is_cpu`), because the two hosts differ and a file that compiles for both may not claim one's property for the other. A single-threaded wasm instance has NO CPU clock (emscripten answers every WASI clock from `emscripten_get_now()`, checked at the first slice so the day it stops being true the assert says so) and NO way to be interrupted mid-call: JS is run-to-completion, so a periodic export between steps is not mid-call, and the only agent that could raise the bit is a second thread in SHARED linear memory (`-pthread`, cross-origin isolation, plus the address of the main thread's own thread-local request byte). That is the transport requirement, named — until it is provisioned the extension's raise sources are the interpreter's own, so the back-edge and call raises are the WASM HOST'S ONLY EDGE and not transition scaffolding. **AND IT IS COSTED, NOT MERELY NAMED.** A SharedArrayBuffer needs the extension pages `crossOriginIsolated`, which takes BOTH `cross_origin_embedder_policy: require-corp` and `cross_origin_opener_policy: same-origin` — `same-origin-allow-popups` does NOT make a page `crossOriginIsolated` — plus `-pthread` on the wasm link and an exported address of the main thread's own request byte. Read `manifest.json` for which of those it currently carries; do not take a number from this file. The flip is not free and the cost is in the OTHER half of this project: §LIVE-VERIFY opens the attacker popup from an extension page, and `same-origin` severs an opener across origins. Whether that delivery survives it is a question to ANSWER on the real harness before the flip, never to assume in either direction — and the COOP value is one setting for every extension page, so there is no per-page way to have both. THE RAZOR: if a resume is not byte-identical — drops, starves, skips, reorders, or forgets ANY flow — it is a CAP, banned; a yield you cannot prove is lossless is a cap.
- **Every runtime job is a scheduler flow — no job-queue drain.** Every enqueued job (async resume, `.then`/`.catch`/`.finally` reaction, `queueMicrotask`, `setTimeout`/rAF) is a first-class flow in the one WFQ (COW-snapshot, preemptible, park-as-snapshot-able). There is NO `while(JS_ExecutePendingJob)` loop — the scheduler IS the job pump. An await's result is DELIVERED (consumed): the continuation resumes WITH the settled value, or RE-THROWS a rejection into it so `try/catch`/`.catch` runs, then continues the same flow — never dropped. Code-loading async ALWAYS executes (`await import(x)`, a chunk `fetch().then(eval)`, a `document.write`'d `<script>`). A flow's OWN await chain resumes strictly in program order; only WHICH flow runs next is value-reranked. An async recursion is a TREE of parkable flows, explored, never terminated or judged "redundant" (redundancy is undecidable). Two mechanisms keep it unbounded-until-disk with no bound: the WFQ orders by actual emitted output (a so-far-unproductive level is momentarily outranked, rises the instant it emits), and RAM pressure suspends the lowest-value tail to the IDB cold tier as a snapshot. STARVE means deprioritize-and-page (resumable, cross-session), NEVER terminate. An async OOM is never a missing bound — it is a non-parkable structure; making every continuation a first-class flow makes that OOM impossible by construction.

# State isolation — per-flow heap+DOM COW delta
- **Shared state = per-flow heap+DOM COW delta.** Each flow owns the heap slots and DOM nodes IT wrote, layered over the shared baseline. Context-switch SWAPS deltas (unapply outgoing, apply incoming), not a serial revert — so every flow is preemptible mid-write (no writer runs to completion) and any number interleave. The delta captures MUTATIONS (restore old value on unapply) and CREATIONS (delete added slot/node on unapply) across the JS heap AND the Lexbor DOM — ONE uniform primitive for isolation, snapshot, eviction, per-arm exploration, cross-session resume. A serial undo-log or host-side save/restore bracket is the wrong design (forces run-to-completion, cannot interleave).
- **The document is a time-travel entity, not a static DOM** — its tree/attributes/inserted nodes are PER-FLOW; `querySelector` in flow A and B can see different documents; rewinding restores the exact document a flow saw. The BROWSER owns the DOM API (reads AND write operations, `browser/document.c`, `browser/dom_element.c`, Lexbor tree); the SOLVER owns the time-travel STATE (`solver/dom_cow.c`: capture each write into the running flow's delta, swap on switch). A DOM write is the coupling point (the mutating edges `appendChild`/`setAttribute`/`innerHTML` are solver-coupled; a pure read like `querySelector` needs no capture).
- **A COMPONENT'S OWN C RECORD TIME-TRAVELS, and the capture belongs in its ACCESSOR.** A browser component keeping state behind a class opaque writes where no property hook and no engine hook can see, so `cow_capture_host_record(obj, rec, &LAYOUT)` runs where the flow REACHES the record: a record a flow has reached is one it may write, the delta dedups to one entry, and there is then NO write site left to miss — which is the only way this goes wrong. The layout names the record's owned JSValues and is the SAME list its finalizer frees, so a field added to one and not the other is caught by reading them together. Finalizers and gc_marks go through `JS_GetOpaque` instead, deliberately: a capture during collection would dup values on an object being torn down. The raw byte capture (`cow_capture_host_state`) is for a POD LATCH ONLY — a memcpy of a JSValue makes a reference it does not count, so the next restore frees a value the blob still names.
- **PLATFORM DATA A FLOW QUEUES IS A JS VALUE, never malloc'd C.** A port's message queue, a broadcast, a pending task's payload: each must PARK to the IDB cold tier and RESUME, and each must fork per-flow. A JS Array does both for free — its mutations are property writes the delta already captures, and the snapshot machinery already carries it. A malloc'd list captured as head/tail POINTERS reverts the POINTERS on a context switch and leaves the NODES reachable from nothing: a leak the runtime's own GC walk cannot see, so no gate reports it.
- **The delta captures ONLY shared baseline state — flow-private state is never captured** (the load-bearing invariant keeping a delta O(shared-state-touched) with no bound). An object CREATED by the running flow (`flow_local`) can never be observed by another flow, so `cow_capture`/`_prop`/`_create` SKIP it. The delta holds only genuine cross-flow state, never a loop body's per-iteration transients. This holds only if EVERY flow runs at flow-private mark, so an iteration over opaque input MUST fork each iteration as its own parkable flow (then each iteration's transients are flow_local). Boot is the one flow whose creations are legitimately BASELINE, so an opaque loop in boot forks per-iteration boot-flow siblings too.
- **A genuinely large delta (a loop mutating real SHARED state each iteration — common, never assume rare) is O(N) shared writes, handled by the ONE resume mechanism, NEVER by serializing delta bytes.** There is no delta-byte paging / buffer-pool spill (that is the live-graph serialization Cross-session forbids — a delta names its target by a live heap pointer with no cross-tier identity). The RAM bound comes from making each iteration its own parkable flow (a loop is a CHAIN of per-iteration flows, each O(1) incremental). Same-session paging and cross-session resume are the SAME operation: a hot flow resumes cheaply; an evicted one serializes its snapshot to disk and resumes it later. One honest exception: a uniformly-productive unbounded shared-accumulation loop (every iteration BOTH emits new AND mutates shared state) hits the physical RAM→DISK floor — the real limit, never a cap and never dedup'd. Diagnose a large delta by WHAT fills it: flow-private bloat (fix by running each iteration at flow_local mark) or genuine shared state (per-iteration flow chain, snapshot-parked, resumed).
- **Async/promise state is per-flow state that time-travels.** A pending promise, its resolve/reject capability, a suspended async frame, a queued `.then`/microtask continuation belong to the FLOW and ride its COW delta — flow A's promise settles with X while flow B's settles with Y. Modeling async as global (a shared job queue, a `JS_ExecutePendingJob` drain, a resolve fn held across a fetch OUTSIDE the delta) is a bug class: one flow's async effect leaks into another's timeline. The correct primitive is ONE — the per-flow COW delta extended over the promise/await/continuation graph.

# The C stack is a NON-limit — trampolining + hooking, overflow impossible by construction
- **All calls trampoline onto the HEAP stack** (`TrampFrame`/`do_tramp_call`/`do_return` + exception unwind): every `OP_call`/`OP_call_method`/tail-call pushes a heap frame and `goto restart`s instead of recursing into `JS_CallInternal`, so the C stack stays flat and direct/method/tail recursion is unbounded — the substrate for snapshot/preempt/evict/resume at depth. The trampoline restores the caller's closure `var_refs` on return (else nested-closure non-tail recursion crashes). `JS_ThrowStackOverflow` becomes impossible on the path; overflow on a not-yet-hooked path CRASHES LOUD (never caught into a soft `RangeError` that masks a bound). Hitting a genuine floor (IDB full) crashes as OOM.
- **C-function re-entry (a C builtin calling `JS_Call`→`JS_CallInternal`) reaches no-C-recursion by TWO mechanisms, split by whether the builtin holds a C continuation:**
  - **Call-site-resolved** (`.bind`/`.call`/`.apply`/`Reflect.apply`, the `f(...args)` spread, the builtins' internal `js_call_function`, and every CALL/READ/WRITE/MEMBERSHIP/DELETE through a Proxy) hold NO surviving continuation — the interpreter RESOLVES them at the operator site and trampolines the ultimate target directly, no C round-trip (`do_forward_call`/`do_forward_callfn` reshape the operands to the method-call shape and share one `do_forward_dispatch`; `js_tramp_proxy_*` re-dispatches the trap's normal handler and places its one result via the stack-shape descriptor `do_return` reads). Recursion is unbounded through a bound/`.call`/spread/proxy reference. **A trap's post-check IS why the continuation exists** — the target's invariants ([[Get]] frozen-property SameValue, [[Set]]/[[Delete]]/[[Has]] non-configurable rejection, [[Construct]] must-return-object) run on the trap's RESULT, so they ride the continuation and execute at `do_return` before the result is placed, sharing ONE implementation with the C path. Routing a trap without its invariant is not a partial implementation, it is a WRONG one — `new Proxy(frozen,{get(){return 999}}).f` must throw.
  - **Continuation-holding** (array iteration `forEach`/`map`/`reduce`/`sort`-comparator, `String.replace`/`JSON.stringify` callbacks, and getters / Promise reactions) keep loop/accumulator state between callback invocations, so they cannot be call-site-unwrapped. **They gain suspend/resume by HOOKING the callback drive into the flow machinery — NOT by re-hosting the builtin in JS (that would violate "don't code browser features in JavaScript").** The builtin STAYS a C engine feature; its callback dispatch routes through the trampolined `OP_call` and the `async_func_resume_run` seam (the single point that self-resumes a body through forced back-edge preempts — see the driver rule below), so the callback's body — sync loop, `await`, generator — suspends/resumes at any point exactly like a directly-called function, and the builtin's own iteration is preemptible at each callback boundary. Where the builtin ITSELF branches on a value (sort's `cf(...)<=0`, stringify's `typeof`/`Array.isArray`), an OPAQUE operand must NOT fork that branch — short-circuit via the `__isOpaque` leaf: sort's element order is meaningless → collapse to 0; stringify's opaque field VALUE is tainted external input → yield the OPAQUE itself (taint preserved, never a de-tainting placeholder). Either way the callback still runs (its emits/side-effects happen); only the meaningless fork is removed.
    **A continuation-holding builtin IS its step machine — the JS_Call-loop version must NOT survive alongside it, and THE CALL PATH ASKS NOTHING AT ALL.** The builtin DECLARES itself a step machine at its definition (`JS_CFUNC_STEP_DEF`), and it is driven from the ONE point every call shape already converges on: the C-function invocation itself (the `JS_CLASS_C_FUNCTION` branch / `js_call_c_function`'s `cproto` switch). **What is banned is a predicate that selects a FALLBACK, not dispatch as such.** The defect is a subsystem deciding, from a pattern, whether to run logic that was never designed to suspend — because that logic then survives, and every narrowing condition in the predicate is a case silently handed to it. Once the legacy body is DELETED there is nothing to fall back to, and the surviving question ("is this callee the Promise constructor / a step machine?") is ROUTING: it picks which one implementation runs, and a shape it fails to answer for CRASHES rather than quietly degrading. Judge a predicate by that test, not by its existence: if deleting the thing it selects against would leave it still needed, it is routing; if deleting that thing makes it meaningless, it was a fallback and should have gone with it. **A dispatch predicate at a CALL SITE is still BANNED — including a single uniform one —** `if (tramp_step_def_of(callee)) goto do_step_tramp;` repeated at `OP_call` / `OP_call_method` / `do_forward_dispatch` is the recognizer allowlist in its final costume: it is still per-spelling plumbing, it must be added once per call opcode, and every omission is a silent gap that only surfaces when some test happens to use that spelling. Renaming the predicate from "recognizer" to "capability check" changes nothing — the test is not what it ASKS, it is WHERE it is asked. One convergence point, no per-site `if`. A `tramp_can_call_<builtin>` recognizer — a list of pointer comparisons deciding which builtins get the suspending path — is BANNED, and so is the same list re-spelled as a magic-indexed table of "who is special". A recognizer can only exist because a legacy implementation still exists for it to choose against, so **the recognizer is a symptom: delete the legacy body and the choice disappears.** **THE GOAL IS TO REPLACE THE FEATURE, NOT TO BUILD A MECHANISM THAT SELECTS BETWEEN TWO OF THEM.** A capability declaration is not a licence for the old logic to keep living behind it — every selection mechanism (recognizer, cproto check, step table, gate predicate) is TRANSITION SCAFFOLDING whose only correct trajectory is to zero, and while it stands it is where the bugs come from. The bug list is not theoretical: a double-free (state freed by `fini` and again by the shared unwind), a stale `tramp_first` handing a builtin `this=undefined`, a `JSStepHdr` overwriting the first fields of a state that had not adopted it, an init-failure leak of ~20 objects per throwing test — NONE of these are bugs in the old walk or the new one. They are all bugs in the seam between them, and they cannot exist once one implementation is gone. So a conversion is not "add the machine, then choose it"; it is REPLACE the feature, in one diff, and the seam never exists to be got wrong. **EXPAND THE NEW LOGIC'S SCOPE UNTIL THE FALLBACK IS REDUNDANT — never un-expand.** A selector that narrows to the cases the new machine already handles (generator-backed sources, bytecode callbacks, string operands) exists because the machine is missing a capability, not because the other cases are unsupportable. Widen it and the failures NAME the missing capability: `iterator-closed-for-*` named IfAbruptCloseIterator; a drive-to-completion DFAIL named plain-iterator `.next` on the tramp. BUILD the named thing, widen again, and when nothing is left to select the legacy body deletes. Reverting the widening because it went red is STOPPING HALFWAY: it hands control back to the fallback and destroys the signal that told you what to build. Widen ONE consumer at a time — widening several at once produces a failure count with no name in it, which is how a previous attempt regressed 12 tests and got reverted with "the C path owns semantics this machinery does not reproduce" and never said which. If a named capability genuinely cannot be built now, record it BY NAME so the next attempt starts from building it, never as a silent narrowing. **DO IT IN THAT ORDER — legacy body FIRST, detector second.** Deleting the detector while its twin still lives breaks every path the detector was routing, and the reflex is then to re-add the detector under a new name (recognizer → "capability check" → a magic-indexed table → a `||` in a gate). Each conversion is three ordered steps: (1) DECLARE the capability at the builtin's definition (`JS_CFUNC_STEP_DEF` for continuation-holding; call-site-resolved for `.apply`/`.call`/spread); (2) DELETE the legacy `JS_Call`-loop body in the SAME diff; (3) the detector now has nothing to choose — remove it. A detector that survives step 3 means step 2 was not finished. The same applies one level up: a gate asking what the TARGET is (`tramp_can_call(t) || tramp_step_def_of(t)`) exists only because the reshape path cannot handle every target kind — fix that path, and the question disappears. The tell that you are building the banned shape: every narrowing condition in the recognizer (a C/bound callback, a non-primitive receiver, a patched `exec`, a subclass) is a SILENT FALLBACK to the old code, and each new call spelling (`.call`, `.apply`, spread, `super[x](...)`, `Reflect.apply`, the direct `@@replace`) becomes its own bug — one builtin answering differently depending on how the call was written. **An unconverted call path is a `@WHY`, never a tolerated slow path.** An earlier version of this rule claimed the opposite — that with the legacy body gone a stray call site would be "merely NOT-PREEMPTIBLE" because a generic driver in `js_call_c_function` still returned the right answer. That was FALSE and is deleted: the preempt hook fires unconditionally, so a callback holding a loop aborts from inside that driver anyway; it never degraded gracefully, it only moved where the crash surfaced. A second, non-suspending driver for the one step machine IS the dual system — it is deleted, and `js_call_c_function` DFAILs on a `JS_CFUNC_step` callee as a BACKSTOP. The enforcement is structural, not that backstop: every call shape whose callee has no bytecode body converges on ONE point (`do_generic_callee`), which is where the step question is asked, so a new call opcode cannot forget to route — there is no route to remember. Each opcode declares only its OPERAND SHAPE (`tramp_first`: `-1` plain `[f,args]`, `-2` method `[this,f,args]`), from which the cleanup follows; that is why those blocks were duplicates and why they collapsed. Every call shape (`.call`, `.apply`, `Reflect.apply`, spread, `super[x](...)`, tail position, and the PLAIN `f()`) must reach the step driver; "it still works, just without suspension" is not an allowed state, because correctness that survives a missing route is exactly what lets routes go missing. **A directory that ABORTS is not better than one reporting errors — it is the same failures with the count hidden.** Routing a previously-unrouted shape turns an abort into a real number, and that number going from "no result" to "67/190" is the FIRST HONEST MEASUREMENT, never a regression to revert. Reaching for the revert there is the same reflex as keeping a legacy fallback: making the report look better instead of making the system right.
    **A step state must be COMPLETE before the first operation that can throw, and a callback frame OWNS its arguments.** Two ownership invariants, each of which produced real bugs (a segfault and two leaks) that all looked different and were the same mistake. (1) `init` must place EVERY owned field on the state — and `string_buffer_init` the accumulator — before anything that can fail, because the failure path tears the state down through `fini`/`_end`, which frees exactly what the state holds and nothing else: a field handed over LATE leaks (the whole collected match array), and a buffer initialised late is freed with a NULL ctx (a segfault). A user `toString`/`valueOf` inside `init` is one of those throwing operations. (2) `narg_alloc == 0` means BORROW the argument slots in place, which is sound ONLY when they are the caller's OPERAND STACK, which the caller frees; a C-builtin callback borrows from the step state's own `cb_args` buffer instead, so a callee with a REST parameter built its rest array out of slots nobody owned and leaked the entire runtime graph on every continuation-holding builtin. A callback frame therefore allocates and owns its arguments. Fixture rule that follows: a step builtin's callback must be exercised with a REST PARAMETER — every other arg shape (`(v)`, `(a,b,c)`, `.call`, `.apply`, bound, thisArg) takes the identical borrowed path and cannot find it.
    **A data pointer must never be stored in `JSCFunctionType`.** That union holds FUNCTION pointers; putting a step-def pointer in it is a strict-aliasing violation that passes at `-O0` and under gdb and segfaults a whole directory at `-O1` with no single file reproducing. Reach the def through a named `STEPDEF_*` id instead. When a crash appears only under optimisation, `-fno-strict-aliasing` is the one-command discriminator — use it before theorising.
    **AND UB DOES NOT ONLY CRASH — IT ALSO HANGS, SO A SENTINEL THE CALLER MUST SUPPLY IS A CONTRACT THE COMPILER ENFORCES BY MISCOMPILING.** A variadic helper that scans its argument array for a terminating `NULL` is reading past the end of a caller-provided automatic array the moment one caller forgets it, and the optimiser is entitled to assume that never happens: from "the scan cannot run off the end" it derives "the loop cannot exit" and emits a **two-byte self-jump**. Measured: one macro with hundreds of correct call sites and TWO that omitted the terminator, and clang at `-O1` turned them into `jmp .` — an unconditional infinite loop inside one C activation, so the interpreter never regained control, the flow could not be preempted, no sibling ran, no document interleaved, and the cooperative quantum's timer raised a bit nothing would ever poll. It cost 27 of 34 killed files in one corpus area and made an ordinary `el.style = ""` never return. **THE TELL IS THAT IT PRESENTS AS A PERFORMANCE PROBLEM**: the budget fires, the process looks busy, RSS is flat, and every instinct says "expensive algorithm" — so the discriminator is a DEBUGGER, not a profiler. Identical `$rip` across independent samples is not a hot loop, it is one instruction; confirm by disassembling the shipped binary rather than reading the source, because the source of a self-jump looks perfectly ordinary. **THE FIX IS NEVER TO ADD THE MISSING SENTINEL AND STOP** — that repairs one caller and leaves the contract enforced by nothing. Bound the scan by `sizeof arr / sizeof arr[0]` at the point where the size is known (a macro expands at the call site, so it knows), and DCHECK the last entry, so a forgotten terminator becomes a named abort instead of a program the compiler is free to reshape.
- **The generator/async DRIVER rule (the suspend/resume seam).** A forced preempt at a loop back-edge returns `FUNC_RET_PREEMPT` to whichever driver resumed the body; `async_func_resume_run` self-resumes through it (park+rebuild the frame, continue) so a preempt is never mistaken for an ECMAScript yield, and clears `throw_flag` before each re-resume (a preempt-resume is a continuation, never a re-throw). `flow_preempt_routable` fires the preempt only where a driver adopts this seam (the flow base; every generator/async body via `js_generator_next` / `js_call_generator_function` / `js_async_function_resume` / `js_async_generator_resume`). A C-reentry callback with no driver is routed by the hooking rule above. Overflow/recursion is reviewed at every depth, never a `RangeError`.
- **Boot IS the forking first flow — ONE boot system, never two.** The COW baseline is PRE-boot (post-env setup, before any page script); boot runs as the first flow with its heap+DOM creations+mutations in `g_boot_delta`. Boot's own `if(__FLAGS.admin)` FORKS a true-arm sibling boot flow in the same run (the primary keeps the canonical logged-out delta). `g_bundle_id` is computed synchronously by a pure Lexbor `<script>` scan, independent of boot execution, so the host reads the frontier key before init returns. A separate non-forking boot pass, or a gate-exploration driver separate from the one boot flow, is a regression. A guarded init (`if(!window.d){window.d=src}`) re-fires because the global is absent at the baseline — no special-casing. A boot-time `.then`/`await` continuation is a first-class async flow with an intact suspended snapshot. For a reply-GATED branch to fork WITH its example, the fetch-initiating scope RE-RUNS as a forking starter when the reply is provided — reply provision enqueues a forking boot re-run, not just a promise resolution.

# Time-travel resume — suspend and resume a snapshot
- **A parked flow is SUSPENDED as a snapshot and RESUMED from it — the same execution continued, byte-identical, at any loop depth or `await`.** The snapshot is the flow's per-flow COW delta (its heap + DOM writes) plus its suspended heap-frame chain (`JS_FlowResume`). The snapshot IS the continuation: restore it and continue from the exact suspension point. Suspend holds the flow at ~zero CPU; resume picks it up unchanged.
- **The frontier persists as suspended snapshots across sessions.** Hot snapshots live in RAM; under RAM pressure the cold low-value tail serializes to IDB and resumes on demand. A browser restart resumes every parked flow from its snapshot by global value-order — a high-value flow suspended last week resumes ahead of a low-value fresh one today.
- **A resumed flow re-derives example VALUES from CURRENT sources** (fresh `fromReply`), so it reflects the live API surface — the point of the tool. The snapshot carries the flow's own path and state; the concrete data values track today's server.
- **OOM / paging:** snapshot/restore is ONE primitive — suspend/resume, eviction, per-arm isolation. RAM holds the hot working set; the cold low-value tail serializes to IDB as suspended snapshots and resumes on demand. Disk is the platform FLOOR. BFS extracts the productive breadth first, so disk-pressure touches only the least-valuable suspended tail. **AND THERE IS A THIRD CATEGORY BESIDE CAP AND FLOOR, WITHOUT WHICH THIS ENGINE CANNOT RUN FOR A MONTH.** A cap decides work will not happen and is banned; a floor relocates work and is honest; a RE-DERIVABLE entry is work whose RECIPE outlives its bytes, and discarding one truncates nothing — so it is neither. The arithmetic that forces the category: the frontier is the union of every flow from every origin ever visited and is NEVER RESET, the store is an origin-scoped quota, and the quota answer is an always-fatal `CHECK`. Monotone growth against a fixed ceiling with a crash at the top is correct for a research engine and wrong for the thing this is — a browser extension that must survive continuous ordinary browsing, which is the whole product. The resolution is NOT a cap and NOT a reset: a recipe is (path, reward) plus its decision vector, and a resumed flow already re-derives its example VALUES from CURRENT sources — so wherever the DOCUMENT can be fetched again the flow can be BUILT again, and shedding its stored bytes converts storage into recomputation instead of into lost work. **AND THE TIERS ARE NOT ALIKE, WHICH IS WHAT DECIDES THE SHAPE OF THE ANSWER.** RAM pressure RELOCATES — the tail moves to disk and nothing is decided, because there is somewhere to put it. Disk has no next tier, so at disk the question changes character entirely: not "where does this go" but "does this deserve the space it is in". That is a RELEVANCE question and it is COMPARATIVE — never keep a document where a more valuable one could be in its place. Which makes it the WFQ's question and no other: the resident set is the STRICT PREFIX of the one value order, kept until the share is spent. Not a best fit, which would keep a small low-weight document over a large high-weight one and is a packing heuristic standing beside the scheduler rather than its answer; not an age; not a count; and not a policy of its own, because once the share is chosen there is nothing left to ask that the ranking does not already answer. **AND THE SHARE IS A PREFERENCE, NOT A CEILING.** How much of a person's device this tool should occupy has no engine-side answer — it depends on the device and the person — so it is configurable, defaulted from what the device reports, and a quota crash is not a thing that should exist: the extension origin is exempted (`unlimitedStorage`) so the platform stops being the constraint, and what remains is a choice rather than a wall. A share is not a cap in §NO BOUNDS' sense: a cap decides work will not HAPPEN, a share decides how much of the work already done is STORED rather than RE-DERIVED, and MEMBERSHIP of the frontier is untouched at every setting, zero included. Re-derivability is then a TIEBREAK on what leaves first and never a gate on whether anything may — the stakes are one re-fetch. The one residue that is not tradeable is the unrecoverable copy (an address naming bytes rather than a server, a principal its address does not state, a caller-assembled inventory): where the tail below the line is all of that, residency STOPS and REPORTS the overage, because a preference about disk is not worth the only copy of work nobody can recompute.

# @S — the PoC is CONSTRUCTED from the running code and PROVEN by firing
- **The breakout is DERIVED from the parsed sink context for EVERY sink class — no fixed payload table.** HTML breakout from the real Lexbor parse context (`solve_html.c`: the HTML §13.2.5 Tokenization state the tainted bytes landed in decides the MINIMAL exit its own transition table defines); JS breakout from a real lexical-context detector (`solve_js.c`: the hole's ECMAScript §12 ECMAScript Language: Lexical Grammar state — string, template, comment, regexp — decides the minimal escape). Both read the string a REAL re-execution handed the sink, never the value's display shape — which is the transform-expression §Re-execution forbids and cannot see the filter that moved, dropped or re-encoded the bytes. The old fixed lists are DELETED. The only residual fixed vectors are single-context sinks (a URL sink IS `javascript:`, a `<script src>` IS an attacker host).
- **Three runtime observations construct it, solved JOINTLY** (path ∧ context-breakout ∧ filter-survival ∧ FIRING): (1) the SINK PARSE-CONTEXT grammar — parse the sink output with the real parser for the exact context the tainted byte lands in, honoring the parser's own decoding (entity/URL/JS-unescape) and mXSS mutation; (2) per-flow CHARACTER/SEGMENT PROVENANCE through the real filter — which bytes survive to which positions and in what form (dropped/escaped/case-folded/re-encoded/moved/split), observed per re-execution (never a static transform-expression, which cannot see a config-loaded allowlist), so breakout bytes are placed where they survive in the surviving form; (3) the path VALUE-DOMAIN so the same input passes every gate en route.
- **ONLY FIRING proves it** — require X9 to actually CALL, not merely appear: `onerror` on an empty `src` never errors, `innerHTML` does not execute `<script>` yet DOES fire `onerror`/`onload`, a `javascript:` URL needs navigation, `setTimeout(str)` evals. The firing vector is chosen per sink from its real semantics, auto-firing (parse-time) preferred over interaction-required, and stated honestly. Absence of a PoC is NEVER a "safe"/"verified:false" verdict (a custom input may still break a gated sink) — only search-not-yet-solved, a PARKED @S flow (never a terminal `@WHY`). Constrained sinks are solved by forced-exec search GUIDED BY THE GATE: the concrete strings the page tests tainted input against are an OBSERVATION a candidate run makes on real operands, composed onto the next candidate — never a guessed token list and never read off a static shape of the expression. **AND A CANDIDATE KILLED BY A GATE MUST BE DISTINGUISHABLE FROM ONE A FILTER ATE AND FROM ONE THAT WAS NEVER SCHEDULED**, because a search cannot be directed toward a gap that it reports with the same number as two other gaps — three states behind one answer is the defect that keeps arriving in the instrument built to end it, and the tell is a rung whose ABSENCE and whose ZERO read alike.
  The search is DISTANCE-DIRECTED, and that phrase makes two claims a reader must be able to falsify separately. **(i) EVERY RUNG HAS AN OBSERVATION SITE STRICTLY BEFORE THE THING IT IS A DISTANCE TO.** A fitness of {filter-survived, sink-reached, context-escaped, handler-fires} whose sites all sit at or past the sink is not a distance at all, it is the outcome restated — a candidate that carried the attacker's bytes nine tenths of the way is then worth exactly what an unstarted one is, and "distance-directed" is true of nothing while every word of it stays in the spec. **(ii) A REWARD IS A LEDGER AND A FITNESS IS A COMPARATOR, AND WRITING THE SECOND INTO THE FIRST DESTROYS IT.** A ledger records what was LEARNED, so it is paid at most once per observation or it reorders the frontier on repetition. A comparator states where an item STANDS NOW, so it must be readable off EVERY item, including ones standing exactly where an earlier item already stood. Pay a distance into the ledger and the rule that keeps the ledger honest is precisely the rule that erases the comparison: the first candidate to travel nine tenths is paid for it, every later candidate that travels the same nine tenths is paid nothing and ties with a flow that never started, and "a dead candidate starves" is then false of the ONLY comparison that matters — between the candidates of one search, which is where a derivation's second, third and tenth breakouts live. So the distance is held PER FLOW, never accumulated, written as a reading rather than a payment, read at the pick, monotone (a flow's payload is fixed, so a lower later sample is another look at the same question and never a demotion), bounded by the optimism term's own range so a PROMISE never outweighs a FINDING, carried by a fork like every other weight term, and re-earned rather than resumed across a park because a distance is an observation of a re-execution this session made. A near-miss is mutated toward the gap using the byte-provenance the run already measured — which segment died and where the rest landed — and **an observation with a computed writer and no reader is not a mechanism**: the mirror of the read-with-no-writer defect, and harder to see, because the value is real, asserted, and consumed by nothing.
- **Cross-flow shared state is solved by re-running the state-producer under the candidate before the sink:** boot re-run (source stored at boot, sunk in a handler), closure re-resolution (drive by source identity, not the stale captured closure), and an attacker-SESSION flow (source stored by handler A, sunk by handler B — one flow fires all handlers in seed order over one accumulating COW delta, then a candidate-session re-fires). A source stashed in a DOM attribute keeps taint via an `(element,name)→opaque` shadow map (Lexbor would ToString it away).
- **A firing breakout in the model is NOT yet a working exploit.** (a) EXECUTION ENVIRONMENT: the PoC must run under the page's ACTUAL policy — CSP (an inline `onerror` is dead under `script-src 'self'`: pick a policy-permitted vector or record "sink REAL, CSP blocks: needs X", never a bare XSS), Trusted Types (an `innerHTML` sink throws unless a policy stringifies), SRI/nonce/hash — read from fetched headers + `<meta>`, confirmed by the sink actually throwing/executing on real Chrome. (b) STORED/second-order is a TWO-STAGE PoC (the plant + the victim load that fires, with ordering and both deliveries), carried by the parked-flow machinery. (c) The attacker value GENERALISES beyond a string — DOM-CLOBBERING (`<form id=cfg>` flips a later `fetch(cfg.url)`) and PROTOTYPE-POLLUTION (a downstream gadget reads `__proto__[x]` into a sink), which the engine solves because it RUNS the gadget a template/SMT never sees. (d) Emit the STRONGEST working input per sink, each carrying its reproduction envelope (browser, needs-a-click, is-stored, required CSP/TT state). (f) A shared sanitizer is characterized once and reused, ALWAYS re-verified by re-execution (never trust-without-running).
- **LIVE VERIFY = ENGINE AGREEMENT:** the engine's exact PoC (its X9 fire-marker → `apiclientsink`) is delivered to the real page in a sandboxed attacker popup via the same URL/postMessage delivery the engine models. A hit = ground-truth real exploit; no hit = an engine-fidelity divergence to fix. Never a re-derived PoC.

# Attacker sources, values, and discovery
- **Each attacker source is defined with its intrinsic BROWSER constraints** (the engine is a real browser except forced-execution). `message.origin` is a valid origin the attacker controls by registering a domain, so a forgeable check (`endsWith`/`includes`/`startsWith`) is SOLVED (surface the required origin) while an unforgeable one (`===` exact) is unsatisfiable cross-origin and SUPPRESSES the finding — never a false PoC, never a dropped real one. `location.search` and `location.hash` are percent-encoded by the browser per the WHATWG per-component sets (verified on Chrome: both encode `< > " space`; the FRAGMENT additionally encodes backtick and NOT `'`, the special-QUERY encodes `'` and NOT backtick) — so a raw-hash HTML breakout is a FALSE PoC unless the app decodes it, but a JS-context breakout (`';X9();//`) is a REAL raw-hash XSS with a source-specific char-set. Deliver each candidate through the source's real browser transform (encode the search candidate, prefix the hash, structure the pm object) so re-execution decides breakout faithfully. Completing this per source (cookies, referrer, `name`, IndexedDB, form values) is the frontier — a source without its constraints yields PoCs that don't reproduce.
- **RUN, DON'T MATCH. COMPUTE OR SHAPE, NEVER INVENT.** Values are what QuickJS computes — no regex/name/identifier matching, scoring, heuristics, or bundler recognition (code is minified; names are meaningless). A value known only to satisfy a range/prefix/regex gate is INVENTED, not computed ⇒ a domain-annotated shape (`{int>5}`), never a concrete pick; only an equality-pinned or run-computed value is concrete. A missing value = a missing host-edge stub or opaque-infectious `OP_*` transfer, never a parallel resolver or re-implemented language feature. Forms/custom-elements are learned by EXECUTION (`.submit()`, `connectedCallback`), never by reading a DOM attribute.
- **The symbolic/trust boundary decides WHICH values carry a learnable example; a SHAPE for an APP-OWNED value is a DRIVING FAILURE.** Genuinely external / attacker input AND server-injected absent state (`window.__USER`/`__FLAGS`/`__NEXT_DATA__` — absent app-state is unknown injected input, so the read is SYMBOLIC and the auth gate FORKS to the logged-in arm, never a concrete `undefined` that buries the admin code) stay symbolic (domain-carrying, example-free), must never force a branch, and legitimately lack an @H example. But the app's OWN same-origin resources are TRUSTED ground truth to LOAD, never a shape: a fetch whose body is JAVASCRIPT is ALWAYS fetched + EXECUTED (a lazy chunk reveals real endpoints — the headline moat surface); a config/data fetch is ALWAYS loaded so its fields become concrete examples, while its use in a BRANCH still forks (a loaded `features.admin:false` must NOT concretize the gate, or the admin endpoint is lost — config is opaque-for-control-flow yet carries its loaded value as the example). `location.origin`/`host`/`protocol` (the principal) is concrete for URL building. A fully-opaque app-owned URL is a FATAL `@WHY` to fix, never a placeholder. Iterating an opaque collection FORKS unbounded (each iteration a parkable flow) — never "driven once" (a banned seen-set), yet it behaves like once because the identical-input tail emits nothing new and is outranked+paged.
- **Active discovery is REQUIRED** (lazy scripts + discovery docs + Google API `req2proto` error-probes) — passive learning is too thin. Each active fetch is made FROM the document that learned the endpoint, CORS-bounded both ways, one-per-endpoint (a method's safety is a PROTOCOL CONTRACT and never a URL shape — see the safety rule below), never a blind sweep. Endpoints learned from runtime fetch/XHR hooks instead of QuickJS mean the core forced-exec is underperforming — fix the driving. Static assets are NEVER endpoints (magic-byte + content-type, not URL suffix) but still drive the code path. A request whose METHOD is outside RFC 9110 §9.2.1 Safe Methods' safe set is NEVER fired to learn — its example values come only from the local forced-exec path (that server-side-effect surface is the frontier where forced execution derives the request WITHOUT firing).
- **A REQUEST CARRIES THE PROVENANCE OF ITS VALUES AND A REPLY INHERITS IT — the rule above asks about the METHOD, which is only half the question.** Forcing exists to reach code a real session would reach and this one did not, so the requests it builds are exactly the ones no real client makes — and that cuts two ways at once, which is why one answer cannot serve both. **The CONSEQUENTIAL half** is what firing does to the world. **The EPISTEMIC half** is what the reply is worth, and it is the half nothing here has been asking. Three provenances, and every outbound request states which it is: **OBSERVED** — the page made this request, or would have made it on the path real values take; **DERIVED** — the real code computed it from real inputs (a concat of the real origin and a real path), so it is a fact about the app even where no session sent it; **FORCED** — a value exists only because a gate was forced, an equality pinned an arm the run did not take, or a range was satisfied at all. A reply to a FORCED request is evidence about what a server says to a request no client makes, and **it is under §@H's own rule — it must NEVER be reported as OBSERVED**, because the failure is not that it is useless but that it is PLAUSIBLE: a 401 body parses as JSON and yields fields that exist nowhere, an error envelope becomes a config, and the fabrication then PROPAGATES, since one invented field is the example that shapes the next endpoint. That is the same defect as inventing `6` for `x>5`, one network hop out, and it is worse there because a server supplied the bytes and nothing in them says they are an answer to a question nobody asked. So a forced reply's values are learned and CARRIED AS FORCED, never merged into the observed pool; a reply whose status denies the request (401/403/redirect-to-login) is evidence the FORCING failed and never evidence about the surface behind the gate. **AND THE FIRING DECISION IS A POLICY IN THE TRUSTED ZONE, NOT A BRANCH IN THE ENGINE** — the engine holds no network policy by construction, so `safeFetch` decides, from the provenance the request declares beside its method and credential state. **IT IS CONFIGURABLE AND PER-ORIGIN, BECAUSE EXPERIMENTATION IS NOT ALWAYS WRONG AND A SINGLE SWITCH CANNOT SAY SO**: firing forced requests at an app you own or a staging host is the point of the tool, and doing it against a stranger's production account is not, and both are true for one person on one afternoon. Default conservative, widened deliberately per origin, never inferred from a site looking like a test. **ONE COMBINATION IS NEVER A SETTING: credentialed AND state-mutating AND forced.** That is not experimentation — it is acting as the user, on a request they never made, with values their app never produced, and no configuration makes that a thing this tool does. Its correct output is the one the rule above already names: derive it in full, report it, do not send it. A derived-and-unfired request is not a gap in the report, it IS the report — that surface is precisely what forced execution can find and a sniffer cannot.
- **"IS THIS REQUEST STATE-MUTATING" IS NOT A QUESTION A CLIENT CAN ANSWER, AND REACHING FOR A URL SHAPE TO ANSWER IT IS §RUN-DON'T-MATCH PERFORMED ON AN ADDRESS.** RFC 9110 §9.2.1 Safe Methods defines safety by what the CLIENT REQUESTS AND EXPECTS — "the client does not request, and does not expect, any state change on the origin server" — and then says the quiet part outright: an implementation MAY include behavior "that is not entirely read-only, or that causes side effects while invoking a safe method", and "what is important, however, is that the client did not request that additional behavior and cannot be held accountable for it." It puts the duty on the other side by name: "it is the resource owner's responsibility to ensure that the action is consistent with the request method semantics", and the very counterexample this file used to cite AGAINST the rule — a delete behind a query parameter — appears there as the resource owner's failure, which they MUST disable under a safe method, precisely because "automated processes perform a GET on every URI reference". So the engine does not ask the unanswerable question. It asks the one it can answer exactly: **DID THIS CLIENT REQUEST A STATE CHANGE** — the METHOD (§9.2.1's safe set is GET, HEAD, OPTIONS, TRACE) conjoined with the PROVENANCE of its values, and nothing else. **AND THIS IS WHERE PATTERN MATCHING IS ALLOWED — THE ONE PLACE, AND ONLY IN THE DENY DIRECTION.** §RUN-DON'T-MATCH bans matching because a name is meaningless in minified code and a matched name would be ASSERTED as a value; a DENY LIST asserts nothing. It REFUSES, and the two directions fail in opposite ways that are not comparable: a wrong deny costs ONE unfired request that forced execution still derives and reports in full, while a wrong assert fabricates a finding that propagates, since one invented field is the example shaping the next endpoint. So a deny list over an outbound request — `/logout`, `/signout`, a session-clearing path, anything that looks like it revokes or destroys — is SOUND PRECISELY BECAUSE IT IS ALLOWED TO BE WRONG, and the accidental logout is exactly the class it exists to stop: a GET that ends the person's session mid-analysis is a CSRF this tool committed against its own user, and no amount of §9.2.1 correctness makes that acceptable to discover afterwards. What stays banned is the INVERSE READING — a path that does NOT match the deny list is not thereby established safe, and no match may ever license firing something the provenance rule refuses. The list is a floor under the policy, never a substitute for it. **AND IT IS A FLOOR UNDER OUR OWN AUTONOMY ONLY — IT MUST NEVER APPLY TO `pageContextFetch`, AND THAT IS A RULE ABOUT WHO ACTED RATHER THAN ABOUT WHICH TRANSPORT CARRIED IT.** The whole soundness argument above is that a deny list is ALLOWED TO BE WRONG, because a wrong deny costs ONE unfired request forced execution still derives and reports in full. That arithmetic INVERTS the moment a human composed the request: the page-context relay carries an address an operator typed at a surface that showed them the address, the verb and the body, so a token list standing there is not a floor under this tool's autonomy, it is the tool VETOING ITS OPERATOR on a substring they never saw and cannot argue with — and the cost is no longer one unfired request but a person told their own explicit act was blocked. SECURITY.md's egress taxonomy already grades that path as authorized by a human at a surface that shows them the bytes, which is the strongest grade in this project; a token list is the weakest, and the weak one does not overrule the strong one. This was BUILT ONCE AND REMOVED, on facts that are every one of them TRUE and led to the wrong conclusion — the list is scoped inside `safeFetch` so a request never reaching that file is outside its scope; the relay is credentialed by construction; two of its three entries name POST, which §9.2.1's safe set excludes. All three are about the REQUEST and none about WHO DECIDED TO SEND IT, which is the entire error and the reason it will be re-derived. So a reader who finds that relay ungated has found a DECISION, not a gap, and the honest response to "one sanctioned transport stands on no floor" is that the floor under an operator's act is the operator seeing it. **AND AN EXEMPTION SCOPED BY WHO ACTED IS SCOPED BY A FACT THE EXEMPTING SITE CANNOT SEE, SO IT IS CARRIED AND ASSERTED OR IT IS NOT SCOPED AT ALL.** That is the half this paragraph got wrong, and it got it wrong in the most durable way available: by describing the CALL GRAPH. It said the relay's entries were operator-typed or an operator-initiated probe, which was a claim about which functions happened to call which, written in a file where nothing could check it — and it was FALSE of three callers the whole time it stood, each firing the instant a captured response body arrived, each credentialed by construction, two of them POSTing a body the app never produced. The relay could see the URL, the verb, the headers and the body, and those are IDENTICAL in shape whether a person typed them or a response handler composed them; so there was nothing there to notice, and the exemption quietly covered the exact population it was argued not to cover. **THE DEFECT CLASS IS AN INVARIANT WHOSE SUBJECT IS ABSENT FROM THE SITE THAT RELIES ON IT** — every other rule in this file about a fact that must travel (the browser-stated principal, the request's provenance, the sender's origin on a delivered message, the initiator here) is the same shape, and the cure is always the same one: the fact is a VALUE stated by the site that knows, carried down every frame, and asserted where it is relied on, never re-derived and never inferred. The tell that you are writing one: the justification for a privilege is a sentence about who the callers are. **AND THE CALLER THAT CANNOT STATE THE FACT IS THE POINT, NOT THE FRICTION.** When the grade became a required value, the three automatic callers had nowhere to go — the chokepoint enforces §9.2.1 STRUCTURALLY, by hardcoding `GET` and reading neither the method nor the body, so a POST error probe cannot be routed there and must not be given a way — and that is the correct outcome rather than an obstacle: the capability moved to the grade entitled to it (a button naming the endpoint), the automatic form was DELETED rather than exempted, and the reach that was genuinely lost was reported as lost. An unstated value takes the same arm as the refused one, so forgetting is not a way to be exempted. **AND IT LIVES IN `safe-fetch.js` WITH EVERY OTHER RISK DECISION** — the engine holds no network policy by construction, so the deny list, the credential choice and the firing decision are ONE policy at ONE chokepoint, and a second copy inside the engine would be the layering violation §Learning-from-replies already names. What the engine owes instead is honesty about what it LEANED ON: a fired safe-method request rests on §9.2.1's contract, and a finding derived from one states that it PRESUMED rather than implying it verified. That presumption is exactly what the per-origin setting above configures, because whether a given app honors the contract is the one thing its owner knows and the engine never can.
- **A REAL NAVIGABLE IS A LEGITIMATE INSTRUMENT, AND THE LINE IS NOT MODELLED-VERSUS-REAL — IT IS WHOSE PRINCIPAL THE NAVIGATION CARRIES.** An earlier form of this rule said exploration must never materialize a real browsing artifact. That drew the line on the wrong axis and foreclosed the capability this tool exists for: a bundle NAMES pages a person never visits — a route only its own router knows, an admin view no link reaches — and reaching them is §What-the-tool-produces' whole subject ("what the bundle CAN do but didn't"), while §LIVE-VERIFY already calls a real fire "ground-truth real exploit" and delivers it through a real popup. A real artifact was therefore never the forbidden thing, and a rule that banned it was protecting nothing while costing the product its reach. What is forbidden is ACTING AS THE PERSON WITHOUT THEIR SAY, and exactly one property decides that: a top-level navigation in their profile carries their cookies, which is what lets a real tab perform an account action and learn a credentialed reply no logged-out client could see — the two hazards §provenance names, arriving through the browser instead of through `fetch`. So the instrument is one of the CUSTOM BROWSER'S OWN TABS. **ITS TABS AND WINDOW REFERENCES ARE ITS OWN CONCEPT AND HAVE NOTHING TO DO WITH CHROME'S** — no `chrome.tabs`, no browser window, no handle that outlives the engine that made it; a navigable dies with its agent, which is why nothing here needs a durable tab record, a browser-session epoch or a startup reconciliation, and why an earlier version of this bullet that reached for all three was answering a question that does not arise. **EVERY ONE OF THEM LOADS THROUGH `safeFetch`** — there is no second transport, and the chokepoint SECURITY.md names has NO carve-out for navigation. **AND EVERY ONE OF THEM SENDS COOKIES**: `safeFetch` supports credentialed loads, and a SAME-ORIGIN navigation carries them, exactly as a browser's does. There is no credential-free context, no partition, no incognito, and no interception — `declarativeNetRequest` is not used in this project at all. That is not a concession extracted from the design; it is what makes a tab worth having and what keeps it honest. A SESSION-LESS TAB IS A THIRD THING THAT MODELS NOTHING: not the person's browser and not a clean client, served a bundle the person will never be served, producing findings that do not reproduce for them — which is exactly what §Attacker-sources means when it says a source stripped of its real constraints yields PoCs that don't reproduce. And a credential-stripping rule would be a GUARD where §Fix-the-ROOT wants an impossible state — safe only while installed and correct, with the window between the tab and the rule as the harm — while placing a NETWORK POLICY where `safeFetch` cannot see it, a second policy point beside the one SECURITY.md names as the only one.
  **WHICH PUTS THE WHOLE OF THE SAFETY IN THE CHOICE OF ADDRESS, DECIDED BEFORE THE NAVIGATION, WITH NO SECOND LINE BEHIND IT.** That is a stronger claim than it looks and it is what the rest of this bullet rests on. A TAB IS A VISIT, NOT AN EXECUTION SURFACE: forced execution happens in the WASM sandbox, and a tab exists to obtain a document and to host §LIVE-VERIFY, so a legitimately-chosen address makes a real tab exactly what it appears to be — this extension visiting a page the way the person would. A top-level navigation is a GET, which RFC 9110 §9.2.1 Safe Methods' safe set contains, so the METHOD half is already answered and the entire remaining question is PROVENANCE. An OBSERVED or DERIVED address is one the app's own code computed from real inputs and a person could have reached, and it is navigated freely — that IS the capability: reaching what a bundle NAMES and no link exposes. A FORCED address is the deliberate per-origin widening, and its reply is carried as FORCED and never merged into the observed pool, because a CREDENTIALED reply to a navigation no client would make is the plausible fabrication §provenance is entirely about. A navigation whose provenance is not established CRASHES at the decision rather than proceeding: with no partition and no interception there is nothing downstream to catch it, so the assert belongs at the only control point that exists. The forbidden triple is unchanged and is now reachable by exactly one route — the address. **AND "ALL NETWORK VIA `safeFetch`" STAYS LITERALLY TRUE, TRANSPORT INCLUDED.** A navigation is a LOAD like any other and goes through the chokepoint; an earlier form of this bullet carved navigation out of that invariant and reread it as a statement about the DECISION rather than the transport, and that was the whole of the error. What would create a second transport is reaching for a BROWSER-DRIVEN tab, and that is the inversion it looks like: every guarantee `safeFetch` makes is decided at its call site — the scheme allowlist, the SOP/CORS gate, PNA on the initial AND the post-redirect URL, CORB by expected type — so a path that skips them is not a more faithful browser, it is an UNPOLICED one. The custom browser's own tab is the faithful one precisely because its bytes come through the same door as every other byte.
- **A DOCUMENT REACHED IN A CYCLE DOES NOT BREAK THE SCHEDULER — IT IS THE CASE THE WFQ IS FOR — BUT THE ADDRESS-VARYING CYCLE DEFEATS THE ARGUMENT THAT SAYS SO, AND THAT DIFFERENCE IS THE WHOLE ANSWER.** A page that frames a page that frames it back, or a page a person opens ten times, APPENDS flows to the ONE frontier — it starts no scheduler, no run and no counter, so there is nothing there to break. A cycle over the SAME address is then handled by the mechanism that already handles iterating an opaque collection: the repeat emits nothing new, the reward term stops paying, CPU-aging sinks it beneath productive and unrun work, and it pages to the cold tier — OUTRANKED, never terminated, and a seen-set to "fix" it is the banned cap. **The cycle that varies the ADDRESS is a different shape and must not be waved past with the same sentence**: a cache-busting query makes every turn a NEW document identity whose first visit legitimately emits, so "the identical tail emits nothing new" is simply FALSE of it and the demotion argument does not apply to it at all. Its answer is the one the disk share already gives — residency is the STRICT PREFIX of the one value order, so a cycle's near-identical documents compete on VALUE against everything else and lose residency as their marginal emission decays, while MEMBERSHIP is untouched. And membership stays affordable for the reason the re-derivable category names: a child address a loop COMPUTED is re-derivable by re-running the parent that computed it, so shedding a generated recipe converts storage into recomputation and truncates nothing. What such a cycle genuinely threatens is neither the queue nor the disk but the REALM CEILING — it is the sharpest generator of per-flow navigables there is, which makes it the FORCING FUNCTION for §7.3.1.6 Navigable destruction's destroy-a-navigable, never a reason to bound the loop.
- **PASSIVE AND FORCED DISCOVERY COMBINE AS A COMPARISON AND NEVER AS A MERGE — and the merge is the tempting one, because it makes the report look FULLER while the solver gets WORSE.** "Passive discovery" names two things that must not share a fate, and separating them is the whole of the design. **WHAT THE PAGE'S OWN TRAFFIC REVEALS IS A THERMOMETER, NOT A SOURCE.** A passively observed endpoint is OBSERVED by construction — the page made that request — so pooling it with a derived one yields a single list in which this tool's own contribution is UNMEASURABLE, and §What-the-tool-produces already says why that is fatal: `netdiff --unused` is a DIAGNOSTIC that the solver dominates the live page, NEVER the optimization target. Merge them and the diagnostic reads the union of itself — an instrument measuring its own input — so the number rises, the driving rots, and NOTHING SAYS SO. That is the plausible-datum defect performed at the level of the product rather than a field. The rule above already fixes the direction: an endpoint learned from a runtime fetch/XHR hook rather than from QuickJS means the forced execution UNDERPERFORMED, so the passive channel's entire worth is that it can EMBARRASS the solver, and a design that merges it away has spent the only measurement that could. **WHAT A PERSON'S BROWSING REVEALS THAT NO SOLVER CAN DERIVE IS WHICH DOCUMENTS EXIST.** A solver explores the bundle it was handed; which origins someone reaches, in which app, behind which auth state, is not a fact inside any one document — so it is not a finding the forced execution failed to make, it is the SEED. That is the half an ambient host is worth keeping for, and it enters the ONE frontier as a document to explore, ranked like any other flow. **A SUGGESTION IS A WORK ITEM, NOT A FINDING**: passive observation may propose WHAT to explore and may never arrive in the emitted surface wearing the grade of something the run derived. **AND A SEED IS AN ADDRESS, NEVER BYTES — an ambient host that ships a DOCUMENT BODY has built a second document-load transport, which is the carve-out §the-chokepoint-has-no-carve-out forbids, wearing the costume of a convenience.** The failure is not duplication, it is that the second path is UNPOLICED BY CONSTRUCTION: bytes fetched in a content script are fetched in the page's own realm, with the person's cookies, reaching `safeFetch` never — so the scheme allowlist, the SOP/CORS gate, PNA on the initial and post-redirect URL, CORB by expected type and the destructive-path deny list all apply to the engine's own navigations and to nothing that arrives this way. It is also a SECOND CREDENTIALED FETCH of a document the person already loaded, which can legitimately answer differently (cache, nonce, personalised SSR, rate limit), so it does not even buy the observed bytes it appears to. What an ambient observer knows that nothing else can is exactly ONE FACT, and it is an address: **the URL the browser actually NAVIGATED to**, which `PerformanceNavigationTiming.name` states and which `history.pushState` cannot forge — the distinction that matters for an SPA, whose `location.href` is a client route the server would 404. Ship that, and the custom browser loads it as an HTML §7.4 navigation through the one chokepoint, with the policy read off the reply exactly as §7.4 step 14 requires. A justification that the content script's fetch uniquely sees response headers is FALSE where a host-permission fetch reads every header, and a rule kept alive by a reason that has stopped being true is the stale-comment failure with a network path attached.
- **AND ONCE THE SEED IS AN ADDRESS, THE SEED IS PER-ORIGIN AND NOT PER-VISIT — WHICH DECIDES THE VEHICLE.** Forced execution from an app's INDEX page reads the bundle, and the bundle NAMES the routes no link exposes, so one entry point per app yields the hidden pages, their endpoints and their sinks. That is the capability, and it means the frontier does not need a stream of every page a person opened — it needs the list of apps, which a person can state, paste, bookmark or import. **So an AMBIENT host is a very expensive way to deliver a string.** Weigh it honestly against what it costs, and the costs are measured rather than argued: a single-threaded WASM instance has no CPU clock and cannot be interrupted mid-call, so §scheduler's cooperative quantum — which that section calls REQUIRED and universal — has no asynchronous budget source at all; the SharedArrayBuffer that would supply one cannot be transferred into an opaque origin at ANY manifest setting, and the COOP flip that would change that severs the opener §LIVE-VERIFY needs; wasm32's address ceiling sits below the frontier's live allocation, so the ASan §Architecture prescribes by name cannot run on the shipped program; and a process boundary must be rebuilt inside a document because two instances in one realm are a namespace rather than a sandbox. Against that, the ambient half buys BREADTH someone would otherwise curate — a convenience, not a capability, and one a minimal feeder that ships only ADDRESSES can supply without any of the above. **The engine's home is therefore the host that gives it real threads, a real CPU clock, a real `fork()` and a real sanitizer; a browser vehicle is ONE host among several, driven through the same ABI, and never the thing every design decision is priced against.** What it must NOT become is a second engine: one ABI, one scheduler, one frontier, whichever host is running.
- **A SELF-SEEDED DOCUMENT IS A WORK ITEM ON THE ONE FRONTIER, AND THE ONLY THING THAT MAKES IT DIFFERENT FROM A FLOW IS THAT IT SPENDS SOMEONE ELSE'S SERVER.** Discovery that walks from an index page generates ADDRESSES, so the cycle question §a-document-reached-in-a-cycle answers arrives here by construction rather than by accident, and the answer is unchanged: ranked by emitted value, outranked when it stops emitting, resident as a strict prefix of the one value order — never a visited-set, a crawl depth, a page budget or a same-URL check, all of which are §NO BOUNDS' caps wearing a crawler's vocabulary. **RE-FETCHING AN ADDRESS IS NOT THE DEFECT AND MUST NOT BE PREVENTED**: §Time-travel-resume REQUIRES a resumed flow to re-derive its examples from CURRENT sources, and the re-derivable tier converts stored bytes into exactly this recomputation, so an engine that refuses to fetch an address twice has broken both. What the ordering owes the other side is that an outbound request is an EXTERNAL EFFECT and therefore a cost the WFQ carries like any other, so an unproductive document sinks beneath productive work instead of being re-fetched at the same rank for ever — the same starvation mechanism, applied to the one work item whose cost is not ours to spend. The UI that presents any of this is a SEPARATE AXIS and decides none of it — a surface can render both columns, and which host collects them is not a question about how they are rendered. **AND THAT CEILING IS THE SAME DEFECT WHETHER THE NAVIGABLE IS REAL OR MODELLED, so refusing real ones does not fix it — it only changes which resource runs out**, and the modelled resource is the engine's while the real one is the PERSON'S. That asymmetry does not make the cycle a different problem; it makes reclamation load-bearing sooner, and it is why destroy-a-navigable is the root fix rather than a policy about which kind of navigable exploration may build.
- **Bind before build:** source a missing Web/spec capability host-runtime (JSPI) → engine intrinsic → existing Lexbor module → faithful spec port → hand-roll last (never crypto/parsers from scratch). APIs must follow their IDLs; nothing may be opaque. APIs work regardless of multiple tabs/windows (cross-WASM chains), a real permission system, plugged-in speakers, or a real filesystem via virtualization. Treat the browser as REAL — permission-gated APIs, URL params, FSA, popups, iframes — or the project can't be made; virtual systems (their own component) let forced execution reach more code (an FSA file containing XSS).

# Security → SECURITY.md
Authorization keys on `sender.tab.url` (never `sender.id`/`msg.*`); credentialed-read PRINCIPAL = `MessageSender.origin`, never URL-derived; content script + website + QuickJS/WASM bundle are UNTRUSTED, the offscreen is the only trusted zone — BUT THE ENGINE DOES NOT RUN IN IT. `bridge.js` says so in its own first paragraph ("NO ENGINE LIVES IN THIS REALM"): every instance is a RENDERER, an `<iframe sandbox="allow-scripts" src="renderer.html">` whose unique OPAQUE ORIGIN is the security boundary, reached over a mojom interface. Measured consequence: `self.crossOriginIsolated` is FALSE in that frame at both COOP values and with the sandbox attribute widened or removed, so a SharedArrayBuffer cannot be TRANSFERRED to it and the wasm host cannot have a watchdog thread. Pricing anything against the offscreen prices the wrong document; one WASM instance per ORIGIN-KEYED AGENT CLUSTER — `(browsing-context group, origin)`, which is what SECURITY.md §The QuickJS/WASM sandbox is attacker-controlled states and is NOT "per document", the wording that stood here and contradicted the bullet directly below it; ALL network via `safe-fetch.js` or `pageContextFetch`; state in the offscreen + IndexedDB (`chrome.storage.local` banned). Tabs may hold cross-origin documents.
- **AN INSTANCE IS AN ORIGIN-KEYED AGENT CLUSTER — `(browsing-context group, origin)` — because that IS the spec's heap boundary, and ACROSS one THE COW DELTA SYNCHRONISES.** Two same-origin documents in one browsing-context group are ONE similar-origin window agent: HTML puts them in a single heap and then RELIES on it. `iframe.contentDocument.body.appendChild(subframe)` inserts a node THIS document created (§4.5 adopt, then the insertion steps), so `subframe.parentNode` is afterwards a node belonging to the OTHER document while the wrapper stays the same object; `frame.contentWindow.onunload = fn` hands the other document this agent's live closure to CALL, with a live Event going back. Those are not property reads that could suspend — they are one object graph — and passing them by NAME is an unbounded bidirectional export table with cross-boundary GC that answers `===` wrong. Splitting a same-origin pair is therefore not the stricter choice, it is the WRONG one, and refusing to costs nothing: the security invariant is ORIGIN, not document, so SECURITY.md's one-principal-per-instance still holds EXACTLY, and an origin-keyed cluster is also what makes `document.domain` a no-op — spec behavior, not a hedge. What crosses an instance boundary is then a CLOSED set — WindowProxy, Location, serialized messages — which is the whole reason the boundary is tractable and is what a real engine ships (Blink's `RemoteDOMWindow`/`RemoteFrame`). A DIFFERENT-ORIGIN document, or the same origin in another browsing-context group, IS a separate instance and may be remote; a flow touching both still has ONE world spanning them, and the delta that world is made of must apply, unapply and park across all of them — a per-instance delta that only agrees locally is two timelines wearing one name, the identical bug class as modelling async state globally. Cross-WASM COW sync is a REQUIRED mechanism, and no design may be chosen because it avoids building it.
- **A HOST THAT CANNOT PROVISION A SECOND INSTANCE HAS NOT TESTED THE TRANSPORT, AND EVERY CROSS-INSTANCE MECHANISM ABOVE IS THEN A DESIGN THAT HAS NEVER RUN.** The peer to provision is a CROSS-ORIGIN document — provisioning one for a same-origin child tests a transport that must never carry it. The world registry, the nearest-first ancestry and the lazy segment materialization can all be written, reviewed and self-tested with no peer in existence — and they were, for long enough that grep once answered "a self-test" when asked who calls them. That is the shape a cross-instance design fails in: not a wrong answer, an unexecuted one. The peer it provisions is a second WASM instance, NOT the offscreen — see §Security. The gaps this surfaces are not absence and will not look like it: one member answering from the WRONG AGENT'S RECORD (`closed`, HTML §7.2.2.1 opening and closing windows — a popup that closes itself leaves the opener answering `false` for ever), and a driver aborting on its FIRST reply because a required field was added to the reply record, so every check below that line is unreachable while the file still looks like a passing gate. So a host is not finished when it can ANSWER a cross-document read; it is finished when it PROVISIONS the peer that answers. In a process that means a child PROCESS (the same binary, re-executed with the child's name, address, origin and policy, over a pipe); in the extension it means a second WASM instance the offscreen routes to. What crosses is TEXT and it carries its TYPE, because a live JSValue crosses neither a process, nor an instance, nor a session, nor a park — and because `otherW.length === 0` distinguishes a number from the string "0". A member whose value is an OBJECT does not cross at all until the remote-object handle exists: answering one by serializing it is how a cross-document read starts returning something that is not the thing, so the encoder CRASHES there instead.
- **A PEER ANSWERS BY RUNNING A PROGRAM, never by reading a property from C.** The read it is asked for is an IDL getter, and a C activation has no flow base under it — the same rule that makes every other read a flow makes this one one, and it is also what lets an answer that has to suspend exist at all.
- **A SYNCHRONOUS CROSS-INSTANCE READ IS A SUSPEND POINT — that is what the primitive is for.** The cross-origin allowlist is not all navigable-own state: `otherW.length` is the child-navigable count of the ACTIVE DOCUMENT and `otherW.closed` tracks the peer, so a cross-origin read must answer on the line that made it while the answer lives in another instance. (Same-origin, `iframe.contentWindow.document.body` is answered in-heap in that same turn, because the two documents are one agent — a suspend there would be OBSERVABLE and therefore a fidelity bug, not extra rigor.) At the real boundary the flow SUSPENDS exactly as it suspends at an `await` or a loop back-edge, the peer instance resolves the read in its own scheduled turn under the requesting flow's world, and the flow RESUMES with the value — byte-identical, at any depth. Sibling flows run meanwhile, which is the point. A same-origin `about:blank` child (`window.open()` with no argument, an `<iframe>` with no `src`) is created synchronously by the spec, and its CSP is not a special case: every Document has a §7.1.7 Policy containers POLICY CONTAINER, and §7.3.2.1 Creating browsing contexts CLONES the creator's when there is one — clone it ACROSS the boundary like any other cross-instance state.
- **HTML §7.2.1 security infrastructure for Window, WindowProxy, and Location objects — ITS SAME-ORIGIN CHECK IS DECLARED BESIDE THE MEMBERS, never asked at the read.** A WindowProxy exposes a FIXED cross-origin list (window, self, location, close, closed, focus, blur, frames, length, top, opener, parent, postMessage) and everything else is same-origin only; a read outside it is a SecurityError, thrown at the read, because a page distinguishes that from `undefined`. The failure mode of checking per-read is SILENCE: this surface had no check at all and was safe only by the accident that the members built so far were nearly the whole list — the first one added without one would have leaked a cross-origin document with nothing to say so. An OPAQUE origin is same-origin with NOTHING, not even another opaque one, which is the same rule SECURITY.md states for the credentialed-read principal because it is the same concept. Both halves are the assertion: a filter that threw for everything passes a test that only checks the throw.
- **A cross-document message is an EMISSION, never shared mutation** — immutable once posted, so nothing has to un-send it when the sending flow parks or is outranked, and it needs no COW capture. It carries three things and each is load-bearing: the SERIALIZED bytes (never a live value — a live value crosses neither an instance, nor a session, nor a park); the SENDER'S ORIGIN stamped by the TRUSTED ZONE, never by the untrusted engine (the same rule as keying authorization on `sender.tab.url` — a forgeable `event.origin` defeats every origin check in every bundle, and would make the solver report exploits that are not real and miss ones that are); and the SENDING FLOW'S WORLD, its decision vector. Delivery SEEDS a flow in the receiver whose world is receiver-baseline ∧ that vector: two arms of a fork post two messages belonging to two contradictory worlds, and merging them fabricates a timeline neither sender was in. The offscreen ROUTES, because it is the only zone that knows which instance holds which document. No second scheduler — a delivery is a work item on the ONE frontier.

# Testing — FEATURE test262 (`node engine/test262.mjs [subdir]`) + the solver differential (`node engine/solvergate.mjs [doc]`)
- **A GATE RUN FROM THE WORKING TREE MEASURES A TREE THAT NO LONGER EXISTS.** The checkout is SHARED and edited continuously, so a build reads its inputs at different instants: `idl_args.h` gained a field 33 seconds before a link finished, `media_query_list.c` compiled `IdlDictMember` at 56 bytes and `idl_args.c` at 64, and the program segfaulted in `strcmp` inside a `DFAIL`'s own order check — a confident false red whose only symptom was a struct read one slot early. That is the loaded-machine defect one layer up: not a wrong number, a number about NOTHING, because no revision of the tree ever contained the program that ran. So a gate runs from a FROZEN SNAPSHOT — `git worktree add --detach <dir> HEAD` plus a worktree of the submodule at `HEAD:engine/qjs` — and the commit it measured is REPORTED WITH THE RESULT. **AND THE SNAPSHOT MUST BE AT A PATH NOBODY ELSE WILL CHOOSE, BECAUSE THE SCRATCH DIRECTORY IS SHARED STATE TOO AND A COLLIDING NAME UNFREEZES IT.** The whole point of the snapshot is that its bytes cannot move under the measurement; a second agent that picks the same obvious name — `frozen/`, `base/`, `before/` — reaches in and moves them, and the run that was carefully isolated from the working tree is measuring a directory two agents are writing. Measured: one lane's frozen clone was clobbered mid-run by a peer and it caught the collision only because its numbers stopped reproducing; it re-froze under a private path and re-measured. The failure is quiet in the usual way — a scan completes and prints — and it is the same defect as running from the working tree, arriving through the place chosen to escape it. So name a snapshot after the LANE and the REVISION, not after its role. A result quoted without the revision it came from is not a measurement, and "I rebuilt and it went away" is the tell that the first build measured the edit rather than the tree. **AND THE SNAPSHOT THAT MAKES A NUMBER QUOTABLE IS EXACTLY WHAT MAKES ITS DIAGNOSTICS STALE, WHICH IS THE TRAP ON THE OTHER SIDE OF THIS RULE.** A frozen build is pinned so its RESULT belongs to a revision — and every warning, assert and abort it printed is pinned with it. Those read as facts about the tree, and they are facts about a revision that a shared checkout has already left behind: the log is fresh, the reasoning is sound, and the defect it names was fixed hours ago. It is the stale-`DFAIL` failure mode arriving through the instrument this file PRESCRIBES, so the discipline that protects the measurement is what corrupts the relay. Measured: a compiler warning (`incompatible pointer types passing 'long long *' to parameter of type 'int64_t *'`) was read out of a frozen build's log and relayed to a lane as live work; the receiving lane found the file already carried `int64_t` at `origin/main`, with a comment recording the fix, and the only thing at that line in the working tree was a THIRD lane's unrelated hunk — so the relay would have sent someone to re-fix a fixed line inside a file somebody else was holding. **So a diagnostic is quoted with the revision that produced it, exactly like a number, and is RE-READ AT `origin/main` before it is relayed as work** — the number is what the frozen revision is for, and the diagnostic is what it is not. The tell is that you are about to describe a defect in the present tense from a log you did not just produce. The corollary is the reason this is not a burden: an agent that cannot build is not being denied a gate, it is being kept out of the shared tree's way, and the one process that DOES build owes every agent the revision its number belongs to. **AND IT IS NOT ONLY BUILDS — A STATIC SCAN READS THE SAME MOVING TREE, AND ITS FAILURE IS THE QUIETER ONE.** Everything above is about a build reading its inputs at different instants, and a build at least CRASHES when it does — a struct read one slot early segfaults. A scan does not crash: it completes and prints a number. Measured with several lanes live: three consecutive runs of ONE scan found the corpus digest changed under EVERY ONE of them, four distinct digests across three attempts, so no stable window existed at all; and an earlier run of that same scan reported 98 broken contracts because a peer's half-written file was read mid-scan, which INVERTS the signal exactly, since every field of one census loses its reader at once. Neither number was noisy — both were about NOTHING, and nothing in the output said so. So the frozen snapshot is the rule for EVERY instrument that reads the tree, `citegen`/`fieldgate`/`idlgen` included, and a BEFORE/AFTER is two runs on ONE frozen state — a baseline copy of the changed script with the change reverted, every other input shared, both runs back to back — never one run before an edit and one after, because the tree moved between them and the difference you attribute to your diff is mostly somebody else's. A scan run against the live tree anyway yields a number belonging to NO REVISION, and saying so is part of reporting it.
- **A SUBAGENT DOES NOT BUILD. THE MAIN AGENT OWNS EVERY BUILD, AND THAT IS THE WHOLE OF THE DIVISION.** No `build.mjs`, no compiler, no gate `.mjs`. A subagent reads, greps, CURLS, reasons, writes the change, and DRIVES THE ALREADY-BUILT ARTIFACT — `testing/harness.js` against the wasm the main agent last built costs no compile, so reproducing a real page's abort in real Chrome is a subagent's job and always was. What it must not do is compile.

Nine parallel agents produced less than one serial agent would. For `build.mjs` that IS the build: an agent doing exactly that compiled 302 translation units and **overwrote `engine/host/out/qjs.{js,wasm}` and `extension/lib/qjs/qjs.mjs` in the SHARED tree**, from a working copy holding its own uncommitted files plus a peer's in-progress ones — an artifact belonging to no revision, sitting where every harness driver looks. - **A BULK GATE IS RUN ONCE, BY THE MAIN AGENT, AND SUBAGENTS REQUEST IT — they never run it themselves.** test262, WPT and solvergate are whole-corpus runs over a SHARED tree on a SHARED machine, so N subagents each running one is not N times the coverage, it is the SAME number computed N times at N different unknown revisions, and it is worse than wasteful: concurrent corpus runs are the loaded-machine defect manufacturing itself. The four worked examples above are all one machine under load, and the arithmetic is not marginal — a 4-core box at load 7.13 makes an elapsed-time kill (test262 at ~590 s, WPT at 60 s per test) fire on healthy code, so every agent's run corrupts every other agent's number AND its own. Two agents waiting on the same corpus is not parallelism at all; it is one gate run twice, serialized by the CPU rather than by anybody's decision, with neither copy trustworthy. So: **the main agent owns the gates and serializes them.** A subagent that needs one states WHAT IT NEEDS TO KNOW and at WHICH revision, and gets back the result with its revision pair — one run answers every agent that asked. What a subagent still does for itself is the TARGETED exercise: one fixture, one file, `test_forced.c`, a single `wpt.mjs` path — that is not the bulk gate, it is how a change is exercised so its asserts get a chance to fire, and it is cheap enough to be nobody's bottleneck. **The DCHECKs remain the gate** (§the engine asserts its own invariants at their origin); the corpus is how code gets EXERCISED, never the thing that certifies a change, so a subagent blocked on a corpus number is usually a subagent that should be reading the ownership contract at the site instead.

An unsupported construct FAILS LOUD (an honest gap to build at the root, e.g. module support in `JS_FlowNew`), never papered over.
- **A passing RESULT does not prove the feature ENGAGED — the harness measures both.** `JS_FlowPreemptStats` reports preempt-requested vs fired; their divergence is exactly where the feature was gated (a body with no adopting driver), so the harness FAILS any run below 100% engagement — a category can never masquerade as green while the feature silently skipped its logic, regardless of codebase state. Correctness comes from the test262 oracle; coverage comes from engagement. **BUT ENGAGEMENT IS A RATIO, AND A RATIO CANNOT SEE WORK THAT NEVER STARTED — SO 100% IS A STATEMENT ABOUT ITS DENOMINATOR AND NOT ABOUT THE CORPUS.** Engagement divides fired preempts by requested ones, and both are counted over code that EXECUTED; a body no run ever entered contributes to neither side, so it cannot lower the figure and its absence is unrepresented in it. That is a different hole from the one engagement was built to catch — that one is a body that ran with the feature gated OFF, and this one is a body that never ran — and the metric is blind to the second by construction. Measured: `test262.conf` carried `mode=default`, which the corpus's own INTERPRETING.md contradicts in a MUST ("each test must be executed twice: once in ECMAScript's non-strict mode, and again in ECMAScript's strict mode"), so **39620 of 43523 files bore none of the four exempting flags and were executed sloppy ONLY — 47.7% of required executions never performed**. The run reported `0/43520 errors, 0 leaks, feature: 100.0% engaged` and every one of those numbers was true of the half that ran. It is also worse than an excluded file, which at least appears in a NOT-RUN count: the file WAS collected, so the missing execution appears in no exclusion list, no skip tally and no NOT-RUN line at all. **So a coverage figure states WHAT IT IS A FRACTION OF, in the same line, or it is not a coverage figure** — and a count of files says nothing about executions when a file owes more than one. Run the WHOLE corpus (default, no arg) for the honest number — cherry-picking a clean subdir and calling a category "supported" is banned self-deception. Leaks are surfaced by the `gc_obj_list` walk in `JS_FreeRuntime` (built NDEBUG so a leak logs+counts as a failure). Test all categories; the time-travel features must be transformed into every one, in spec order so no subproblem is skipped. Use design review, not a test metric as a target (a smaller number is not automatically worse). Browser tests are in C. Delete a regression test after use — it prevents better designs.
- **A TEST FILE THE GATE DOES NOT COLLECT IS AN EXCLUDED TEST, AND AN EXCLUDED TEST IS A FAILURE.** It is the same defect as a directory that is not checked out, and worse, because the total LOOKS complete: a gate that collected `.any.js` and `.window.js` only left more than half the checked-out corpus — nearly all of `html/browsers` — never run and never counted. WPT classifies a test document by what it LOADS (a file that pulls in `/resources/testharness.js`), never by a naming convention, and so does this gate. An HTML test is FETCHED from the corpus's own server rather than read off disk: a `.sub.html` is a TEMPLATE whose hosts and ports wptserve substitutes, and running the bytes on disk tests the template. **AND A TEST THAT IS COLLECTED, RUNS, AND REPORTS IS STILL NOT A TEST THAT MEASURED ANYTHING — ITS OWN FIXTURES CAN BE UNREACHABLE, AND THEN IT RETURNS A SMALL HONEST NUMBER THAT READS AS A SMALL HONEST RESULT.** The excluded-test rule above is about files the gate never collects, and a collection audit can find those. This is the case AFTER collection is correct, which is why no audit here could see it: every `idlharness` document in the corpus was reached, ran, and reported — **exactly two subtests each**, for its setup and its harness, because `idlharness.js` fetches its own `.idl` from `/interfaces/` and that directory was in no reachability list. The family passed every self-check the gate makes about its own collection and **had never executed one IDL assertion in this tree**, while being the only oracle for a property no local instrument can ask. The diagnostic existed exactly ONCE: one document said `Error fetching /interfaces/cssom.idl` in words and the other twenty-two timed out awaiting the same promise, so twenty-two copies of one cause wore the shape of a slow test. So a gate reports a test's SUBTEST COUNT beside its verdict, and a family whose members all report a floor of two is a family to open — and when a test declares fixtures (a fetched IDL, a serviced resource, a substituted host), the reachability of those fixtures is part of collecting it, not a separate question the test is left to discover at runtime. The gate reports PER AREA as well as in total — one number in which `encoding` answers three quarters of a million subtests is a number in which every other component is invisible.
- **A MEASUREMENT THAT A LOADED MACHINE CAN FALSIFY IS NOT A MEASUREMENT, AND A WALL CLOCK IS THE USUAL WAY IN.** Four separate checks in one session reported an artifact of HOW they ran as a defect in WHAT ran, and each one produced a confident false red that sent someone hunting a phantom: the seam assertion fired at 14486 ms of ELAPSED time with `points asked=0` and could not tell a stretch that offered no suspend point from one that was DESCHEDULED (a descheduled thread executes no instructions and so reaches no preempt check either, which is why that second number did not save it); `g_tramp_frames_live` was one process-wide count for run-test262's SEVERAL corpus threads, so its unwound-chain DCHECK fired on a race between two healthy threads; `wpt.mjs` killed a test after 60 s of elapsed time and reported it in the same column as a DCHECK naming a missing capability, so `dom/ranges` read 15743 pass against a 25056 baseline with an IDENTICAL fail count; and `test262.mjs` killed the corpus at 590 s and reported it through a message naming three causes it distinguished none of ("segfault/abort/timeout"), so a healthy binary read as a corpus-wide crash. **MEASURE THE THING THE INVARIANT IS ABOUT** — CPU actually consumed (`RLIMIT_CPU`), or work actually performed (forks + flows + jobs), never elapsed time; where the host has no CPU clock, CHECK that rather than assume it (emscripten answers every WASI clock from `emscripten_get_now()`, and musl's `clock()` lands in the same place). **A budget that must remain for a case the real measure cannot see — a deadlock consuming no CPU — is a BACKSTOP, is generous, and reports through a DIFFERENT SIGNAL so the two never collapse into one verdict** (`SIGXCPU` from the kernel, `SIGTERM` from the harness). Print both numbers, name which one is the verdict, and label the artifact case with the load average that explains it. The tell that you are looking at this defect rather than a real one: **a kill leaves an EMPTY tail where a crash leaves the output that preceded it**. And the response is never to raise the cap — making a saturated machine report green chooses the number over the forcing function — nor to accept a bounded probe as the corpus result, which is the cherry-picked-subdir self-deception under a new name.
- **ONE RUN OF A LIVE SITE IS NOT A MEASUREMENT, AND A BEFORE/AFTER BUILT FROM TWO OF THEM IS AN ARTIFACT OF THE SITE.** A live page changes under you — its bytes, its server's answers, the order its orphans are reached — so the same artifact against the same URL legitimately returns different numbers, and a single run reads as a clean measurement while carrying all of that variance. One site went 37 endpoints, then 0 with an abort, then 0 without one, across three runs of two builds, and the endpoint column was quoted as a regression before anyone had established the run-to-run spread. **A before/after belongs on FROZEN BYTES — a mirror, a fixture, a recorded payload replayed — where the only thing that changed is the engine.** Live sites are for DISCOVERING signatures, which is what they are uniquely good at: an abort with a real frame list names an unbuilt capability no fixture would have thought to ask for. Report a live number with its run count and its spread, or do not report it as a comparison. **AND THE RULE IS NOT ABOUT LIVE SITES — IT IS ABOUT REPEATABILITY, WHICH IS A PROPERTY YOU MEASURE AND NEVER ONE YOU INFER FROM BOUNDEDNESS.** A local driver that is bounded, offline, single-machine and finishes in seconds reads as deterministic, and that reading is an ASSERTION about a program nobody re-ran. Measured, and it cost a whole bisect: a two-instance driver reported 31 routed posts at one revision and 5 at another, the ratio was quoted as a 6× collapse localised to one commit, and a later lane ran the UNCHANGED pre-fix driver against ONE binary four times and got 5, 5, 31, 31 — then three more on a second build for 5, 31, 5. Seven runs, two modes, no code between them. The shape also PREDATED the accused commit by seventeen hours in a log already on disk. The mechanism was in the instrument's own banner all along (`"measure":"wall … isCpu":false,"sliceMs":12`): a wall-denominated quantum lets machine load pick which side of a race the run lands on. **So the run-count-and-spread obligation attaches to every comparison, and the cheap instruments are where it gets skipped** — precisely because their cheapness is what makes re-running them free. Run it until the spread is known BEFORE attributing a difference to a diff, and never call an instrument deterministic in a report unless a repeat is what established it. **AND ON A SITE THAT ABORTS, THE EMITTED-OUTPUT COLUMN IS NOT A MEASUREMENT OF ANYTHING** — how much a run learned before it died is a function of where the crash landed, so a crashing site's endpoint count moves on its own; the crash record is the stable fact and the count beside it is noise until the crash is gone.
- **A CAVEAT STATED AND THEN NOT APPLIED IS WORSE THAN NO CAVEAT, BECAUSE IT LAUNDERS THE NUMBER IT WAS ATTACHED TO.** The rule above says to establish the spread before attributing a difference; this is the failure that survives KNOWING it. The shape is not ignorance — it is writing the disclaimer, feeling the obligation discharged by having written it, and then reasoning from the numbers exactly as if it were absent. It is worse than silence because a reader takes the stated caveat as evidence the author weighed it, so the conclusion arrives with MORE credibility than a bare number would have carried, not less. Measured, in a relay one lane was about to act on: a comparison across four runs was handed over with "this host has no CPU clock, the quantum is wall-denominated, census counts vary run to run" written into the message — and the very next paragraph proposed a causal hypothesis whose entire support was two of those counts being small. A later run on a clean tree refuted it: the quantity said to be blocked came back with the supposed cause still present, and the two runs where "nothing retired" had produced 11 and 13 censuses against the 103 and 290 of the runs where things did — one engine at two amounts of progress, which the caveat had already named and the argument had already ignored. **THE TELL IS SYNTACTIC AND YOU CAN CHECK IT ON YOUR OWN DRAFT: a paragraph that names a source of variance, followed by a paragraph that reasons from a quantity that variance governs, with nothing in between that BOUNDS it.** So a caveat is not prose to be discharged — it is a CONSTRAINT ON WHAT MAY BE CONCLUDED NEXT, and either it eliminates the reading (say so and drop the reading) or it does not (say why, in the same breath). And when a comparison's two sides differ in HOW MUCH WORK THEY DID, that difference is the first hypothesis and not the last: a count that never rose in a run that barely ran is not a finding about the mechanism, it is a finding about the run.
- **MEASURE WHAT THE SHIPPED PATH WRITES, NOT WHAT A HARNESS PRINTS.** A marker a harness prints and production never emits reads ZERO for a page that learned a thousand endpoints — the §Architecture default-hides-a-hole defect wearing a measurement, and a zero that is a property of the instrument rather than of the run. The renderer deliberately does not tee its stdout to the console (a hot engine's traffic would bury it), so a console scrape is the wrong surface by construction. Before counting a token, GREP FOR ITS WRITER and confirm a shipped path emits it; read the result DOCUMENT rather than the log. An absent count and a zero count are DIFFERENT facts and must never be averaged: a run that reported no document is not a page that was analysed and found clean.
- **A SCAR IS NOT A WOUND — AN ORPHANED COMMENT IS NOT AN ABSENT MECHANISM.** A comment describing an upstream mechanism this fork REPLACED survives the replacement and then reads as a gap: one agent concluded the backtracking regexp had no suspend seam from a leftover "call the interrupt callback often", when the yield points, the split begin/step/end and the driver that parks between slices were all present. GREP THE ENTRY before writing the code a comment seems to ask for, and when you replace a mechanism, delete the prose that described the old one in the same diff. **AND THE MOST DANGEROUS STALE COMMENT IS THE ONE ANNOUNCING A REMOVAL, BECAUSE EVERY OTHER KIND SENDS YOU TO LOOK AND THIS ONE TELLS YOU NOT TO.** A scar describes a mechanism that WAS there and reads as a gap; a reader who acts on it goes and looks, and finds out. A comment saying a mechanism IS GONE closes the question — it is read as a completed deletion, so nobody greps, and the thing it claims to have removed goes on running under a paragraph certifying its absence. Measured, inside the instrument this project uses to catch stale claims: `citegen.mjs`'s header said in capitals that its file-vote fallback "IS GONE" and an inline comment said it "can no longer decide a citation on its own", while the line DIRECTLY BENEATH that comment did exactly that — and it was deciding **8300** citations' standard by inference, out of 32614 that name no standard at all. An auditor of the auditor would have looked for the guess, read those two sentences, and concluded there was none. So a removal is announced only where the grep now answers empty, and announcing one is the same obligation as making one: run the grep, in the same diff, and if anything answers, the sentence is the thing that is wrong.
- **A TRANSLATION UNIT NO GATE COMPILES IS OUTSIDE THE GATE, AND THE SHIPPED ENTRY POINT IS THE ONE THAT ROTS.** `test_forced.c` and `main.c` are ALTERNATIVES — each owns the program's entry — so the default build links one and never touched the other, and the production ABI entry stopped compiling entirely (a missing include, and a `(void)unused;` naming an argument that does not exist) across many commits in which every gate was green. That is the excluded-test defect one layer down, and it is worse: an unbuilt entry cannot be tested by anything. So `engine/build.mjs` COMPILES THE ENTRY IT DID NOT LINK, with the flags taken from the link's own argument list rather than restated. The rule generalises: a file that is in the program but in nobody's build is not "unused", it is unverified, and the first change that breaks it is invisible until someone builds it by hand.
